## 2026-08-27 · feat(admin): the admin search finds a GUEST by name, across every celebration

Owner ruling 2026-08-27, asked directly and framed to him as a privacy posture call — should an admin be able to search any guest by name across every celebration? **"YES."** It pairs with his earlier same-day ruling: *"we must be able to find them and have our actions as admin available when we find them."*

**RULE 0 — nothing was rebuilt.** The cross-record search already ships (`ugatSearchInner`, `lib/ugat/data.ts`), already runs parallel reads over five tables, already opens the real record per hit (#4903), and `guest` was **already** a member of `UgatEntityType` with a label, icon and colour tokens in `UGAT_TYPE_VOCAB`. This adds a sixth read and a destination; it draws nothing.

**The measurement that decided the implementation.** Guests were searchable nowhere in the admin — the only `from('guests')` in the whole tree is a count. Read out of production rather than assumed: **`guests.display_name` is populated on 0 of 40 rows, while `first_name` and `last_name` are on 40 of 40.** A search written against `display_name` — the column the events, users and vendors arms all match on, and the obvious one to copy — would have compiled, passed review, returned nothing for every guest who exists, and looked exactly like a feature nobody uses. All three are searched; `display_name` is simply never searched alone.

**A full name works, because it is split over two columns.** `first_name.ilike` and `last_name.ilike` are separate, so "Maria Santos" matched neither on its own — the owner typing somebody's whole name is the expected case. `guestNameOrFilter` adds `and(...)` pairs in both orders ("Santos Maria" is how half a guest list gets written down).

**A latent bug in the shipped search, fixed in passing.** The sanitizer escaped `%` and `_` and nothing else — but `.or()` splits its clauses on COMMAS, so any query containing one (`Dela Cruz, Maria`) built a malformed filter, PostgREST refused the **whole** query, and all five arms resolved with an error and no rows. The box said "No matches" and nothing was logged. Rejected, not thrown; the only symptom is an absence. `sanitizeIlikeTerm` now strips `,()"` as well, and it is shared, so the four existing arms are fixed too.

**What a hit shows, and what it can never show.** The name, the RSVP status, and which celebration — a name alone identifies nobody. `email`, `mobile` and `address` are **not selected by the query at all**, so there is no arm of this feature where a contact detail reaches a screen; they live on the record's own surface, the privacy-preserving default the shipped record links already follow. The search is **by name only** — not a reverse lookup from a contact detail, which is a different power and was not granted. Deleted guests are excluded. A refused read is now logged rather than silently reading as "no matches".

**The privacy lock is narrowed, not lifted, and its wording was corrected in the same commit.** `lib/ugat/data.ts` carried an explicit lock — message bodies, face data, file contents, and "no individual guest PII in slice 1". The first three are **untouched and asserted untouched**. The guest half is superseded to exactly the extent the owner ruled and no further: SEARCH by name is open; the guests **table browser stays aggregate-only**, because browsing every guest was not what was asked for. A file that records a decision in its header and contradicts it in the middle gets read from the middle — so both the header and the table's own on-screen note were updated, not just one.

**Where a guest opens, and why.** A guest has no admin page: there is no `/admin/guests`, no `[guestId]` segment anywhere in the tree. A new `guest` kind in `ugatRecordHref` **delegates to the `event` arm**, landing on the celebration narrowed to that one row — the same answer this console's own guests table already gives, for the reason its comment already states. Delegated rather than copied, so the two cannot drift.

**`people` is deliberately NOT added, and this is the measured reason.** It has no admin surface at all — zero references to `people` or `person_id` in `app/admin`, which is structural, not a count. `/admin/users/[userId]` is the tempting destination and resolves for **none** of the people you could find by name: all 9 claimed people in prod carry no name of their own, and both people who DO have a name are unclaimed, so they have no user row and that page `notFound()`s. The two populations are disjoint, and a claimed person is already reachable through the `user` arm. Giving `people` a home needs a surface first, not a sixth entry in the switch.

**"With our actions available" is honestly unmet, and named rather than faked.** Of the admin's record-keyed jobs, guests have **zero**. A found guest can be identified and located; there is no admin action to offer on one yet. Attaching actions to guests is a product decision with a privacy dimension, not something to invent here — the surface is built so they can be attached when they exist.

Guards — new `lib/ugat/guest-search.test.ts` (23 assertions) plus 4 added to `record-href.test.ts`: the searched columns, full-name matching, comma/paren/wildcard safety, the contact-detail fence (asserted on the guest query block, not the file), deleted-guest exclusion, the untouched half of the off-limits lock, the table browser staying aggregate-only, and the **wiring** — that the search calls the helpers, pushes the group, that the bar says it finds guests, and that `requireAdminAction()` runs before the service-role read. The wiring half is the half that matters: every pure assertion passes with the search never calling any of it, which is the state `href` shipped in for its whole life. 12 mutations, each measured by occurrence count before → after, all red.

SPEC IMPACT: None — no schema change, no migration, no price, no flag. The owner's 2026-08-27 ruling that narrows the guest half of the admin off-limits lock is recorded in the corpus `DECISION_LOG.md`.
