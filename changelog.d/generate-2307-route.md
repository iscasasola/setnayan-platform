## 2026-07-25 · feat(bir): quarterly 2307 filings cron route (compute + record; PDF stubbed)

Migration `20260516100000_iteration_0026_bir_2307_filings.sql` shipped the `vendor_2307_filings` table AND the `quarterly_2307_generation` pg_cron schedule, but never the endpoint the schedule POSTs to. Every quarterly firing since has 404'd (and before migration `20270930270000` re-pointed the job's `X-Cron-Secret` at Supabase Vault, it was also sending an empty secret). This lands the missing route.

- **`app/api/admin/cron/generate-2307/route.ts`** — POST-only (GET → 405), `runtime = 'nodejs'`, `dynamic = 'force-dynamic'`. Auth mirrors the other cron routes: `X-Cron-Secret` (what the DB job sends) **or** `Authorization: Bearer`, both timing-safe via `lib/secure-compare`, fail-closed 503 when `CRON_SECRET` is unset. Resolves the target quarter (default: the quarter that just ended on the **PH** calendar — the job fires just after the boundary), optionally overridden by a `{ tax_year, tax_quarter }` body. Reads `vendor_payouts` rows actually PAID inside the quarter, aggregates gross + withheld per month-of-quarter, and UPSERTs one `vendor_2307_filings` row per vendor on `(vendor_profile_id, tax_year, tax_quarter)` — regeneration UPDATEs in place per the migration's audit-trail contract, appending to `audit_log` and bumping `regenerated_count`. A re-run whose figures are unchanged writes **nothing at all**.
- **`lib/bir-2307.ts`** (new, pure) — quarter resolution + window bounds, body-override validation, month-of-quarter attribution, the ATC mapper, and the per-order stage allocation. All PH-calendar (`Asia/Manila` is UTC+8 year-round, so a fixed offset is exact). The timezone is load-bearing exactly once and it is the case that bites: at 2026-01-01 00:30 PHT the UTC clock still reads 2025-12-31, so a UTC month read would file Q3 instead of Q4 every January.
- **The triple-counting guard.** `lib/payouts.ts` (`dispatchVendorPayouts`) stamps the **order-level** `gross_centavos` and `bir_withholding_centavos` onto **every** stage row of an order, so a coming_soon vendor's 20/60/20 release carries the full order withholding three times. Summing the column across paid rows would report 3× the tax actually withheld. `allocateOrderTotals` splits the order-level totals across that order's stages by release weight in integer centavos (last stage absorbs the remainder), so the shares re-sum to exactly one order's withholding and each quarter only counts the stages paid in it. That's why the route also reads the non-paid sibling rows of each touched order.
- **`totals.atc_rows[].rate_bps` is the EFFECTIVE rate**, derived from the aggregated figures rather than the ATC's nominal 2%. `lib/payouts.ts` withholds `BIR_WITHHOLDING_BPS` = 50 bps (0.5%, RMC 8-2024 marketplace rate); printing WI158's nominal 200 bps next to real 0.5% numbers would make the certificate internally inconsistent.
- **PDF generation is explicitly out of scope** — a `TODO(0026-pdf)` marks the render + R2 upload + `status → 'generated'` + `vendor_payouts.form_2307_issued` flip. A filing therefore lands at `status = 'queued'` with the PDF columns NULL, which is the honest state: the figures are computed and recorded, the document is not.
- **`lib/bir-2307.test.ts`** — 31 node:test cases over the pure helpers: quarter resolution (all four real cron instants, both sides of every PHT midnight boundary, the Jan-1 PHT-vs-UTC year-turn), window contiguity, override validation against the table's CHECK bounds, month attribution across the PH/UTC day line, the ATC mapping, the 20/60/20 allocation (incl. rounding remainder, sort-order independence, zero-weight orders), and end-to-end per-vendor aggregation asserting 400c not 1,000c on the triple-count fixture.

No migration — the schema and the cron schedule already exist in prod; this PR is purely the missing route + its pure helpers.

**Expected output today: zero filings.** Setnayan takes 0% commission and never sits in the vendor↔couple money path (settlement is off-platform per the 2026-06-07 as-built correction), so no `vendor_payouts` row is ever marked paid and there is nothing to certify. The route reports that empty result honestly rather than manufacturing rows. Its practical value right now is that the quarterly job stops 404'ing and starts returning a truthful, auditable `{ ok: true, … , filings_upserted: 0 }`.
