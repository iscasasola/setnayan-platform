## 2026-07-26 · fix(schema): 26 queries read columns that do not exist — all 26 fixed, plus the CI guard that ends the class

**The class.** PostgREST fails the WHOLE query with `42703 undefined_column` when ANY named column is unknown — it does not skip the bad one. supabase-js reports `{ data: null, error }`, and a downstream `?? []` / `?? null` turns that into "no rows". The feature then silently does nothing, in production, indefinitely: no error, no red test, nothing in the type system, because a PostgREST select list is a string and the tables live in another process. One bad column also takes the whole ROW with it — a header selecting `business_name, logo_url, city` loses the name and the logo too, not just the city.

**Triage.** A static sweep of `apps/web` flagged 26 candidate sites. Every one was read by hand before being touched. **26 REAL / 0 false positives** — the `.from()`→`.select()` window heuristic misattributed nothing. 22 of the 26 were a wrong column NAME; the other 4 were a column production genuinely does not have.

**Fixed by migration `20271011120000` (4 columns).** The subset where "rename the read" was wrong: the feature is real, the WRITE path targets the same column, and prod simply lacks it — removing the reads would have deleted shipped UI. Two root causes, both new and both worth naming. (A) **`CREATE TABLE IF NOT EXISTS` silently no-ops against a pre-existing table of a different shape**: the migration is recorded as applied, `db push` reports success, and the declared column never lands — `concierge_abuse_flags.admin_notes` (declared 20260518000000:83) and `manpower_gigs.posted_by_user_id` (declared 20260704020000:52, `NOT NULL`). (B) **the feature shipped with no migration at all** — `events.kwento_flash_auto_wall` and `events.last_kwento_notify_at`. Consequences: the coordinator's flash-auto-wall kill switch did nothing (its UPDATE failed silently and the read defaulted to ON regardless of their choice); flagged-story notifications to the couple had **no debounce at all**; posting a manpower gig 42703'd, which is why prod has 0 gigs; and clearing or confirming a concierge-abuse flag would have 500'd the admin console for any real flag. All `ADD COLUMN IF NOT EXISTS`, `SET NOT NULL` applied only when provably safe.

**The guard — `apps/web/lib/security/select-column-scan.ts` + `.test.ts` (10 tests).** Diffs every `.from('t').select('…')` in `apps/web` against the schema derived from `supabase/migrations`, reusing `readSchema()` from `lib/security/migration-schema.ts` rather than cloning it (two parsers would disagree, and the disagreement would be invisible) — so it runs offline with no database. Shaped like `export-coverage-guardrail.test.ts`: a **ratchet, not a wall** (`KNOWN_PHANTOMS` = 2 entries, `KNOWN_PHANTOM_CEILING` = 2, T3 forbids growth, T4 forbids an entry outliving its cause), with **anti-vacuity enforced rather than assumed** (T5 the schema parsed ≥300 tables; T6 the scanner found ≥2000 select sites and >90% resolve to known tables; T7/T8 fixture-driven positive and negative controls that hold independent of repo state; T9/T10 the select-list parser and the attribution guards directly). A guard that quietly matches nothing is worse than none — that is exactly how this class survived.

Measured on the fixed tree: **374 schema tables · 3064 select sites · 307 distinct tables · 2995 sites resolving to a known table · 8 phantom sites across 2 allow-listed keys.** Both remaining keys (`events.story_tone`, `events.story_language`) were created by `RENAME COLUMN` inside a `DO` block, which the shared parser handles for neither reason; both verified present in prod before being allow-listed.

**Also fixed a defect in the shared parser.** Its ALTER regex is non-greedy to the first `;`, and `--` comments were not stripped before that pass, so a prose semicolon inside a comment truncated the statement before its first `ADD COLUMN` (`20260912000000:55` — "…tap-to-start (autoplay blocked); streamed from R2…" swallowed all ten columns that ALTER adds). Stripping comments first — the same treatment the CREATE body already got, for the same reason — recovered **20 of the 22** keys the guard was otherwise about to allow-list. Widening is safe for the two existing consumers by construction: T10 (export) and SEEN (erasure) assert that classified tables ARE seen, so seeing more cannot trip them; both verified green.

**Honest limits, documented in the docblock rather than in a commit message nobody re-reads:** the 700-char window heuristic; interpolated `${…}` selects are skipped entirely; dynamic table names are invisible; unknown tables (including all VIEWS) are skipped rather than flagged; only `.select()` is checked, so `.insert()`/`.eq()`/`.update()` can still name a phantom; test files are out of scope. And the sharpest one — **the migrations can themselves be wrong about production**: this guard called both cause-(A) columns above VALID because the migration text declares them, while prod 42703'd on both. Closing that needs a live-database diff, which does not exist yet.
