## 2026-09-28 · perf(maker): a pick shows at once, a save never reloads the whole Maker, and every stage is loaded before it is asked for

Owner, verbatim (2026-09-28), on the Event Hub Maker: *"is it possible to load everything so it runs smoothly?"* · *"picking something takes a lot of time before the website reacts"* · *"and a lot of times. it reloads the whole page. which shouldn't"*.

- **A pick the canvas already shows no longer reloads it.** The canvas hold (`element-preview.ts`) held only element choices; it now holds any change the bridge has drawn — a part, words, a scene's background (`sceneBg`, laid by the server's own functions) and a scene taken off the page (new bridge message `sceneShow`) — and compares BOTH halves of what the canvas shows: every scene's canvas and which scenes each stage draws (`canvasOrderOf`, from the navigator's own resolver). A render the canvas could not have shown (Undo, Restore, Apply, a scene put back, a reorder, another tab's write) still reloads it, double-buffered. Every write the bridge did not draw — any Maker form, and every draft save not marked `held` — now releases the hold, so nothing can be absorbed by mistake. A refused background save puts the canvas and the hold back.
- **One render per burst of picks, not two per pick.** `hubDraftAction` (save · reset · undo · restore), `draftEventsAndReturn`, the widget draft door, the drafted hero and backdrop no longer call `revalidatePath` — a draft reaches no guest, and the revalidation made the action's own response carry a full render of the Maker that the caller then asked for again. Every Maker draft save goes through `lib/maker-refresh.ts` (`makerSave`), which refreshes ONCE after the last save in flight lands (so quick taps no longer race the hold). The drafted hero no longer invalidates every guest page. Apply still revalidates the guest page it changed.
- **A save never remounts the Maker.** Every Maker form redirected to its `return_to` + `?saved=1` — a new page key, so the App Router swapped the whole Maker for the grid skeleton and mounted it fresh (the canvas loaded from the top, un-buffered). The shell now points every Maker form at the address the couple is already on (`lib/maker-stay.ts`, capture-phase submit listener) and `resolveReturnTo` honours it verbatim (`maker_stay=1`). A drag's remaining steps are held by the shell instead of `?chain=`. Details' "what the prints include" form posted natively to `/api/hub-print/words` (a full document reload): it now saves in place (`soft-post.tsx`; the route answers JSON when asked).
- **Everything loaded up front.** After first paint, when idle, the other three stages load hidden behind the canvas (`buffered-canvas-frame.tsx`, one at a time, never while a save is in flight); a stage switch shows the frame already loaded — the same iframe, never moved in the DOM (moving one reloads it) — and the stage left stays warm. Every pick the bridge draws reaches the warm stages too; one still loading is dropped and loaded again after the save. Capped at the shown stage + 3; none on a phone with `deviceMemory` ≤ 4 or on save-data. The canvas now stays mounted (hidden) under Hero, Logo, Reveal, Love Story, Details and RSVP, so coming back is instant. Every face in the Font dropdown and the couple's own photos are fetched in the Maker's own document on idle (`lib/maker-preload.ts`) — no face gains a `preload`, guest pages are untouched.
- Measured (harness around the real `BufferedCanvasFrame`, stand-in guest page at the ~2 s production load, 375 px): a stage switch took 2,009–2,021 ms and one page load before; 0.7–9 ms, the same document and zero loads after.
- Tests: `a-maker-pick-never-reloads-what-it-drew.test.ts` (every kind of pick through the server's own draft → overlay → stage-list pipeline), `a-draft-save-does-not-rerender-the-maker.test.ts`, `switching-stage-or-page-never-navigates.test.ts`, `maker-stay.test.ts`, `maker-refresh.test.ts`; pinned guards extended (`buffered-canvas-frame.test.ts`, `element-preview.test.ts`, `the-made-once-items-are-pages.test.ts`, `a-scene-background-previews-instantly.test.ts`).
- Not done: a performance profile of the Maker's first-load long tasks (step 4 of the brief) needs a signed-in local event; none exists that a session may open (the local env points at production), so nothing was cut on a guess.
