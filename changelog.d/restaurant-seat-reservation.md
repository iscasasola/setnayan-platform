## 2026-08-01 · feat(reservations): Setnayan holds the restaurant table — seats, a date of its own, and a cancellation that actually gives the seat back

Owner 2026-08-01: asked whether to link out to the restaurant's own booking page or to **hold the reservation ourselves**, he chose to hold it — real availability, real confirmations, real cancellations. Canonical framing is `Setnayan_AI_Gap_Leaves_Travel_Dinner_Date_2026-07-17.md` Part C-ter: *book a table by restaurant × meal-timeslot × party-size, with confirm-back from the restaurant; settle on-site, 0% commission, Setnayan holds no money.*

**Most of this already existed and was NOT rebuilt.** `vendor_service_time_slots` (migration `20260928000000`) already gives a vendor named per-service windows with times — "7PM Seating", 19:00–21:00. That is the supply primitive and it is reused as-is. `event_vendors.service_time_slot_id`, `acquire_service_time_slot`, the vendor authoring UI in `services-manager.tsx` and the couple picker in `accordion-lock.tsx` are all untouched. `vendor_schedule_pool_bookings` is deliberately **not** conflated with this: it is day-granular (a photographer books your whole wedding day), and a table at 7pm is a different shape.

**The four things that were genuinely missing**, established against prod rather than against the specs:

1. **Capacity was counted in bookings, not in people.** `acquire_service_time_slot` does `count(*)` over confirmed `event_vendors` rows. A 40-cover seating would therefore have admitted **40 parties**. Party size is the entire point of a table reservation and had nowhere to live.
2. **The reservation had no date of its own** — the existing acquire derives the date from `events.event_date`. A dining date on a travel itinerary, or the rehearsal dinner the night *before* the wedding, could not be expressed at all.
3. **There was no reservation record to cancel.** Release was implicit in a status filter, and `vendor_status` has no `cancelled` label (`considering|shortlisted|contracted|deposit_paid|delivered|complete`).
4. **One `event_vendors` row per (event, vendor)** — a couple could not hold two tables at the same restaurant on two dates.

**How double-booking is made impossible.** Capacity here is a **sum** (seats), not a count, so no unique index can express it. The guard is a per-`(slot × date)` ledger row plus `CHECK (seats_taken >= 0 AND seats_taken <= seats_capacity)`, consumed by a single conditional `UPDATE ... SET seats_taken = seats_taken + n WHERE ... AND seats_taken + n <= seats_capacity`. Under READ COMMITTED a concurrent transaction blocks on that row lock and then re-evaluates the predicate against the newly committed row, so there is **no read-then-write window in application code at all**. The CHECK is an independent second belt: a future caller that writes the UPDATE wrong still cannot push the ledger past capacity — the transaction aborts. The lock domain is exactly `(slot × date)`, so a full 5 Aug never contends with 25 Dec on the same seating.

**Cancellation releases exactly once.** The status flip is itself a conditional `UPDATE ... WHERE status IN ('held','confirmed')`; a second cancel matches no row, returns `already_cancelled`, and never reaches the decrement. A cancelled reservation that still consumed capacity — and a double-cancel that minted capacity — are both covered by tests.

**A `held` reservation consumes capacity immediately.** That is what distinguishes holding the reservation from linking out. The restaurant then confirms (`held → confirmed`, capacity unchanged) or cancels (seats released). A pending state that did *not* consume capacity would let the table be sold twice while the confirmation was outstanding.

**`seat_capacity` is a NEW column, deliberately not a reuse of `slot_capacity`.** `slot_capacity` already means *bookings* to `acquire_service_time_slot`; making one column mean two units in two code paths is precisely the tile-vs-category vocabulary defect that made all three specialization desks unreachable in prod. It is also literally too small — `slot_capacity` is CHECKed `<= 50` and one restaurant seating can be 120 covers. `seat_capacity IS NULL` therefore doubles as the discriminator with no extra flag: NULL = an ordinary tier-#3 booking slot (unchanged behaviour), NOT NULL = reservable by the seat. The reserve RPC **fails closed** on NULL.

**Single-writer ledger.** `authenticated` is granted `SELECT` only on both new tables; every mutation goes through a `SECURITY DEFINER` RPC. `seats_taken` therefore cannot drift from the reservations that justify it, and a migration post-condition RAISEs if `authenticated` ever holds INSERT/UPDATE/DELETE. Post-conditions also assert `anon` holds nothing — asserting the **role**, since `REVOKE ... FROM PUBLIC` does not remove anon's own default-ACL grant.

**Shipped flag-dark.** `NEXT_PUBLIC_TABLE_RESERVATIONS_ENABLED`, default **off**. The flag gates the surface, never the safety: the DB guard is unconditional, so flipping it can expose a reservation UI but never an unguarded one. No existing booking path changes state with the flag down.

What they prove is the property that makes the race safe — the invariant is owned by a CHECK and one conditional UPDATE rather than by application sequencing.
