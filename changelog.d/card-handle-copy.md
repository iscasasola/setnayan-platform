## 2026-07-27 · feat(vendor-services): tell vendors to write "at" instead of "@" on cards

A vendor whose card line was refused purely because of an `@` ("Coverage @Tagaytay", "Reception @Shangri-La") got the generic "phone numbers, emails, links are not allowed" sentence and no way to act on it. The `@` stays blocked — the HANDLE rule cannot tell a venue from a real handle like `@juanphotos`, and loosening it would reopen the leak the gate exists to close (owner ruling 2026-07-27: "yes make it at Tagaytay") — so the fix is the copy. `findVendorTextViolation` now returns `SERVICE_HANDLE_MESSAGE` when `handle` is the ONLY category that fired, quoting the vendor's own word back at them (`Write "at Shangri-La" instead of "@Shangri-La".`); when `handle` fires alongside a phone / email / link / solicitation the GENERIC message still wins, so the softer tip can never mask a real leak. Plumbing is one optional field, `ContactMatch.sample`, populated for `handle` only; the detection rules and both filter profiles are unchanged. The sample is extracted with a display-only pattern because HANDLE's character class has no hyphen and would quote `@Shangri` at a vendor who wrote `@Shangri-La`.

SPEC IMPACT: None (copy only; the HANDLE rule is unchanged — owner ruled 2026-07-27 that @ stays blocked and the fix is the message).
