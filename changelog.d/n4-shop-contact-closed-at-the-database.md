- Migration `20271221366210_a_shops_contact_is_not_in_the_database_door`: revokes SELECT on both columns from `anon`, `authenticated` and `PUBLIC` (SELECT only — the shop's own INSERT/UPDATE is kept). ALSO rebuilds `public.vendor_market_stats` without `contact_email`: that view is `security_invoker`, public, and projected the email — a second door the brief did not name, and a view that would otherwise have 42501'd every marketplace read after the revoke. Post-conditions assert both roles lost SELECT, UPDATE survives, service_role keeps it, the view is invoker + public + contact-free, and `vendor_profiles_self` still carries both columns.
- The shop still sees its own contact details: My Shop, the open-shop wizard and the dashboard editor read through the definer view `vendor_profiles_self` (unchanged).
- Two browser-session readers moved to the service role through ONE lookup (`lookupExistingVendorByEmail`): "start a thread by the shop's email" on the couple's Messages page and the couple-side invite's already-on-Setnayan check. The lookup re-states the public-read row rule (verified + visible shops only), matches the address exactly (ILIKE wildcards escaped — an unescaped `a%` would be a letter-by-letter oracle), and answers only id + name.
- Guards: `lib/security/shop-contact-is-not-session-readable.test.ts` (every select/filter/or-string/embed naming either column must run on a PROVABLY service-role client — nearest binding, or every caller of a parameter; plus: My Shop reads them via the self view; no migration re-grants them) and `tests/db/a-shops-contact-is-not-in-the-database.db.test.ts` (11 tests as real anon/authenticated roles, with positive control and a rolled-back neutralisation). The two older vendor_profiles column suites now pin anon at 20 columns and exclude the contact pair from the stranger allowlist.
