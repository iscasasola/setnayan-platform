## 2026-07-27 · test(booking-fee): assert the APP-LAYER post-conditions of `collectBookingFeeAtLock` — the ORDER and the PAYMENT, not just "it returned"

The vendor booking fee is **armed in production** (`NEXT_PUBLIC_BOOKING_FEE_ENABLED=true`). Verified read-only against prod at the moment of arming: nothing has billed and nothing *can* bill yet (0 chat_threads, 0 event_vendors with a marketplace link, 0 verified vendors). **The first real marketplace booking will therefore be the first production execution of this path — on real vendor money.**

**The gap.** The SQL half was already covered end-to-end by `apps/web/tests/db/booking-fee-lock.db.test.ts` (taper, free-5 boundary, idempotent re-lock, off-platform, non-contracted, settle bridge, sourced-set parity). The **TS half was not covered at all**: `collectBookingFeeAtLock` (`apps/web/lib/booking-fee-lock.server.ts`) is what turns a computed charge into money a vendor actually sees — it resolves the payer, inserts an `orders` row (status `submitted`, `SN`+hex reference code, VAT-inclusive `vendor_`-prefixed `service_key`) and a `payments` row (channel `manual`) so the bill lands in `/admin/payments` for reconciliation. None of that was asserted anywhere. `booking-fee-rederive.db.test.ts` even hand-mints the order the TS "would" write (`seedOrder`) — which tests the hand-mint, not the code.

**Its signature failure mode is succeeding while doing nothing.** Five of its arms (`disabled`, `skipped`, `free`, `zero_fee`, `no_payer`) return a non-error status and write no money row; two more (`order_exists`, the payments-rollback) are about rows that must not be duplicated or must be un-written. A test asserting "no throw" would pass against a function whose body had been deleted.

**New file — `apps/web/tests/db/booking-fee-order-postconditions.db.test.ts`** (12 tests, 860 lines). Every assertion is a **positive post-condition — a row exists with the right values**, never merely that the call returned. It drives the **real production function** (not a re-implementation) against the **real replayed schema** in PGlite, through a supabase-js-shaped adapter that **returns errors as data rather than throwing** — the rollback arm is only reachable that way. Writes run as `service_role`, the sanctioned caller, so `guard_money_row_insert_caller` (SEC-4b) is exercised rather than bypassed by a superuser.

Covered: the happy path (charge + order + payment, with the ORDER↔PAYMENT link asserted explicitly and the payer proven to be the **vendor's claiming user, not the couple**); amount agreement across all three layers (ledger centavos ↔ order pesos ↔ payment pesos) for a sub-peso taper-crossing value (₱123,456.78 → ₱5,234.57) and for the ₱50 floor; `no_payer` on an unclaimed vendor profile (charge survives, **neither** money row is written); order-layer idempotency (two calls → exactly ONE order and ONE payment); free-5; off-platform; vendor-brought import; the package anchor (ONE order) vs a covered row (none); and **the compensating delete** — a test-local `BEFORE INSERT` trigger forces the payments insert to fail and the test asserts the just-created order **is gone**, then proves the charge is left retryable by actually retrying it.

**Neutralisation.** Five one-branch sabotages of the production file, each confirmed to turn a **named** test red, then restored byte-identically (`git diff` clean): skip the payments insert → *billable lock…* (+5 more); skip the orders insert → same; drop the `no_payer` early return → *unclaimed vendor profile…*; drop the idempotency guard → *calling twice…* reports **2 orders, not 1** (a real double-bill); drop the compensating delete → *payments insert fails…* prints the orphan bill.

Test-only. No production code, no migration, no schema change.
