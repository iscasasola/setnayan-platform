## 2026-07-26 · feat(ci): schema-drift guard — the ledger said applied, the schema disagreed

`CREATE TABLE IF NOT EXISTS` silently no-ops when the table already exists in a different shape. The columns inside never land, but the statement **succeeds**, `supabase db push` reports success, and the version is written to `schema_migrations`. The ledger says applied; the schema disagrees. Nothing anywhere goes red. `20260628000000_v2_additive_phase_a.sql` uses that idiom for tables that already existed.

**The guard** — `apps/web/tests/db/schema-drift.db.test.ts`, auto-discovered by the existing `test:db:ci` glob inside the required "typecheck + lint" job, so it runs on every pull request with **no production credentials**:

- Replays migrations into PGlite and diffs the result against a committed snapshot of prod, `supabase/security/prod-schema.snapshot.txt` (generated by `pnpm --filter @setnayan/web schema:snapshot`; the prod half is committed for the same reason the exposure baseline is).
- **Three-way diff, not two.** It replays twice — once with only the migrations prod's ledger claims to have applied, once with everything in the repo — so a migration added by an open PR is not reported as drift, and a pending migration that *fixes* a divergence clears it immediately. Without that, every schema PR would go red and the guard would be deleted inside a month.
- **Ratchet:** `KNOWN_GAPS` + `KNOWN_GAP_CEILING` (now 2). Entries need a real reason, and an entry that stops matching anything **fails the suite**, so the list cannot rot into stale excuses.
- **Anti-vacuity:** floors on both sides (≥300 tables, ≥4000 columns, ≥900 ledger rows) plus named core tables, snapshot header/row-count reconciliation, and canonical-order checks. A truncated or emptied snapshot fails instead of trivially agreeing.

**Why not the existing regex parser.** Diffing `readSchema()` against prod was built first and thrown away: it reported 32 missing columns of which **18 were false positives**, because it unions every migration and never processes `DROP COLUMN` or `RENAME COLUMN`. Replaying real SQL kills that whole class at the root — plus `CREATE UNLOGGED TABLE` (`rate_limit_hits`) and `ALTER TABLE … RENAME TO` (`reel_music_tracks`), both invisible to the regex. Measured: **32 declared-missing collapsed to 7**, with zero allow-list entries spent on parser artifacts.

**`manual_payment_logs` — the real find, on the payments table.** Prod's table was created out of band (its PK `id` is declared by no migration) and the phase-A `CREATE` no-opped against it. The declaration and reality are incompatible three ways — PK `manual_payment_id` vs `id`, `items_ordered` JSONB vs `text[]`, and a `payment_status` CHECK that **forbids `'VERIFIED_AND_ACTIVATED'`, the exact value the live `verify_and_activate_manual_payment()` writes**. A fresh environment built from these migrations would have a *broken* manual-payment activation path; prod works only because the declaration never landed. So the declaration was corrected **down to prod** (`20271011873973`, every statement a guarded no-op on prod) rather than adding seven unused columns.

⚠ **Product gap surfaced, not fixed:** the iteration 0034 **7-day pending-payment expiry does not exist** (pending manual payments never expire) and there is **no admin reconciliation audit trail** (`verified_at` / `verified_by_admin_id` / `rejection_reason`). Both were only ever declared, never built. If wanted, they belong on the real payments spine (`orders` / `payments` / `order_ledger`), not this vestigial Maya-branch table (0 rows, one writer).

**RA 10173 correction:** `lib/erasure/coverage-guardrail.test.ts` and `lib/export-coverage-guardrail.test.ts` classified `manual_payment_logs` as "the audit trail behind a retained payment" whose "staff-authored fields need stripping first" — describing columns that do not exist. There is nothing staff-authored to strip and **no direct subject key** (attribution is only via `event_id`). Both notes restated to match the real seven-column table.

**Six out-of-band columns back-filled** (`users.concierge_banned{,_at,_by,_reason}`, `platform_settings.onboarding_bg_music_r2_keys`, `vendor_services.per_guest_delivery`) with types copied from prod's `pg_catalog` — `ADD COLUMN IF NOT EXISTS` matches on name only, so a wrong type would no-op on prod and diverge on a fresh database, which is the same trap this closes. Side effect worth naming: the exposure baseline had **never seen these seven real prod columns**; refreshing it (+7/−7, no collateral) brings them under the freeze for the first time.

Not back-filled, deliberately: the two prod-only *tables* (`event_service_deliveries`, `pioneer_incentive_logs`). They carry RLS, policies, grants and FKs, and adding them also widens the exposure surface — its own reviewable change, allow-listed with that reason.

Neutralisation: a phantom declared column, an undeclared prod column, and a truncated snapshot were each injected and each turned the suite red naming the object; reverted, green. Typecheck proven non-vacuous by an injected type error. 4212/4212 unit, 396/396 DB.
