## 2026-08-09 · fix(vendor-calendar): a booked date now REOPENS when the booking is released — the auto-block had no inverse

Found while auditing the owner's 2026-08-09 description of vendor scheduling ("schedules for each service · block that date if a customer is locked · allow wait list in case the person who purchased for that date backs out"). RULE 0 paid off: **all four parts already ship** — named calendars per service (`NEXT_PUBLIC_NAMED_CALENDARS_ENABLED`, live-by-default since 2026-06-21), the 6-state day taxonomy incl. `locked`/`whitelist` (`20270403356945`), auto-close at `deposit_paid` (`20270428213000`), and the Booked-Out Waitlist with vendor-picked acceptances 1–3 (`20270320335355` + `20270428213000`). Nothing was rebuilt. **But the last one had a hole exactly where the owner asked about it.**

**THE BUG — the auto-block was permanent.** `event_vendor_autoblock_on_booking` → `vendor_block_booked_date()` writes an org-wide `setnayan_booking` calendar block when a marketplace booking reaches `deposit_paid`. That block is the single thing every couple-facing availability path reads — `getVendorAvailableDays` (marketplace filter), the `vendors_blocked_on_date` RPC (search down-rank), and the shop page's own "is my date free?" check that gates the *Join the waitlist* CTA. **Nothing anywhere deleted one.** `vendor_block_booked_date` had no counterpart; `removeBlock` filters `.in('block_source', ['manual','external_client'])` so it *cannot* delete one; and `calendar/surface.tsx` additionally hides `setnayan_booking` rows from the removable list (`b.source !== 'setnayan_booking'`). All **six** `releaseSchedulePools()` call sites free the POOL reservation and leave the BLOCK standing.

⇒ Couple backs out → the vendor's capacity is free internally and **every other couple is still told that vendor is busy that day, permanently.** The waitlist built for precisely this moment could still be emailed (the vendor's one-click "a slot opened" button works) — but those couples land on a page that still reads *unavailable* and cannot book. 🔑 **Same disease as the phantom column / phantom enum value / phantom RPC argument: nothing throws, nothing logs, CI is green, and the only symptom is an absence** — here, a date that never comes back.

**Severity, honestly: latent, nobody harmed.** Verified against prod 2026-08-09 — 2 vendor shops (both hidden), `waitlist_enabled` FALSE on both, **0** calendar blocks of any source, 1 pool booking, and the one marketplace `event_vendors` row sits at `contracted`, which never reached the auto-block. No couple has hit this yet.

**THE FIX — migration `20271121865976`, built as a trigger, not app code**, so it mirrors the auto-block's un-bypassable shape and the two halves cannot drift (an app-only inverse would miss the admin/dispute/force-majeure paths, which do not route through the six release sites):

- `public.vendor_unblock_booked_date(vendor, date, except_event_vendor_id)` → `boolean` — deletes the org-wide `setnayan_booking` block for that day, but **only** when no OTHER live booking (`deposit_paid`/`delivered`/`complete`) still holds it. Matches on byte-for-byte the same predicate the forward primitive uses to decide "already blocked" (`pool_id IS NULL` · `block_source` · `blocked_at::date`), so the pair can never disagree about which row they mean. Returns TRUE only on a real reopen.
- `event_vendor_reopen_on_release` — AFTER UPDATE OF status **OR** DELETE on `event_vendors`, firing when a row *leaves* the capacity-consuming set. Exception-safe, exactly as the auto-block is: a failed reopen can never roll back the cancel the couple just made.
- ⚠ It deliberately **never touches a vendor's own manual block**, their `locked`/`whitelist` day states, or an external-client block. We may only undo what we wrote.

**Plus the notify** (`notifyWaitlistIfBookingReleased` / `notifyWaitlistForFreedDate`, wired at the genuine BOOKED→white release via `after()`): the couples waiting on that date get the "it opened up" email automatically, the same way removing a manual block already does. 🔑 **Fails toward silence on purpose** — it re-reads the calendar and emails only when the day is *genuinely* open (any covering block of any source, or a failed read, means no email), because a "your date opened up!" mail that lands on a page still reading *unavailable* is worse than no mail at all. That also makes it order-independent, so it cannot race the trigger. Not wired to the two rollback releases (a status flip that never landed released nothing) nor to the hard-delete paths, which refuse downpaid rows and so never closed a date.

**Tests — `tests/db/vendor-date-reopens.db.test.ts`, 12 cases, all driven through real UPDATE/DELETE so the trigger wiring itself is exercised, never by reading the function body.** Covers the back-out, the cascaded delete, `deposit_paid → delivered → complete` NOT being a release, a second live booking on the same day keeping it shut (and reopening when the last one leaves), the vendor's own manual closure surviving, neighbouring dates untouched, a hand-entered vendor being inert, the primitive reporting honestly, block↔unblock round-tripping, and the trigger being **attached**. A `BASELINE` case asserts the auto-block still fires first — without it every other assertion would pass vacuously.

🛑 **THE EXPOSURE FREEZE CAUGHT A REAL WIDENING IN THIS PR.** The first cut granted `EXECUTE` on the new primitive to `authenticated` out of habit — which would have let **any signed-in account reopen any vendor's booked date**. The forward twin `vendor_block_booked_date` is `postgres + service_role` only, and nothing in app code calls either directly (the SECURITY DEFINER trigger runs as owner). Narrowed to match the twin exactly; the freeze then passed with no baseline edit, because a function no unprivileged role can reach never enters the surface. 🔑 **Mirroring a twin means mirroring its GRANTS, not just its shape.**

🧪 **Mutation-tested, three ways, each verified to have APPLIED before trusting the red:** detaching the trigger → 7 fail; neutering the "another live booking" guard → the double-booking case fails alone; widening the DELETE past `block_source` → the manual-closure case fails alone. ⚠ The third sabotage silently did **not** apply on the first attempt — `\n` inside a perl `\Q…\E` is a literal backslash-n, not a newline, so the file was unchanged and the suite's green meant nothing. The applied-check is what caught it. Typecheck clean; migration-timestamp, migrations-dir and server-only-boundary guards green.

SPEC IMPACT: None — this fixes the code to match the behaviour `20270428213000` already described ("the waitlist is a layer ON TOP of the blocked date"). No locked decision moves: the schedulable resource stays the (org, leaf-category) pool, waitlist acceptances stay 1–3, and couples still only ever see "unavailable", never who or why.
