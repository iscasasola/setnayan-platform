## 2026-09-23 · fix(guests): the Wedding March moves in place — no page reload, one write instead of fifty, and it exists on a phone

Owner, arranging his own Principal Sponsors: *"when i move someone, the whole screen refreshes. feels laggy."* · *"when it reloads, it goes back up and does not stay on where we are editing. this is hassle because we need to always scroll back down. we want them to move and pair people easily and fast."* · *"the guest list on mobile mode is different from the desktop mode. seems like the mobile mode was not edited properly."*

**MEASURED IN PRODUCTION, NOT INFERRED.** Vercel runtime logs for his own session, event `044f7e64…`, 2026-09-23:

```
POST …/guests 303 at 05:51:33  →  the page's two GETs land 05:51:36-37
POST …/guests 303 at 05:52:17  →  05:52:19-20
POST …/guests 303 at 05:52:04  →  05:52:04-05
```

Every Move ↑ was a **303**. Move ↑ / ↓ were plain `<form action={serverAction}>`, and every one of those actions — `moveInEntourageOrder`, `setEntourageLineOrder`, `clearEntourageOrder`, `joinEntourageLine`, `swapEntouragePlaces`, `moveEntourageSection`, `resetEntourageSections` — ended in `redirect('…?gview=walk&…')`. A 303 from a form post is the browser throwing the document away and loading it again: that IS "the whole screen refreshes", and a document load starts at the top, which is "it goes back up". Two to four seconds and a lost scroll position, to move one line by one place.

**And the write was fifty round trips.** `entourage-order-actions.ts` rewrites the WHOLE group on every move — deliberately, so there is no "have we normalised yet" state to get wrong — but it did so as one `UPDATE` per person, `await`ed in a `for` loop. His Principal Sponsors are 50 people across 29 lines, so one tap of Move ↑ was 50 sequential trips from a Vercel lambda to Supabase Singapore. The pairing path was worse: `pinOrder` ran the same loop and *then* called `join_entourage_line`. 🔑 **The row count was never the problem — the round trips were.**

**What changed**

- **New migration `entourage_order_in_one_write`** — `public.set_entourage_order(event_id, guest_ids[], orders[])` writes a whole group in ONE statement via `unnest`, and `public.clear_entourage_order(event_id, guest_ids[])` does the same for Reset. Both `SECURITY INVOKER` like `pair_guests` and `join_entourage_line`, both `REVOKE … FROM PUBLIC, anon` then `GRANT … TO authenticated`, both returning a row count so a zero-row UPDATE cannot be reported as a save. **What is written is unchanged** (0..n-1, both halves of a pair sharing a number); only how many times we ask.
- **No action redirects any more.** They return a `MarchResult` (`lib/march-result.ts` — its own module so the client island can name the type without dragging a `'use server'` surface or a `server-only` import along). 🔑 **A returned refusal is still a refusal**: every sentence that used to travel as `?error=<reason>` through a page load is now returned and *printed next to the list it is about*. Nothing got more permissive.
- **`lib/entourage-write.ts`** (new, `server-only`, NOT `'use server'`) holds the shared read/write/pin. They take a Supabase client and a list of lines — arguments no HTTP endpoint should accept — so keeping them out of the action modules keeps the action surface to exactly the moves a couple can make.
- **The island owns its arrows.** `walking-order-lines.tsx` draws Move ↑/↓ itself; a tap reorders on screen immediately and the write goes out behind it, snapping back with the reason if the server refuses. 🪤 **The coupling this removes:** the arrows used to arrive as a `children` ARRAY drawn as `children[i]`, with `i` from the island's OPTIMISTIC order while the array was built in the SERVER's order. They agree until a move is in flight — exactly when somebody is tapping — and in that window every arrow below the moved line was bound to whoever *used* to stand at its position. Join and swap change which lines exist, so those two ask the server and then `router.refresh()`: new data in place, no document load, no scroll jump, no remount.
- **One write in flight, always posting the latest order.** ⚖ The owner's ask is to move people *fast*, i.e. to tap ↑ again before the last tap has landed. One request per tap races: several single-step "move him up" calls, each resolved against its own fresh read, interleave and settle somewhere nobody chose — while the screen goes on showing the order he tapped for. A tap now only updates `desired`, and a drain loop chases it: at most one request out, each posting the WHOLE sequence on screen, so two taps during one write collapse into one write of the final order. `moveInEntourageOrder` is **deleted**, not left uncalled — an uncalled `'use server'` export is still a live HTTP endpoint.
- **`march-button.tsx`** (new) does the same for the section arrows and the two Reset links.
- **The row drop now checks `byId.has(from)`** before splicing. A drop carrying an id this list does not hold made `indexOf` return -1, and `splice(-1, 1)` quietly moves the LAST line instead of the dropped one.
- **The doors row is no longer `hidden lg:block`.** ⚠ That one class hid the Wedding March from every phone: `rosterDoors` is the ONLY producer of `?gview=walk`, and `mobile-guest-carousel.tsx` emits `gview: null` or reads `gview === 'map'` — it never links to the walk view. A phone had no control that could reach the processional; the only way in was to type the URL, which is how the owner got there. 🔑 **The mobile design already existed and was switched off** — `RosterTabs` is a snap carousel measured at 380px with an 8px edge fade, and "Arrange the room" is an icon on mobile because the owner asked for exactly that on 2026-09-20.

**THE BLANK SCREEN IS THE SAME DEFECT, AND IT IS NOT A CRASH.** Caught live in the browser on 2026-09-23 while the owner reproduced it:

- **Nothing throws.** The console holds no error at all — only font-preload warnings. No exception and no 5xx on the route in Vercel's logs across the whole window, and SSR-rendering the panel against his live 29 lines (plus three simulated post-join states) does not throw.
- **`<main>` is simply empty, then it comes back.** At the moment he said "a blank happened", the page held its layout — sidebar, topbar — and no body content. Seconds later the same `<main>` held 215 KB and read "Section order saved."
- **So the blank IS the navigation.** Every move is a form POST → 303 → a fresh full-page render that takes 2-4 seconds (50 sequential UPDATEs, then the whole 81-guest page rebuilt). For those seconds there is nothing to draw. That is the blank, and "it goes back up" is the same event.
- **And sometimes it never returns.** Vercel's edge log for his session, 07:21:11-07:21:13Z: a POST answered `303`, then **four consecutive requests with HTTP status `0`** — no response at all, where every healthy move logs `303` then `200`. That is "stops loading", and a request that never answers produces no runtime error to find, which is why the logs looked clean.

🔑 **One cause, two faces: a blank that heals is a slow re-render; a blank that does not is a request that died.** Both are the navigate-per-move design, and both go when the navigation does — the body is never torn down, and the write is one short statement instead of fifty that can pile up.

**Trade accepted, named.** The arrows no longer work with JavaScript off. Nothing else on this page does either — the pickers, the drag, the grab-and-move and the whole roster above are already client islands — so an arrow that worked alone in a JavaScript-less browser was never a path anybody could complete a processional through.

Tests — new `the-march-moves-without-a-reload.test.ts` (6: no action redirects or imports `next/navigation`; every exported action returns `Promise<MarchResult>`; no `<form>` in the three march components; the refused reason reaches the render with a `role="status"`, not just a live region; the order write is one `rpc('set_entourage_order')` and not a per-row UPDATE; the island draws its own arrows and is never handed them by index). New `the-march-is-reachable-on-a-phone.test.ts` (2: the walk door exists in `rosterDoors` and is still the only one, and the row that carries it is not `hidden`). `wedding-march-names-move.test.ts`'s verdict guard re-pinned to the property rather than the phrasing — the verdict must be ACTED ON between the check and the write, whichever way the reason travels. All guards sabotage-probed in both directions.

**Exposure baseline regenerated, deliberately and with the reason measured.** `exposure-freeze.db.test.ts` caught the two new functions and was right to — it is the guard that exists because Supabase publishes `public` as a REST surface and the anon key is in the page source. Both added lines are `secdef=no exec=authenticated` (SECURITY INVOKER, anon revoked), so the caller's own RLS decides every row. 🔑 **And this is not new reach:** the baseline's own `col public.guests.entourage_order	anon=SIU authenticated=SIU` says `authenticated` could already UPDATE that column straight through PostgREST — which is exactly what the old loop did with the session client. The RPCs are a *narrower* path to the same capability: event-scoped, `deleted_at`-filtered, array-length-checked and row-counted.
