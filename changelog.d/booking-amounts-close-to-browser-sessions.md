## 2026-11-13 · fix(security): a booking's five amounts are closed to browser sessions (#5936 · migration B)

DECISION_LOG 2026-11-09 — event_vendors price split, Supplier Build 5. Second half of PR #7560 (migration A, the definer readers, merged and serving).

- **Migration `20271343340931`** revokes SELECT on `event_vendors.total_cost_php · deposit_paid_php · transport_php · food_allowance_php · pax_surcharge_php` from `anon` and `authenticated`. Because a column REVOKE does not override a table-level grant, each browser role's table-level SELECT becomes a per-column grant of every OTHER column. It checks its own result: the five closed, every other column still open, `service_role` unchanged. RLS is unchanged. INSERT/UPDATE are unchanged on purpose: the session writers still save a typed price, and `lib/booking-cost-write.ts` decides which amounts a caller may write.

- **New guard `lib/security/booking-money-is-not-session-readable.test.ts`.** It fails when a browser-session query names one of the five, or `*`, in a select, a filter, an order or an embed. It proves each client is the service role with the receiver proof that the shop-contact guard already used. That proof now lives in `lib/security/service-role-receiver.ts`; it was moved, not changed. Four reads reach the service role by a route the proof cannot follow. Each is listed per function with the route I checked by hand. A write payload is not counted as a read. I tested the guard by adding `total_cost_php` back to `lib/budget-truth.ts`'s `VENDOR_SELECT`, and it went red.
