## 2026-07-27 · fix(security): close the anonymous read on `platform_settings` — a LIVE disclosure of Setnayan's own TIN, bank details and unreleased roadmap

Policy `platform_settings_read_all` (`20260513230000:41`) was `FOR SELECT TO anon, authenticated USING (true)` — **no condition at all** — and `anon` additionally held table-level `SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER`. RLS filters ROWS and can never hide a COLUMN, so anyone holding the publishable anon key (in the page source by design) could `GET /rest/v1/platform_settings?select=*` and read the whole settings row.

**This one exposed live data.** Unlike the sibling finding on `vendor_profiles` (PR #3821), which was fix-before-first-verification against an effectively empty table, `platform_settings` holds **1 row and it is populated in production**. Verified against prod before writing: `business_tin`, `business_address`, `business_email`, `bdo_account_name`, `bdo_account_number`, `bdo_qr_url`, `gcash_account_name`, `gcash_number`, `gcash_qr_url`, `resend_from_address` and `vendor_validate_email` all hold real values, and `SET LOCAL ROLE anon; SELECT business_tin …` succeeded. Also exposed: the admin search-ranking dial (`firstlook_boost_weight`), `setnayan_pay_fee_pct`, `referral_reward_php`, `radar_min_n_floor`, the ops cron timestamps, and **every `*_enabled` feature flag** — which together disclose the unreleased roadmap. The `bir_payor_*` / `bir_authorized_rep_tin` columns are anon-readable too but currently NULL; they would have become a disclosure of a **named individual's TIN** the moment the owner filled in the BIR block on `/admin/settings`.

**Root cause is the original comment.** `20260513230000:39` reads *"Everyone can read — these are display values (business name, TIN, merchant payment info), not secrets."* A TIN was never a display value, and the table has since grown from 13 columns to 64: the policy stayed `USING (true)` while 50 columns of internal configuration were added underneath it. A `USING (true)` policy on a settings table is an open-ended promise that every future column is public.

**The fix — full revoke, no re-grant.** `anon` needs exactly zero columns. Migration `20271014400000` revokes `ALL` from `PUBLIC` + `anon`, replaces the policy with `platform_settings_read_authenticated` (`TO authenticated`), and strips every write bit (TRUNCATE included — RLS is never consulted for TRUNCATE, so "there are no write policies" was never sufficient) from `authenticated` while keeping its SELECT.

Nothing breaks invisibly: confirmed against prod that **no view** in `public` references the table (so there is no `security_invoker` view whose anon reads would start 42501-ing) and **no RLS policy on any other table** subqueries it. Those were the two traps that forced #3821 to re-grant 21 columns; neither applies here, which is why this migration can take everything back.

**No application code changed, and none needed to.** Every read path was mapped: all 60+ call sites either use `createAdminClient()` (service_role, bypasses grants) or sit behind a `getUser()` hard gate. Every logged-out-reachable surface that needs a value here — brand icons (`lib/brand-settings.ts:65`), loader chrome (`lib/loader-settings.ts:39`), onboarding music, the favicon route, homepage spotlight — already reads via service_role. Zero `'use client'` modules query the table (the one that mentions it does so only in comments; the values are passed as props).

**The payment fields are a deliberate product call, not an oversight.** `bdo_*` / `gcash_*` / `business_name` / `default_vat_rate_pct` exist to be shown to customers under apply-then-pay. They are not hidden from customers — `authenticated` keeps full SELECT and every surface that renders them is already behind a login (`/receipts/[receiptId]/page.tsx:24` redirects a logged-out visitor *before* the read). Publishing payment rails to authenticated buyers is the product; publishing them to anonymous scrapers is not.

**Scope — `authenticated` deliberately keeps SELECT on all 64 columns**, leaving a documented hole (any logged-in user can still read `business_tin`). Not folded in because `fetchPlatformSettings` (`lib/platform-settings.ts:94`) returns a hardcoded FALLBACK on **any** error — a column grant that missed one of its 25 columns would not throw, it would silently blank the BDO/GCash details at checkout and reset the VAT rate to 0. That is a money defect CI cannot see; it needs that helper to fail loudly first, in its own PR.

Migration carries six `DO $$` post-conditions that `RAISE EXCEPTION` (`schema_migrations` can report APPLIED while the DDL never landed): anti-vacuity canaries; **no column** anon-selectable (asserted over every column, so a future column cannot land anon-readable); anon holds zero table privileges; no policy names anon; the full checkout column list still resolves for `authenticated`; and `service_role` untouched.

New db test `apps/web/tests/db/platform-settings-anon-revoke.db.test.ts` — 17 cases under real `SET ROLE`, asserting behaviour not bookkeeping, with four non-vacuity defences (META role check, positive control returning a row, differential control re-running every denial as `service_role`, canary column existence). Covers the PostgREST probe vector (Postgres requires SELECT privilege on any column in `WHERE`/`ORDER BY`).

Verified by mutation: migration removed → **9 fail** (8 denials + the write-revoke); policy narrowed but REVOKEs dropped → migration **refuses to apply**, P1 naming all **64 columns still anon-SELECTable** (proving a policy-only fix is no fix); `authenticated` revoked with the re-grant dropped → refuses to apply, P4 naming the exact checkout columns lost. Exposure baseline regenerated: `tpriv …|anon SIUD` removed, all 64 `col` facts go `anon=SIU` → `anon=-`, facts 6216 → 6215, and **zero added lines grant anon anything**.
