## 2026-09-06 · feat(gifts): promo free windows can now be scoped to an event-date range — Gifts & Deals G5

Owner ask 2026-09-05, verbatim: *"Give for events — 1. pick any of the paid service. (a) For an event for a specific date (b) For a specific event for a specific date/range (c) For any event. 2. Should cover all services like papic, live stream, event hub pro, and other paid services in events."* (b) — one NAMED event — already shipped via `comp_grants.event_id` (PR #5193). This PR is (a) and (c) only; (c) "any event" was already the entire pre-existing `all_couples` behavior and needed no schema change — only (a) is new.

**Shape chosen: two nullable columns on `promo_free_windows`, not a new `audience_type` value.** (c) "any event" must keep working exactly as it does today, unfiltered. (a) "an event dated on/in a range" is the SAME audience (all couples) with an added filter, not a disjoint cohort — a new audience value would force every existing/future `all_couples` window into one bucket or the other. Nullable `event_date_from DATE` / `event_date_to DATE` (migration `20271208727445_promo_free_windows_event_date_range.sql`) let a window optionally carry a date filter: both NULL → any event (unchanged); either/both set → only an event whose `events.event_date` falls within the inclusive bound(s) qualifies. An event with `event_date IS NULL` (not yet locked) never qualifies for a date-filtered window — unknown means excluded, never assumed included. Two CHECKs enforce this stays sane: `event_date_to >= event_date_from` when both are set, and both columns must stay NULL for any non-`all_couples` audience (no "event" concept on a vendor cohort).

**Reader (`lib/promo-free-windows.ts`):** new pure predicate `coupleWindowCoversEvent(window, eventDate)`, mirroring `vendorQualifiedAt`'s shape on the couple side. `isSkuFreeForCouplesNow(serviceCode, eventDate?)` and `promoFreeSkusForCouples(eventDate?)` both gained an optional `eventDate` parameter (still `cache()`d — React's `cache()` keys by argument value, so this dedupes correctly per `eventDate` within one request; the underlying window-list fetch via `getLiveCoupleFreeWindows()` stays single-fetched-per-request regardless).

**Call sites (`lib/entitlements.ts`) — `eventOwnsSku`, `eventSkuActive`, `eventActiveSkus`, the only three consumers in the repo:** each now fetches the event's own `event_date` via a new cached helper `fetchEventDateForPromo`, GUARDED behind `isPromoFreeWindowsEnabled()` first — mirroring the existing `getPromotedVendorTierFor` double-guard idiom — so while the flag is off, zero extra DB queries run and behavior is byte-identical to before this PR. Proven by a new inert-while-dark test in `lib/promo-free-windows.test.ts`.

**Coverage confirmed, mechanism-by-mechanism:**
- `COUPLE_WEBSITE_PRO` ("Event Hub Pro") — gated via `eventOwnsSku`/`eventSkuActive` → **reachable**, date-filterable.
- `LIVE_STUDIO` — gated via `eventSkuActive(admin, eventId, 'LIVE_STUDIO')` directly → **gate is correct, reachable**. BUT the admin creation UI's SKU picker (`fetchV2CustomerCatalog`) excludes `LIVE_STUDIO`/`LIVE_STUDIO_ROAM`/`LIVE_STUDIO_HOSTED_CHANNEL` by name while `NEXT_PUBLIC_LIVE_STUDIO_ROAM_ENABLED` is off — so an admin cannot actually create a window covering it today, independent of and not fixed by this PR.
- `PAPIC_UNLOCK` — `eventHasPapicUnlock` calls `checkOrderActive` DIRECTLY, bypassing `eventOwnsSku`/`eventSkuActive`/`isSkuFreeForCouplesNow` entirely. **Confirmed still true against current `main`: a promo window listing `PAPIC_UNLOCK` would NOT unlock unlimited Papic allowances.** Not fixed here — a separate, larger change to the Papic metered-allowance system (camera day-quotas, guest 150-credit cap) with its own blast radius, explicitly out of scope for this PR.

**Admin surfaces:**
- `free-windows-actions.ts` `createFreeWindow` couple branch: new optional `event_date_from`/`event_date_to` fields (plain `YYYY-MM-DD`, NOT PH-anchored — compared against another date-only column, not a wall-clock instant), validated `to >= from`; new required `reason` field (min 10 chars, matching the vendor branch's existing bar) now logged into the same `admin_audit_log` metadata for the couple path too (it was vendor-only before).
- `free-windows-surface.tsx` (Catalog Studio "Free windows" tab): couple form gained the date-range fields + required Reason; listing shows a date-range chip when set.
- `/admin/gifts`: new **"Couple free windows"** section, styled after the existing "Vendor cohort deals" section, with its OWN `ConsoleTable` (Title / Event dates / Services / Ends / Manage) rather than merging into the vendor-shaped `VendorGiftRow` table — a couple window has no vendor/tier concept, and forcing it into that table's columns would produce blank cells on every row of one kind or the other. New reader `fetchCoupleFreeWindows` in a new sibling file `lib/promo-free-window-admin.ts`, mirroring the existing split where the entitlement-gate reader (`promo-free-windows.ts`, cached, graceful-degrading) is kept separate from the admin-listing reader (`vendor-tier-comps.ts`'s `fetchVendorDealWindows` was the precedent; this is its couple-side sibling — a new file rather than extending `vendor-tier-comps.ts` because that file is explicitly documented as the VENDOR half of `/admin/gifts`).

**Registries:** `pnpm admin:map` / `pnpm admin:jobs` re-run and committed — no new page (route count unchanged, 60 pages/41 redirects), no new job (314 jobs, 207 form-driven, unchanged — only new fields on the existing `createFreeWindow` job), so `MODEL_CHOICE_CAP`, `ADMIN_NAV_DESCRIPTIONS`/`ALIASES`, and the `CONVERTED` list in `admin-console-is-one-table.test.ts` needed no changes — verified by running `rank-choices.test.ts` / `admin-console-is-one-table.test.ts` (32/32 pass), not just assumed.

**Exposure baseline:** widened as expected (`event_date_from`/`event_date_to` columns on `promo_free_windows`, `authenticated=SIU` each, same shape as the sibling `deal_length_days` column from G4) and regenerated via `pnpm --filter @setnayan/web exposure:baseline` in this PR — a column-level REVOKE against the table's existing table-level GRANT is a no-op, so narrowing was not an available fix; accepting matches the precedent already set for every other column on this table.

Tests: `lib/promo-free-windows.test.ts` (+11 cases: `coupleWindowCoversEvent` no-filter/null-date/inclusive-bounds/open-ended/single-date/stray-time-component, plus an inert-while-dark proof for the couple side), new `tests/db/promo-free-windows-event-date-range.db.test.ts` (7 cases: both CHECK constraints, a clean `all_couples`+range insert, a clean unfiltered insert) — one file per migration, matching the convention `promo-free-windows-cohort-deals.db.test.ts` set for G4. `exposure-freeze.db.test.ts` green post-regen.

**Full `test:db` caught a real regression, not a false alarm.** The new `promo_free_windows_event_date_couples_only` CHECK (`audience_type = 'all_couples' OR (both date columns null)`) also matches `%all_couples%` / not `%promoted_vendor_tier%` — the exact filter G4's own `promo-free-windows-cohort-deals.db.test.ts` used to find "the one" audience-vocabulary constraint, so the schema went from 1 to 2 matches and that pre-existing, already-merged test failed (`2 !== 1`) against a perfectly correct migration. Fixed by tightening that test's query to also require the enum-style `= ANY (ARRAY[...])` shape, which uniquely identifies `promo_free_windows_audience_type_check` versus the plain-equality G5 constraint — no hardcoded constraint name needed. 2337/2338 → 2338/2338 on re-run.
