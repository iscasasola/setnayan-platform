## 2026-08-06 · fix(security): close the last five NEEDS_REVIEW anon-RPC findings — four revoked, one was a false flag

The 2026-08-01 anon-RPC sweep left five `NEEDS_REVIEW` lines in `apps/web/tests/db/anon-rpc-surface.baseline.txt` and nobody had closed them. All five were read against the live catalog (`pg_get_functiondef` + `proacl`, project `njrupjnvkjkitfctetvi`) and every caller located by its actual `.rpc(...)` call site — a name grep cannot tell a service-role client from a session one, and that distinction is the whole decision here. Migration `20271116688263`.

**`refresh_vendor_fraud_scores()` — off `anon` AND `authenticated`. The only one that WRITES.** No arguments, no identity check, body is `REFRESH MATERIALIZED VIEW CONCURRENTLY public.vendor_fraud_scores` — real work over the vendor tables — and it swallows every error (the inner handler downgrades to `RAISE WARNING`). So any holder of the publishable key that ships in the public JavaScript bundle could call it in a loop and get a 200 back every time, never learning it was failing. That is a denial-of-service shape rather than a disclosure one, which is exactly why a read-oriented sweep filtered it as low risk. All four callers (`app/admin/fraud/actions.ts` ×2, `lib/fraud-detection-runner.ts` ×2) use the admin client.

**`papic_event_points_remaining(uuid)` — off `anon` AND `authenticated`. The one worth remembering.** Migration `20271028837115` revoked `papic_event_pool_status` on 2026-08-01 — and *this* function is a `SECURITY DEFINER` wrapper whose entire body selects from it. The room was locked and the window left open for five days. Every other member of the Papic pool family (`papic_reserve_event_points`, `papic_seat_dedicated_points`, `papic_event_points_remaining_for_seat`) was already `postgres`+`service_role` only; this was the odd one out, not a deliberate guest surface. **A revoke is not finished until its callers are checked too.**

**`event_host_is_internal(uuid)` and `review_is_booked_through_setnayan(uuid, uuid)` — off `anon` only; `authenticated` deliberately kept.** Both are the id-as-credential shape the baseline header names. But both are read on the *signed-in user's own* client (`lib/entitlements.ts`, `lib/reviews.ts`), and **both wrappers return `false` on any RPC error** — so over-revoking would not throw. It would silently strip a §10a internal host's permanent SKU grant (the exact defect migration `20270806100000` exists to fix) and silently mislabel a review's "Booked through Setnayan" receipt. Every public/guest surface already passes a service-role client, so `anon` loses nothing real. `stamp_review_provenance` is `SECURITY DEFINER` and therefore unaffected; no RLS policy references either function.

**`reveal_vendor_name_on_first_reply()` — a FALSE FLAG. Nothing revoked.** It `RETURNS trigger`, so PostgreSQL refuses a direct call and PostgREST never exposes it; the `anon` EXECUTE bit is inert. The 2026-08-01 note described the *trigger's* logic and attributed it to the *grant*. The tell was available all along: the repo's other derived guard — the exposure-surface collector — excludes `prorettype = 'pg_catalog.trigger'`, which is why this function appears in the anon-RPC baseline and **not** in `supabase/security/exposure-surface.baseline.txt`. Two derived guards disagreed and nobody diffed them. The note is corrected in place rather than the grant being revoked for tidiness.

**Named but NOT fixed here** (carved out the way `papic_grant_camera_points` was carved out of `20271028837115`): `chat_messages_member_insert` lets a couple insert into their own event with a caller-chosen `sender_role`, and **three** AFTER INSERT triggers branch on `NEW.sender_role = 'vendor'` — so a forged "vendor" message unmasks a vendor's real business name before that vendor ever replied. That is a policy + product change on the live messaging path touching three triggers and the service-role bot inserts; it needs its own PR and its own tests.

**Tests, watched fail first.** New `apps/web/tests/db/anon-rpc-2026-08-01-review-closures.db.test.ts` (9 cases, 4 of them red before the migration) asserts the denials *behaviourally* under a real `SET ROLE`, each paired with a `service_role` differential control so a failure is attributable to the grant and not a typo. It also asserts the half a revoke usually gets wrong: `authenticated` **keeps** the two the couple surfaces call, `service_role` keeps all four, and the Papic guest-capture chain still resolves end to end (`papic_event_points_remaining_for_seat` still returns the no-fence sentinel). The four are added to the named-regression list in `anon-rpc-surface.db.test.ts`, so a later `CREATE OR REPLACE` re-applying Supabase's default privileges reddens CI instead of silently reopening them. Full `test:db` suite: 807/807.
