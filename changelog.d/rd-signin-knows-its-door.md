## 2026-09-23 · fix(login): a refused password sign-in says which door the account uses

Owner, 2026-09-23: *"we also need to detect if they are a google account, they just directly sign in via google icon?"* Measured on prod the same day: 3 of 11 real accounts (the owner's own among them) are Google-only — `auth.users.encrypted_password IS NULL` — and typing any password got them *"That email and password do not match."* That sentence was false: the password does not fail to match, it does not exist, and the advice (retry, reset) could never work.

- **New migration `20271242648512_sign_in_door_for_email.sql`** — `public.sign_in_door_for_email(p_email)` returns `has_password` and the account's `providers` (read off `auth.users.raw_app_meta_data->'providers'`, the array GoTrue maintains). `SECURITY DEFINER`, **REVOKED from anon and authenticated, granted to service_role only**. Exposure baseline regenerated.
- **`lib/sign-in-door.ts` (pure)** decides the sentence: a Google-/Apple-only account → *"This account signs in with Google."* + *"Use the Google button above."* (or, on the phone shell where OAuth is hidden, where to find one); an account with a password → the ordinary mismatch; **a lookup that could not run → "we could not check how this account signs in" — never "wrong password"**; an unknown email → the ordinary sentence, so the door never confirms an absence; every other refusal (rate limit, captcha, unconfirmed) passes through untouched.
- **`app/login/actions.ts`** — the lookup (`lib/sign-in-door.server.ts`, admin RPC) runs in the ONE shared helper both doors use (`exchangeCredentials`), **only after `signInWithPassword` refused, and only for the credentials refusal** — the owner's constraint: reveal the provider only after a failed attempt, never on blur/change/submit-before-auth. The route redirect carries `&provider=`; `signInInPlace` carries it in state; the card renders the next step.
- Guards: `lib/sign-in-door.test.ts` EXECUTES the decision (8 cases) and READS the action for the ordering (lookup after the refusal, gated on the credentials regex, exactly one call site, both entry points through the helper, no client importer, the RPC revoked from anon/authenticated). Sabotages watched red: "could not tell" collapsed into "wrong password"; the lookup un-gated. A db test replays the migration and exercises the function on seeded rows.

SPEC IMPACT: `DECISION_LOG.md` — owner ruling 2026-09-23 (provider revealed only after a failed password attempt); to be recorded with the ONE DOOR rows.
