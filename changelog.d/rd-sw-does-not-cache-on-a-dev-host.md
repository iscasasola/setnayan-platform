## 2026-10-09 · fix(sw): the service worker is a pass-through on a development host

`public/sw.js` is registered wherever the app runs, `next dev` included. On a dev server the files behind `/_next/static` are not content-hashed — one URL holds new bytes after every edit — and the worker's stale-while-revalidate answered each such script from its cache FIRST, so the first load after every change ran the PREVIOUS page script against the NEW html and css (the reviewer judged code that had already been replaced). On a development host — `localhost`, `127.0.0.1`, `[::1]`, `*.localhost`, `*.test`, and a private LAN address (`10.*`, `172.16–31.*`, `192.168.*`) — the worker now never reads a cache, never writes one (no install pre-cache, no PRELOAD_ASSETS) and never calls `respondWith`; on activate there it deletes every `setnayan-…` cache an earlier copy made and claims its clients, so an already-installed worker is replaced. A production host behaves exactly as before: `app/sw-is-a-pass-through-on-a-dev-host.test.ts` runs the real worker for each kind of host and compares the production trace (install, activate over old caches, every kind of request twice, both messages) with `sw-production-trace.golden.json`, recorded from the worker as it was before this change. All inside `sw.js` (a static file): no bundle, no first-load cost; the registration script and layout are untouched, and `scripts/stamp-sw.mjs` (which rewrites only the `const VERSION` line) leaves the new code intact. No request, no server action, no migration.
