## 🛑 Two more requirements added 2026-09-03 — owner directive, both land in this PR

**1. Every vendor photo entering this pool carries the Setnayan watermark.** This is not new
scope — it is an **existing owner-locked decision from 2026-05-21**, already in `lib/watermark.ts`'s
own docblock: *"Vendor marketplace photos MUST have watermarks (default-on for IP protection
against scraping)."* The gap is that `watermarkFile` is **client-side Canvas only** — it already
runs in `stylist-library-editor.tsx` (the vendor moodboard-library upload surface). RULE 0 FIRST:
determine whether that surface **is** this session's upload path or a **different, already-working
one** — do not assume; trace it. If this is a genuinely separate path (the "shipped May 2026, never
used" page), wire the existing client-side watermark in the same way, or build the server-side
`sharp`-based equivalent if any part of this upload flow runs server-side without a browser present.

**2. Vendors may not upload photos carrying their own logo, contact information, or a QR code.**
This is the boundary that keeps discovery running through Setnayan rather than around it. There is
**no existing infrastructure for this** — checked and confirmed: `vendor-image-repost-watch.ts`
does cross-vendor theft detection via perceptual hash (a different problem: "is this someone
else's photo," not "what does this photo contain"), and nothing else in the repo inspects image
*content*.

**Owner correction, 2026-09-03: two of the three checks are precise enough to auto-block at
upload — no admin queue, immediate inline rejection, vendor fixes and resubmits.**

- **QR code detection.** Near-deterministic — a QR code is either machine-decodable in the image
  or it is not. Any standard detection library (e.g. a zxing/jsQR-class decoder) works. **Hard
  block on any hit.** There is no legitimate case for a QR code in an inspiration photo.
- **The vendor's OWN contact info.** Not generic "any phone number anywhere" — OCR the image, then
  match the extracted text against *that specific vendor's own profile data*: business name,
  phone, email, website domain, social handle. This is a targeted match against known values, not
  a fuzzy guess, so confidence is high. **Hard block on a match**, with the rejection message
  naming what was found (e.g. "we found your phone number in this photo — please upload a clean
  version") so the vendor can fix it immediately rather than wonder why it bounced.
- **Their own logo.** Confirmed field: `vendor_profiles.logo_url` — the photo they uploaded and
  set as their shop's logo. When it's set, check the upload against **that specific image**, not
  generic third-party logo recognition — an image-similarity / perceptual-hash comparison, the
  same technique `vendor-image-repost-watch.ts` already uses for cross-vendor theft detection,
  just pointed at one vendor's own reference image instead of every other vendor's hashes. When
  `logo_url` is null (no logo on file), there is nothing to check against — skip this check
  rather than guessing at "logo-shaped" content in the abstract.
- **Only the genuinely ambiguous residue** — something logo-shaped that matches none of the
  above — needs a lighter touch than a hard block. If a session builds this and finds the
  false-positive rate on QR/own-contact-info/own-logo checks is NOT actually low in practice,
  say so plainly and fall back to flagging that specific check for review rather than silently
  shipping an automated block that guesses wrong. But do not default the whole feature to a
  review queue when the two front-line checks are precise enough to act alone.
