## 2026-10-20 · perf(rls): policies ask "who is this" once per query, not once per row

Owner: "we want all pages to load at its fastest." Measured on prod (read-only): one guests read cost 21–27 ms with the user's JWT against 1.5 ms as service_role; Supabase's performance advisor reported 275 `auth_rls_initplan` findings.

Migration `20271281556823_rls_checks_once_per_query.sql` (generated by `apps/web/scripts/gen-rls-once-migration.ts` from the replayed schema) rewrites 548 policies on 322 tables with `ALTER POLICY … USING / WITH CHECK` only — no policy dropped, created, renamed, re-roled or moved between permissive and restrictive:

- bare `auth.uid()` / `auth.jwt()` / `auth.role()` / `auth.email()` → `(SELECT auth.uid())` (one InitPlan per statement);
- bare `is_admin()` / `is_console_admin()` → `(SELECT is_admin())` (STABLE, no arguments);
- `moderator_area_level(event_id, '<area>') <P>` → `event_id IN (SELECT l.event_id FROM current_moderator_area_levels('<area>') l WHERE l.level <P>)` — new `public.current_moderator_area_levels(text)` (STABLE SECURITY DEFINER, authenticated only) computes the levels with `moderator_area_level` itself, once per statement. Every call site sits under AND/OR only, where NULL and FALSE cannot differ.

Each ALTER runs only if the policy still reads exactly as generated (md5), otherwise it is skipped with a NOTICE — never a stalled deploy, never an overwritten policy.

Proof: `tests/db/rls-checks-once-per-query.db.test.ts` replays to just before the migration, seeds a world, runs a 14-identity × SELECT/UPDATE/DELETE/INSERT matrix on every touched table plus the hot tables, applies the migration to the same database, and requires every cell to match; it also checks every predicate equals the rewrite as Postgres prints it, and that a broadened policy turns the matrix red. Guard: `tests/db/policies-ask-once-per-query.db.test.ts` keeps every public policy a fixed point of the rewrite.

Not done: merging permissive policies (`multiple_permissive_policies`) — Postgres already ORs permissive policies for a role+command into one qual, so a merge changes no plan, and on guests/orders the overlap is with `FOR ALL` policies a same-command merge cannot remove. `NOT is_limited_helper(event_id)` (restrictive write policies) is left per-row: under a NOT, NULL and FALSE differ.

SPEC IMPACT: None — no access rule changes; policies admit exactly the rows they admitted before.
