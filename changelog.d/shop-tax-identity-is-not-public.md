## 2026-09-10 · fix(security): a shop's tax identity is no longer readable by every signed-in account

`vendor_profiles_public_read` admits roles `{anon, authenticated}` for every VERIFIED shop, and Postgres RLS is ROW-level — it can never hide a COLUMN. Migration `20271014385411` closed this for `anon` (21 of 106 columns) and said so in its own docblock: *"THE HOLE THIS MIGRATION DOES NOT CLOSE: any logged-in user can still read every verified vendor's TIN and registered address."* Measured in production by the catalogue before writing anything: `anon` = 21 columns, `authenticated` = **106 of 106**. So any couple, and any rival supplier, could `GET /rest/v1/vendor_profiles?select=tin_number,registered_address,business_owner_name,registration_number_raw` with the public anon key and a plain signed-in session.

**The blocker the anon pass named is gone, which is why this could ship now.** That migration deferred `authenticated` for one stated reason: `app/api/profile/export/route.ts` read this table with `select('*')` on the SESSION client for the RA 10173 subject-access export, so a column grant would 42501 it. Read on `origin/main`, not assumed — that route now issues the read on the **service-role** client, `.eq('user_id', user.id)`, with the named projection `VENDOR_PROFILE_EXPORT_SELECT`, and its own docblock records that the change was made for exactly this migration. Tests T11/T12 pin both halves.

**Eleven columns move off `authenticated`'s read surface** (migration `20271217955839`) — the identity documents a shop hands the government: `tin_number` · `tin_type` · `registered_business_name` · `registered_address` · `registered_zip` · `bir_service_category` · `registration_number_raw` · `registration_number_normalized` · `registration_number_submitted_at` · `registration_number_needs_review` · `business_owner_name`.

`REVOKE SELECT`, **not** `REVOKE ALL`: `authenticated` legitimately holds INSERT/UPDATE/DELETE here (`vendor_profiles_owner` is `FOR ALL`), and the tighter-looking statement silently breaks every shop editing its own row. The re-grant allowlist is COMPUTED from `information_schema`, never hand-typed — a missed column does not blank a field, it makes PostgREST refuse the WHOLE query.

**Where the shop reads its own: `public.vendor_profiles_self`.** Column privileges are ROLE-level, so the same revoke takes those columns from the shop ITSELF. A definer view (`security_invoker = false`, owner `postgres`) whose WHERE clause is an exact mirror of the two policies that already govern this — `vendor_profiles_owner` (`user_id = auth.uid()`) and `vendor_profiles_member_read` (`current_vendor_ids('viewer')`), both read out of prod with `pg_get_expr`/`pg_get_functiondef`. It widens nothing and narrows nothing; SELECT only, because an auto-updatable definer view is a write door past RLS. No `is_admin()` arm: there is no admin RLS policy on a CLAIMED vendor row, and every admin surface reading these columns already runs on `createAdminClient()`.

🚨 **The break this would otherwise have caused is SILENT, which is why code ships with the migration.** `lib/vendor-profile.ts` retries its FULL projection against a LEGACY one on ANY error and back-fills `business_owner_name: null`. Pointed at the table, a 42501 does not crash the vendor dashboard — it makes the shop's own owner name read as MISSING, and `businessProfileChecklist` then asks the supplier to type in a name we are already holding. Four registration-number probes swallow their errors the same way, and `vendor-dashboard/verify/actions.ts` turns that into a HARD block: the shop is redirected away from submitting verification because it "has no registration number on file", forever.

**Seven read sites repointed** at the view, found by scanning all 401 `.from('vendor_profiles')` call sites rather than by memory: `lib/vendor-profile.ts` (both the FULL and LEGACY projections), `vendor-dashboard/shop/page.tsx`, `vendor-dashboard/verify/actions.ts`, `vendor-dashboard/shop/inline-docs-actions.ts`, `lib/vendor-first-steps.server.ts`, `vendor-dashboard/actions.ts` (the correction snapshot) and `open-shop/page.tsx`. The same scan proves the parts that must NOT change: **zero** `select('*')` on this table anywhere, and of the fifteen writes with a RETURNING projection **none** returns a denied column, so writes are untouched. `/admin/verify` and the RA 10173 export keep reading the table — both on the service-role client.

⚠ **The brief for this work said it was harmless because the columns are all NULL. That is false for one of them.** Measured in prod: `tin_number`, `registered_address` and `registration_number_raw` are NULL on both shops, but **`business_owner_name` IS SET on one**, and that shop is `verified` + publicly visible — so one real person's legal name was readable by every signed-in account today. The tax columns were the future exposure; the owner name was a live one.

**The cost, stated plainly, and guarded.** `authenticated` now has no table-level SELECT here, so a column added by a future migration is born unreadable — the `public.events` trap, which cost that table a month-long outage. The db suite structurally cannot catch it (the replay recomputes the allowlist over the new column in `before()`), so the guard reads migration TEXT: `scripts/lint-vendor-profiles-column-grants.mjs`, modelled on `lint-events-column-grants.mjs`, with no prefix cutoff (prefix order is not apply order). It requires a new column to carry its own `GRANT SELECT (col)` **and** its migration to rebuild the self view. Wired into `ci.yml` with all three edits — step, env binding, and `check` line.

Its `GRANDFATHERED` set is generated, then **cross-checked against production**: the scanner found 106 names, `information_schema` reports 106 for this table, and the two sets are identical in both directions — zero invented, zero missed.

**Measured, not asserted.** 15 new db assertions (`tests/db/a-shop-tax-identity-is-not-public.db.test.ts`), all green, with a META anti-vacuity check that the impersonated session really is `authenticated` and cannot BYPASSRLS, a positive control that a stranger still reads the shop's public columns AND gets a row, and a differential control re-running every denied statement as `service_role`. It also asserts a denied column cannot be smuggled through a `WHERE`, `ORDER BY` or aggregate — `?tin_number=eq.…` is a membership oracle, and a guard that checks only the select list would miss it.

Mutation-tested, occurrence counts printed before → after. Migration: deleting the REVOKE fires POST-CONDITION 1 (naming all 11); with that post-condition ALSO removed the db test still goes red on exactly 2 of 15. Opening the view's fence fires POST-CONDITION 6; a sabotage crafted to satisfy that check still goes red on "a STRANGER reads ZERO rows". Granting UPDATE on the view fires POST-CONDITION 7. `REVOKE ALL` fires POST-CONDITION 4, naming INSERT/UPDATE/DELETE. Lint: a new column with no grant fails on both rules; with a grant but no view rebuild, on one; with both obligations met it passes (it does not cry wolf); the SECOND column of a multi-clause `ALTER TABLE` is seen — the exact blind spot that hid 81 columns from the events guard. Blinding the scanner's regex reports **106 → 15 columns seen, FAIL** instead of a clean pass — a bug found by that mutation, since the anti-vacuity branch had never executed.

Exposure baseline regenerated after merging main, and every changed line counted: 14 removed / 15 added — 11 `col` lines and 1 `tpriv` line losing their `S` (narrowings), the `view` and `facts` header counts, and **one** genuine new line, `view public.vendor_profiles_self … honours_rls=NO select=authenticated`. Facts 6612 → 6613, exactly +1.

**Two existing guards caught this before CI did, and both were right to.** `tests/db/elevated-views-checked.db.test.ts` refuses any new definer view an app principal can read until it is registered with the reason its own predicates are the complete access control — `vendor_profiles_self` is now registered there and pinned behaviourally in that same file, in the `events_host` shape: anon holds no verb and is really refused, `authenticated` holds no write verb, a signed-in stranger sees zero rows, and a NEUTRALISATION test recreates the view without its WHERE inside a rolled-back transaction and proves that same stranger then sees everything — so the zero above is attributable to the filter and not to an empty table. `lib/security/select-column-scan.test.ts` refuses a `.from()` naming a relation no migration declares; its `KNOWN_UNRESOLVED_TABLES` ceiling goes 11 → 12, with the decision stated inline: a PARSER GAP, not a phantom relation (`readSchema()` parses `CREATE TABLE` only, exactly as for `events_host` directly above it), and teaching it about `CREATE VIEW` would still not resolve this one because the projection is computed inside a `DO` block precisely so a column cannot silently drop out of it.

⛔ Deliberately NOT narrowed, named rather than attempted: `contact_phone`, `hq_address` and the fraud/billing columns (`anon` cannot read them either, but a signed-in couple reading a supplier's phone number is arguably the product working — widening the deny-list is a product call, not a security repair). `authenticated` also still holds table-level TRUNCATE on this table, which RLS is never consulted for; not reachable through PostgREST today.

SPEC IMPACT: None — no product behaviour, price, SKU or owner ruling changes. What a person experiences is unchanged in every direction that was supposed to work, and closed in the one that was not.
