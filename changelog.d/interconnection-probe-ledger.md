## 2026-07-31 · feat(observability): interconnection probes — a ledger that says when a surface is hiding rows from someone entitled to them

Owner asked for a way to track whether the app's interconnections actually work, framed as: *"a log that an account did this action destined to arrive to this interconnection, testing if the interconnection did work. if successful, good. if not, then we need to be notified."*

**The reframe that made it buildable.** A pure write-arrival log would not have caught the incident that motivated it. The song desk shipped as 8 PRs, every DB object individually verified, 64 DB tests green — and it was UNREACHABLE in prod the whole time. The three pending song requests *arrived perfectly*; a write-arrival check would have gone green. What failed was the READ: `vendor_profiles.services` speaks TILES (`live_band`), `get_vendor_event_brief().booked_categories` speaks CATEGORIES (`band_dj`), and the surface intersected them raw. So the destination is not a row — **it is a reader seeing the row**, and the probe compares the surface's own reader against what `service_role` can see. Where they disagree, the surface is lying.

**The verdict rule is the load-bearing part** (`lib/interconnect/verdict.ts`, pure, 8 unit tests). An RLS denial and an empty read are the same value — `count: 0`, no error — and `fetchActSongRequests` documents that collapse in its own header ("Returns [] rather than throwing on a denied gate"). A boolean ledger would therefore have recorded the broken desk as healthy. Five states instead: `ok` · `empty` (permitted, and service_role agrees there is nothing) · **`lying`** (permitted, saw nothing, service_role SEES ROWS) · `denied` (the gate refused a reader who should be in) · `error` (the probe itself failed — recorded, never swallowed, because a dead probe reads exactly like a healthy joint). `classifyPopulation` is the stricter sibling for joints asked of a whole population: four vendors reaching their desks and a fifth stranded is `lying`, not `ok` on the strength of the four.

**Two probes, both halves of the same real incident** (`lib/interconnect/probes.ts`):
- `vendor-desk-reach` — the CAUSE. Every booked (vendor, event) pair whose categories map to tiles the vendor does not hold. Those vendors have no day-of desks at all, and the denial renders as an empty page.
- `song-requests-audience` — the SYMPTOM. Pending `event_song_requests` on events where no booked vendor can open a desk. Nobody is ignoring them; nobody can see them.

Both call `tilesForVendorCategories()` — **the shipped bridge, imported, never re-implemented**. A probe that re-derives the surface's logic drifts with it and stays green while the product breaks, which is how a retired SKU sat on a live page for eight days behind a passing guard. `tiles === null` is treated as REACHABLE (the bridge declines to narrow on purpose; reading null as "no tiles" would invert its intent and scream about healthy bookings).

**Runner is cron-free** (`lib/interconnect/run.ts`) — `claimPeriodicJob('interconnection-probes', 6h)` off `after()` on the homepage, same shape as `runDailyEmailJobs`. Best-effort, never throws into a page render. Its honest limitation is stated in the code and printed on the surface: no traffic means no ticks, so **an empty ledger must never be read as green**.

**Migration `20271026875375`** — `interconnection_probe_runs` (RLS at CREATE TABLE time + `REVOKE ALL … FROM PUBLIC, anon, authenticated`; no policies at all, since the only writer and only reader is service_role) plus `interconnect_booked_vocabularies()`, SECURITY DEFINER and revoked off every session role. That function exists because `event_vendors` reaches `vendor_profiles` through EITHER `linked_vendor_profile_id` OR `marketplace_vendor_id` — two real FKs to the same column, both populated in prod — and PostgREST embedding picks one, silently dropping the other half of the bookings. It returns RAW category strings; translating them in SQL would create the second hand-maintained copy this system exists to catch. (⚠ `event_vendors.vendor_id` is that table's own primary key, not a vendor reference.)

**Surface** — a ninth tab on the Insights Studio, `/admin/app-performance?tab=interconnections`. Driven from the PROBE REGISTRY, not from the ledger: a probe that has never run shows "Never run", so adding one and forgetting to deploy it cannot leave the page looking complete. `empty` renders grey rather than green — this database is pre-launch-empty, and a wall of green that means nothing is worse than no page. Staleness is printed at the same weight as the verdict.

Coverage is stated on the page rather than implied: 2 probes against 83 mapped Ugat joints, and the map itself reaches ~a third of the app (`ugat-concept.baseline.txt` still lists 47 `map-backlog` subsystems).

Tests — `lib/interconnect/verdict.test.ts` (8, including the song-desk case and the partial-service case) + `tests/db/interconnection-ledger.db.test.ts` (10, inside the required check): META anti-vacuity (table exists, RLS on, anon really is anon and cannot BYPASSRLS), anon + authenticated denied SELECT/INSERT/UPDATE/DELETE/**TRUNCATE** (a table privilege RLS never mediates), the vocabulary function off every session role, each with a service_role differential control — and every verdict string the TypeScript union can emit inserted for real against the CHECK constraint, because if those two drift the insert throws, the runner logs, and the console shows the last good verdict forever.

Not in this PR, deliberately: arrival probes (write-site declarations of an expected downstream landing) need an expectations table and instrumentation at each write, and land next. A synthetic actor walking real journeys as the test accounts is what makes the ledger meaningful before launch traffic exists.

SPEC IMPACT: None — new observability surface, no product or pricing decision changed.
