## 2026-08-01 · fix(security): revoke the stale `anon` table grants on 11 tables from the 202608xx–202609xx era — biometrics and vendor payment details had RLS as their only layer

Every relation created in `public` inherits Supabase's default privileges, which grant the full `arwdDxtm` set to **both `anon` and `authenticated`** at `CREATE TABLE` time. The anon key ships in the page source by design, so any browser can act as `anon`. A migration that does not explicitly say `REVOKE … FROM anon` leaves the table open at the privilege layer, with RLS as the only thing in the way. And the reflex fix does not work: **`REVOKE ALL … FROM PUBLIC` does not remove a role's own explicit grant** — the role has to be named.

**Eighteen migrations in the 202608xx–202609xx window created tables and not one of them revoked `anon`.** Of the tables they created, eleven hold anon `SELECT/INSERT/UPDATE/DELETE` and have **zero** RLS policies that admit anon — every policy on all eleven is `TO authenticated` — so the grant buys anon nothing and is pure standing risk. Migration `20271029105532` revokes it:

`admin_approval_requests` · `app_telemetry_logs` · `budget_allocation_decisions` · `budget_builds` · `event_editorial` · `event_floor_plan` · `guest_face_enrollments` · `taxonomy_category_requests` · `vendor_payment_methods` · `vendor_service_agents` · `vendor_service_time_slots`

**Two of them are why this is more than hygiene.** `guest_face_enrollments` holds **biometric** data — `face_vector`, `vector_model` and `asset_url` (the full-res selfie on R2) — which is sensitive personal information under RA 10173, on a table whose own header calls `consent_at` "structurally mandatory". `vendor_payment_methods` holds vendors' **payment destinations** — `account_name`, `account_number`, `provider`, the decoded QR destination, the payment link. RLS was the *only* layer between an anonymous PostgREST caller and both. This restores the second layer; defence in depth means the policy set is not allowed to be a single point of failure, and this codebase has already shipped policy logic that read as correct and was not.

**Re-verified against live production before writing** (2026-08-01, SELECT-only) rather than trusted from the migration files — `schema_migrations` has recorded migrations as APPLIED in this repo whose DDL never landed. All eleven confirmed: anon holds SIUD (plus TRUNCATE/REFERENCES/TRIGGER/MAINTAIN), `rowsecurity = true`, policies admitting anon or PUBLIC = **0**. None was dropped from the list.

**Behaviour change: none.** anon has no policy on any of these tables, so every anonymous request against them already failed — it just failed one layer later. This narrows what is *possible*, not what happens. No application code touched: server-side reads go through `createAdminClient()` (service_role, bypasses grants) and every session-client read sits behind an auth gate.

**Scope is deliberately narrow.** `authenticated` is not touched — a narrowing must never break the live caller. Post-condition **P2 is a positive control** asserting `authenticated` kept SELECT/INSERT/UPDATE/DELETE on all eleven, and P3 does the same for `service_role`. The 11 sibling tables from the *same era* that do have anon-reachable policies (`canonical_service_taxonomy`, `service_categories`, `planning_deadlines`, `budget_allocation_config`, `budget_leaf_benchmarks`, `onboarding_refinements`, `onboarding_refinement_options`, `wedding_tradition_items`, `token_burn_bands`, `vendor_event_unlocks`, `vendor_token_purchases`) are untouched — their grant is intentional and load-bearing, the public taxonomy powers `/explore`. No policy, `USING` or `WITH CHECK` edits.

Five `DO $$` post-conditions that `RAISE EXCEPTION` rather than trust the ledger. Every one asserts the **ROLE `anon`**, never the `public` pseudo-role — a `public`-scoped check passes while a role's own explicit grant sits untouched, which is exactly how a sibling change shipped with the lane still open under a green post-condition. P0 anti-vacuity (all eleven tables exist, so P1 cannot pass on nothing); **P1a** `has_table_privilege` over the seven standard privilege types; **P1b** a direct `relacl` scan for *any* entry naming anon, naming no privilege type at all — so a class this file does not enumerate (`MAINTAIN` today; whatever PG adds next) cannot slip through a hardcoded list; **P2/P3** the positive controls; **P4** RLS still enabled and still no policy admitting anon, pinning down the premise the whole migration rests on.

Exposure baseline regenerated in the same commit. **The diff is narrowings only** — 11 `tpriv …|anon SIUD` lines removed and 165 `col` facts moving `anon=SIU` → `anon=-`, with `authenticated=SIU` unchanged on every one of them (the positive control, visible in the diff). Filtering the added lines for anything that is *not* `anon=- authenticated=SIU` leaves exactly two: the `# facts:` and `#   tpriv` header counters. **Zero lines grant anon anything new.** The regeneration also folds in pre-existing drift from two already-merged PRs that never regenerated the file — the `event_floor_areas`/`event_floor_objects` drop and the `sec-close-anon-secdef` RPC revokes — also all narrowings.

**Two findings reported, not fixed here.** (1) `authenticated` also holds `TRUNCATE`/`REFERENCES`/`TRIGGER` on all eleven from the same default ACL; no shipped path uses them and RLS is never consulted for TRUNCATE — trimming it changes what a logged-in caller can do and deserves its own diff. (2) **This era is not special:** a prod sweep found **243 of 379 tables** in `public` where anon holds SELECT and no policy admits anon. Every era shows the same defect. A 243-table revoke is not a reviewable diff, and each batch needs its own reachability check first.
