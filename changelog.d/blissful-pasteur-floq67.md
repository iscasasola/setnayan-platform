## 2026-11-28 · feat(social): Facebook posts itself, in the owner's three slots

Owner, 28 Nov (specs DECISION_LOG "FACEBOOK POSTING IS AUTOMATIC, IN THREE DAILY SLOTS", "WHAT EACH FACEBOOK SLOT CARRIES", "THE FACEBOOK DAILY CAP COUNTS THE PLANNED POSTS TOO"): posting is automatic at 8 AM, 2 PM and 8 PM Manila, with holiday greetings as an extra. Server side only; no page changes.

- **Slots (`lib/social/governor.ts`, rewritten):** the slots are 08:00 morning, 14:00 afternoon and 20:00 evening, plus 12:00 holiday, which opens only for a planned row marked holiday. They replace the 12–1 PM and 7–9 PM windows and the weekend 10 AM window. One post per slot instant is the whole daily cap, and planned posts count toward it. Every site auto-post (new shops, badges, recaps, milestones, teasers, announcements) takes the next free 14:00. A slot stays open for its hour. A missed post is re-slotted (see below). When two rows hold one slot, the planned post keeps it.
- **2 PM live composer (`lib/social/live-update.ts` + `.server.ts`):** from 12:00 until the 2 PM slot closes, if today's 14:00 is still empty, it reads this week's real news and composes one post. On Sunday that is the weekly totals; otherwise new verified suppliers (named only on a paid size, never counted), then events held this week. Counts are round totals from the milestone ladder (10 and up) only. With no real news, the slot stays empty and the server log says so once that day. One live update a day (`source_ref = live:<day>`); a pulled one is never re-drafted.
- **Library import (`apps/web/scripts/social/import-library.ts` + `lib/social/library-import.ts`):** reads the library v2 CSV and writes an idempotent migration. Each row becomes `source_type 'library'` with `source_ref` = a hash of date + slot, the caption as body, the Door as `link_url`, the pinned comment as `first_comment`, and its slot and Manila time stored as UTC. A row already present in any status is skipped. Bad rows stop the run with their line number. The real migration is not generated here; the controller generates it once library v2 merges.
- **First comment (`lib/social/facebook.ts` `commentOnFacebookPost`):** right after a Facebook post goes out, its `first_comment` is posted under it. The Graph API has no call to pin a comment, so `platform_results.facebook.first_comment` records the comment and `pin: "pin by hand"`.
- **Multi-photo posts (controller, 28 Nov; `lib/social/facebook-multi-photo.ts`):** a row with 2 or more photos in `media_urls` becomes ONE Facebook post. Each photo uploads to `/{page}/photos` with `published=false`, in order, then `/{page}/feed` attaches them in that order (`attached_media`). If any upload or the feed post fails, nothing is posted, the error is recorded, and the unpublished uploads are deleted. The single-photo and link paths are unchanged. Instagram and TikTok take the first photo (`media_url`). The importer fills `media_urls` from "Images, in this order". Relative paths resolve under `--images-base` plus the row's Folder; without a base, the run stops.
- **The slots now open on time (controller review, 28 Nov):** a new GitHub Actions schedule, `.github/workflows/social-slots.yml`, calls the new `POST /api/cron/social-flush` at :02 and :12 of 00, 04, 06 and 12 UTC, which is 08:00, 12:00, 14:00 and 20:00 Manila. The route is guarded by `CRON_SECRET` (the same pattern as the other `/api/cron/*` routes) and runs the same flush with a 1-minute throttle, so it no longer waits for page traffic. This is a workflow schedule, not a Vercel cron or pg_cron: `vercel.json` keeps `"crons": []`, which is the repo's cron-free decision as `deploy-prod.yml` words it. It needs the repository secret `CRON_SECRET`; until that is set, the job does nothing and says so.
- **A missed planned post is moved, never lost:** it goes to the next free slot of its own kind (a missed 8 AM moves to the next free 8 AM), is logged, and is recorded in `platform_results.missed_slots`. Only a holiday greeting expires, because it is tied to its date.
- **Review fixes:** at most 10 photos per post (the owner's rule; 11 is refused before anything uploads). A failed delete of an unpublished photo is logged and recorded in `platform_results.facebook.cleanup_failures`. The importer refuses impossible dates such as 2026-02-30, which `Date` used to roll over to 2 March. The Graph token travels in the request body for DELETE too, never in the URL.
- **Flush (`lib/social/flush.ts`):** a slot pass (re-slot, expire, settle clashes), then the 14:00 assignment, then the live composer. Dispatch publishes only a row inside its slot hour. `autopublish_enabled` and the per-platform switches still gate every publish.
- **Admin queue actions (`app/admin/social-queue/actions.ts`):** Post now uses the slot open right now, else the next free 2 PM. Retry hands the post back to the governor. Announcements take the next free 2 PM. No new server action.
- **Migration `20271365405436_social_slots_library_live_update.sql`:** `source_type` gains `library` and `live_update`; new columns `social_posts.slot` (checked against the four slots), `social_posts.first_comment` and `social_posts.media_urls` (ordered `text[]`); new function `social_live_week_facts()` (service_role only), which leaves out test and sample data by the rules of `social_milestone_real_counts()`.
