## 2026-07-27 · fix(privacy): narrow the RA 10173 export's `vendor_profiles` read to an explicit projection — the one `select('*')` that makes column privileges impossible

**PR 1 of 3. It changes no security behaviour on its own.** It exists to unpin 93 columns so PR 2 can revoke the ones nobody legitimately reads.

**The blocker, measured.** A logged-in NON-OWNER can read any verified vendor's `tin_number`, `registration_number_raw` and `is_founder` — demonstrated with a real `SET ROLE authenticated` probe. `vendor_profiles_public_read` admits every verified vendor's whole row and Postgres RLS is ROW-level, never COLUMN-level, so the only fix for part of that set is a **column-level `REVOKE`** on `authenticated`. That is not currently expressible. `apps/web/app/api/profile/export/route.ts` read the table with `.select('*')`; PostgREST expands `*` to every column and Postgres checks SELECT privilege per column, so that single call requires the role to hold SELECT on **all 93**. With the wildcard in place the set of columns that could be revoked without breaking a shipped surface is **exactly empty**.

**Two changes, both load-bearing.**

- **The wildcard is gone**, replaced by a named 93-column projection in the new `apps/web/lib/export-vendor-profile-columns.ts`. The projection was machine-derived from the repo's own migration parser (`lib/security/migration-schema`), then diffed against production `information_schema.columns` — 93 columns on both sides, identical names — and the exact select list was executed against prod (`limit 0`) to prove it does not 42703. The exported payload is unchanged, column for column.
- **The read moved to the service-role client.** Column privileges are ROLE-level, not row-level, so the moment PR 2's revoke lands the vendor cannot read their **own** `tin_number` either, and PostgREST fails the whole statement (42501) rather than omitting one field — the subject's entire `vendor_profile` section would vanish from their own subject-access file. Filtered `.eq('user_id', user.id)` on a server-verified session identity, fixed projection, no joins, read-only: the same four properties that bound the two coordinator reads already on this route.

**The route's own bounded-bypass contract is now MORE true, not less.** Its property 3 has always read *"a fixed column projection. No `select('*')`, no joins"* — and `vendor_profiles` was violating it one screen below, invisibly, because that read was on the session client where the stated rule and the code did not visibly collide. Moving it behind the bypass forced the collision and it was resolved in the rule's favour. There is now **no `select('*')` anywhere on this route**, privileged or not. The docblock records that the property was aspirational until today rather than quietly claiming it always held.

**The new risk is UNDER-EXPORT, and it is what the tests are for.** A wildcard cannot forget a column; a hand-written list can, and the omission is invisible — 200 OK, section looks populated, typecheck silent (a PostgREST select list is a string), and the existing phantom-column scanner only checks the opposite direction. A data subject would simply never receive their registered business address. So:

- **`T12`** (new, `lib/export-coverage-guardrail.test.ts`) asserts the projection is **exactly** the table's migration-derived column set minus an explicit, reasoned `VENDOR_PROFILE_EXPORT_OMITTED` deny-list — equality, not subset, in all three directions (under-export · phantom column · stale withholding decision), plus an anti-vacuity floor so an emptied projection cannot pass by matching an emptied schema.
- **`T13`** (new) pins that the `admin === null` path (no `SUPABASE_SERVICE_ROLE_KEY`) is **disclosed**: `vendor_profile` now passes `adminUnavailable` into `singleOutcome`, and the two media sections that hang off the profile row are named NOT READ with it. Without this a run with no service key would tell a vendor in writing that Setnayan holds no business record for them.
- **`T11`** extended from two tables to three; **`T6`** extended to assert `vendor_profiles` stays filtered on `.eq('user_id', user.id)` — service-role means RLS is no longer a second line of defence, so the uid filter is the only bound on the row set.

**Mutation-tested, five ways** — each produced exactly one named red test: drop `tin_number` from the projection (T12, names the column) · add a phantom column (T12) · revert the read to the session client (T11) · drop `adminUnavailable` (T13) · **add a new `vendor_profiles` column via a scratch migration (T12 fails, naming it)** — which is the claim that matters: a future column addition fails the build instead of silently vanishing from every vendor's legal export.

`VENDOR_PROFILE_EXPORT_OMITTED` ships **empty on purpose** — this PR is payload-identical by design. Two candidates are flagged for the DPO rather than decided in a refactor: `created_by_admin_user_id` and `experience_verified_by` each hold a **Setnayan staff uid**, and the route's own `not_included` copy already argues (for `admin_data_access_log`) that naming the admin who acted is a third-party disclosure pending DPO review.

`singleOutcome` in `lib/export-integrity.ts` now takes `data: unknown` like `listOutcome` already did — supabase-js resolves `.select(someConstant)` to `GenericStringError` against an untyped schema, exactly as it does for an embedded select.

Verified: `tsc --noEmit` clean · `pnpm lint` no new warnings on touched files · `pnpm run test:unit` **4622/4622** · the exact projection executes against prod.

SPEC IMPACT: None yet — no SKU, price, or schema change, and no change to what any role can read. It is the prerequisite for the follow-ups: **PR 2** adds the column-level `REVOKE`/`GRANT` on `public.vendor_profiles` for the zero-reader sensitive set (`tin_number`, `registration_number_raw`, `is_founder` and the rest of the BIR/DTI identity block), and **PR 3** extends `tests/db/vendor-profiles-anon-columns.db.test.ts` to cover `authenticated` alongside `anon` so the closed hole stays closed. The corpus decision row lands with PR 2, when the exposure actually changes.
