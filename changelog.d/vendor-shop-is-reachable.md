## 2026-08-06 · fix(vendor): every shop gets a web address — nothing ever minted `business_slug`, so a Free shop's page could not be reached at all

Owner: "fix vendor." Live production carried **2 vendor rows and BOTH had `business_slug IS NULL`.** `business_slug` is the ONLY key `/v/[slug]` (and the bare root `setnayan.com/{slug}`) resolves a shop by, so **neither shop had a URL of any kind.**

**The defect — a gate on CHOOSING an address silently became a gate on HAVING one.** Verified three ways, not inferred:

- `handle_new_vendor_user()` (20270401574089) does `INSERT INTO public.vendor_profiles (user_id)` — no slug.
- `/open-shop`'s `becomeVendor` inserts the same bare row, then patches `business_name` / owner / phone / email / services / `event_types` — no slug.
- **Live prod `pg_proc`, 2026-08-06:** the only two functions mentioning the column (`resolve_custom_domain`, `public_venue_scene`) merely READ it. **Zero triggers, zero writers.** The one existing auto-mint on this table is `screen_name`, not the slug.

The only writers were `saveVendorProfile` and `updateVendorWebsiteField`, both gated on `tierCaps().customWebsiteName` — **Pro / Enterprise / Custom only.** ⚠ Correcting a prior claim: this is **not** "only the top paid tier". **Solo is a PAID tier (₱999) and also could not set one.** So Free, Verified *and* Solo shops could never hold an address, while `lib/vendor-microsite.ts` promises in its own words that "Free / Verified get the clean auto-composed page" — a page with no address to be reached at. `/v/[slug]/page.tsx` gates on visibility only, never on tier, so the page really is theirs; only the door was missing. `/explore` does **not** filter slugless rows: `vendor-card.tsx` renders such a card with **`href="#"`**, so the first shop the owner approves would list on the marketplace with a card that goes nowhere. My Shop said it out loud: *"No public address yet — a custom address is a Pro feature you set in Website."*

**Fix — `supabase/migrations/20271117527966_…`.** `generate_business_slug_for_vendor()` + an `AFTER INSERT OR UPDATE OF business_name` trigger, modelled on the one auto-mint this table already has (`generate_screen_name_for_vendor`, 20260714000000 + its collision fix 20270820111851): SECURITY DEFINER, a bounded uniqueness-retry loop, and a **persistence rule that NEVER reissues** — a public address is a promise, and moving it 404s every link, QR and share already handed out. Sources in order: slugified business name → name + 4 chars of the row's `public_id` (for 1–2-char names) → `public_id` lowercased. Gating the trigger on `UPDATE OF business_name` (not a bare `UPDATE`) is what makes it non-re-entrant — the generator's own `SET business_slug = …` never names that column. **Existing rows backfilled in the same migration**, oldest first. All four new functions `REVOKE`d from `PUBLIC, anon, authenticated` — verified directly against the replayed schema (`has_function_privilege` = false for all five, not merely inferred from an unchanged baseline).

**What this deliberately does NOT do — `public_visibility` is untouched.** Its `hidden` default and admin-only writes are an **owner ruling, 2026-07-27, verbatim: "no. we only show shops that are ready" / "demote. remove coming soon entirely"** (20271013500000), enforced in the database by `guard_vendor_profiles_entitlement`. **Holding an address is not being listed.** A hidden shop's page still 404s for everyone and `/sitemap-vendors.xml` still requires `public_visibility='verified' AND verification_state='verified'`, so **not one row becomes newly public and no real company's page is published by this PR.** A dedicated test asserts it.

**Second copy, mechanically compared.** Vendors, events and users share ONE top-level namespace, and `app/[slug]/page.tsx` answers `RESERVED_SLUGS.has(slug)` with `notFound()` *before* it looks for a vendor — so a shop minting `explore` would hold an address resolving **nowhere**. The database cannot import `lib/reserved-slugs.ts`, so `public.business_slug_is_reserved()` restates it — and the db test feeds the TypeScript set into the SQL function and **fails naming any word that drifted**. Proven by mutation: deleting `explore` + `features` from the SQL list failed the test with exactly those two words. New `lib/vendor-slug.ts` gives the manual (Pro) path the same refusal — until now `parseSlug` checked shape only, so a Pro vendor could claim `pricing` and get a dead address.

**UI (`vendor-dashboard/shop/`).** The address now shows on **every plan**; the Pro block's row is retitled **"Change your address"** (Pro buys picking a *different* one, not having one). Both surfaces stop linking a not-yet-approved vendor at their own page — that 404s for the owner too, because the visibility check in `/v/[slug]` runs *before* the owner-preview carve-out — and say instead: *"This address is yours for good. Your page opens to couples once Setnayan approves your shop."*

Tests — new `tests/db/vendor-business-slug-mint.db.test.ts` (8 cases, full replayed prod schema, **watched failing 8/8 before the migration**): the real registration shape (bare row → later `UPDATE` of the name) mints a slug · it satisfies the app's own `SLUG_RE` · same-name shops don't collide · a slug is never regenerated across a rename · a shop named `Explore` never takes `explore` · every reserved word is reserved in the DB too · an un-slugifiable name still yields a valid address · **minting publishes nothing (`public_visibility` stays `hidden`)**. New `lib/vendor-slug.test.ts` (5 cases, mutation-checked). `anon-rpc-surface` + `exposure-freeze` + `screen-name-collision` green (25/25); exposure baseline regenerated and **byte-unchanged** (6233 facts). Typecheck clean.

⏭ **Owner decision, NOT changed here:** both live shops sit at `public_visibility='hidden'`, so after this PR they have an address but still show nothing to the public. One of them (`Saysay Live Band & Hosting (FIXTURE)`) is a leftover test fixture in prod carrying `verification_state='verified'` with `public_visibility='hidden'` — a mismatch the real `/admin/verify` approve path cannot produce (it writes both together), i.e. it was inserted directly. **Publishing a real business is the owner's call at `/admin/verify`, never Claude's.**
