That is notified so the client can see."* Approved prototype frames G (share picker) and H (card in the client's chat), `prototypes/service_card_row_2026-11-11/index.html`. Follows #7464, which drew Share waiting.

- **Share opens "Share to a client event"** (`services/_components/service-card-share-sheet.tsx`, the house `Sheet`): the line *Posts “<card>” into their chat. They get a notice.*, then this shop's client events — initials · event name · date. A client event is a conversation this shop can write in: **accepted** and **not removed by the couple** (`isShareableThread`, `lib/service-share-targets.ts`; read once per page by `readShareTargets`). An unread list says so; an empty one says how an event comes to be there.
- **A pick is the shipped offer from another door** (Rule 0): the existing `offerServiceInterest` action with `via=share` → `offerServiceCore` — same ownership gate, same "online cards only" gate, same `chat_messages.offered_service_id` card the stream already draws. An Offline card says so in the sheet before any pick. Then the sheet closes and the toast says **"<Client> notified"** — or "Posted in <Client>'s chat" when nobody could be told (`offerServiceCore` now returns how many were).
- **In the app only.** New notification kind `service_card_shared` (its own enum migration), sent by `offerServiceCore` for `notice: 'shared'`; the in-chat ＋ offer keeps `chat_message`. It is NOT on the email allowlist and the couple ↔ supplier register declares it app-only. Push level `normal`, like the other couple ↔ supplier notices.

A card with an open booking is named with each booking on its own line; an unread read refuses.
