## The build — four parts, in this order

### Part 1 · Attire recolours (the fix is a SELECT)

- In `page.tsx`, the attire query must select the same nested
  `moodboard_asset_color_ranges ( slot_id, sampled_hex, tolerance_de, region_label )` the
  venue/florals query already selects, and `figureBySubtype` must carry them.
- `attireCards` passes `regions: toRegions(...)` exactly as `churchRow`/`bouquetRow` do.
- **Delete the two false "no-CORS host" comments** (the `moodboard-board.tsx` header and the
  `page.tsx` attire query). Replace with the measured fact and the curl that re-measures it.
  A false comment is how this stayed broken; do not leave a softened version of it.
- `BoardCardView` draws recolourable sources through the canvas path. Confirm the `<img>` it
  loads for canvas carries `crossOrigin="anonymous"` — a CORS-clean host is useless if the tag
  never asks.
- 🔑 **THE RISK IS THE WHITE.** The seeded range is `#FAFAFA ± 15 ΔE` on white attire. If a
  figure SVG has a white/near-white background, the bride's gown AND the page behind her both
  turn burgundy. You must look. Verification is a **pixel assertion per region against a real
  render**, not "the bytes changed" — see [[presence-of-ink-is-not-fit-of-ink]] and
  [[a-flag-in-an-object-is-not-ink-in-the-pixels]]: measure deviation in the attire region vs
  a background sample. If backgrounds bleed, the honest answer is a tighter tolerance or a
  region mask on those rows — via a migration on `moodboard_asset_color_ranges`, never a
  hard-coded override in the component.

### Part 2 · No palette → no colour (the owner's report)

- When `paletteColors.length === 0`, `BoardCardView` today falls through to
  `<img src={card.imageUrl}>` at stock colours while `PaletteStrip` says *"Set this palette
  above to see it here."* The picture contradicts the caption.
- Required: with no palette, the card renders an **honest empty** — a neutral (greyscale or
  outlined) treatment of the drawing, or no drawing, with the caption. Never the stock-coloured
  figure. Pick the neutral treatment that the recolour engine can produce from the same source
  (desaturate through the same canvas path is the natural shape); do not ship a second asset set.
- **Guard:** a unit test that mounts `BoardCardView` with `paletteColors: []` and a recolourable
  card and asserts the stock image is NOT what renders. Sabotage it by restoring the fallthrough;
  it must go red. Anchor on the component, not a substring of a file — see
  [[a-source-guards-window-must-end-at-the-brace]].

### Part 3 · The placeholder photographs come down (migration + guard)

- Migration (allocate with `pnpm migration:new`; must sit ABOVE `20271205612762` and above
  whatever MB21's PR #5184 allocated — check the PR, `pnpm migration:new` cannot see another
  worktree's untracked file): set `retired_at = now()` on every `moodboard_library_assets` row
  with `source = 'internet_placeholder'` **or** `storage_path` on `picsum.photos`. Do not delete
  rows (the gallery rule: never delete seeded photos — [[inspiration-gallery-owner-decisions-2026-09-04]]).
- With no live `venue_scene`, `churchRow` is undefined and the Ceremony card simply does not
  build. That is correct and honest. **Do not substitute a photograph.** The Ceremony drawing
  is an owner-supplied asset (see "Owner owes" below); until it exists the card is absent.
- **Guard (db test):** no row that is `approved_at IS NOT NULL AND retired_at IS NULL` may have
  `source = 'internet_placeholder'` or a `picsum.photos` host. Sabotage by un-retiring one row in
  the test's own transaction; red.
- **Guard (action):** the admin approve path in `app/admin/moodboard-library/actions.ts` refuses
  to approve a placeholder host/source. ⚠ **MB21 (#5184) is in that file.** Put the refusal in a
  small `lib/moodboard-library-placeholder.ts` predicate and import it — one added line in
  `actions.ts`, so the merge with MB21 is trivial. Rebase onto MB21 once it merges if it lands
  first.

### Part 4 · Report, do not fix

Write these into your PR body and your report to oversight; do not build them:

1. The 10 pilot `venue_scene` rows (`20271194970382`) point at `media.setnayan.com`, which does
   not resolve, and the objects 404 on the working `r2.dev` host too. Unapproved, so invisible
   today — but the guard in Part 3 should ALSO refuse approval of a URL whose host does not
   resolve? **No** — a DNS check in an approve action is a flake generator. Report it; the
   session that owns the pilot decides.
2. `R2_PUBLIC_URL`'s production value is **unmeasured** (sessions cannot read Vercel env values;
   the live HTML emitted neither host on first paint). Vendor logos are stored as `r2://`
   references resolved through it at read time. If it is `media.setnayan.com`, every vendor
   photo is broken; no evidence either way. Say exactly that.
