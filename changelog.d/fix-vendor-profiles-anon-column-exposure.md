## 2026-07-27 · fix(security): close the anon column exposure on `public.vendor_profiles` — 93 anon-readable columns down to 21

**The hole.** `vendor_profiles_public_read` is `roles={anon,authenticated}` with `USING (public_visibility='verified' AND verification_state='verified')`, and the `anon` role held **table-level** `SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER` on all 93 columns. RLS is ROW-level and can never hide a COLUMN — so anyone holding the publishable anon key could `GET /rest/v1/vendor_profiles?select=*` and receive, for every verified vendor:

- a complete **BIR Form-2307 tax identity** — `tin_number`, `tin_type`, `registered_business_name`, `registered_address`, `registered_zip`, `bir_service_category`
- **DTI/SEC registration numbers** — `registration_number_raw`, `registration_number_normalized` (the latter carries a UNIQUE index, so an anon read is a confirmation oracle for a guessed registration number)
- **personal PII** — `business_owner_name`, `contact_phone`, `hq_address`
- **fraud-enforcement state** (`fraud_suspended_at/banned_at/tombstoned`), demo markers (`is_demo`, `demo_batch_id`), privilege bypass (`is_founder`), and every competitor's billing/entitlement windows.

**Current blast radius is ZERO** — 1 vendor row, 0 matching the public-read predicate, 0 TINs stored. This is fix-before-first-verification, not an incident.

**The fix.** `REVOKE ALL ON public.vendor_profiles FROM PUBLIC, anon` (roles named explicitly, per `supabase/security/README.md:126-133` — a bare `FROM PUBLIC` leaves Supabase's role-specific grants in place), then a column-level `GRANT SELECT (…21 columns…) TO anon`. anon keeps SELECT on 21 of 93 columns and **no write privilege of any kind**, TRUNCATE included (RLS is never consulted for TRUNCATE, so "there are no anon write policies" was never sufficient reasoning).

**No application code changed, and none needed to.** Every logged-out-reachable surface (`/explore`, `/v/[slug]`, `sitemap-vendors.xml`, `/api/v1/vendors`, `/vendor/fit/[ref]`, homepage spotlight) uses `createAdminClient()` (service_role), which bypasses grants; zero `'use client'` modules query this table.

**Why 21 and not 0 — the part a bare revoke gets wrong, invisibly to CI.** The re-grant exists for two *non-application* consumers:

- `public.vendor_market_stats` is `WITH (security_invoker = true)`, so an anon read of the VIEW is checked against anon's own column privileges on the BASE table. It projects **19** `vendor_profiles` columns (confirmed from the live view body via `pg_get_viewdef`, not from the migration that created it). Without them, every logged-out hit 42501s — while the exposure baseline still cheerfully records the view as anon-granted.
- **Seven** other tables carry a PERMISSIVE anon/PUBLIC SELECT policy whose `USING` clause subqueries `vendor_profiles` (`vendor_ig_media`, `vendor_service_attributes`, `event_vendor_booth_posters`, `registered_crew_devices`, `vendor_calendar_blocks`, `vendor_subscriptions`, `vendor_token_purchases`). A policy runs as the querying role, so those anon reads flip from `returns []` to `42501`. They need `is_published` + `user_id`.

This was verified empirically, not assumed: a bare-revoke variant of the migration passes **every** deny assertion in the new test file while failing the five availability ones.

**Five post-condition `DO $$` blocks that RAISE EXCEPTION**, so the migration cannot silently no-op (the documented `schema_migrations`-lies failure mode). They assert: (1) none of 43 sensitive/internal columns is anon-selectable — via `has_column_privilege`, which folds in table-level grants and so catches a leftover one; (2) all 21 intended-public ones are, **plus a drift guard that recomputes the requirement from the LIVE `vendor_market_stats` body** — so a future engineer who adds a column to that view without extending the grant gets a failing migration instead of a production 500; (3) anon/PUBLIC hold zero table-level privileges; (4) anti-vacuity — the 4 canary columns must exist, or (1) passes trivially against a drifted schema; (5) `service_role` kept SELECT and `authenticated` kept `tin_number`, which is the tripwire against someone "improving" this migration by adding `authenticated` to the REVOKE.

**New db test** `apps/web/tests/db/vendor-profiles-anon-columns.db.test.ts` (14 cases) asserts **behaviour under `SET ROLE anon`**, never that the migration is in the ledger: `tin_number` is refused, `SELECT *` is refused, WHERE/ORDER-BY on a denied column is refused (the PostgREST oracle vector), `business_name` succeeds **and returns the seeded verified row**, and `vendor_market_stats` + all seven policy tables still read cleanly. Non-vacuity is enforced four ways — a META check that `current_user` really is `anon` with no BYPASSRLS and no table ownership, a positive control, a differential control re-running every denial as `service_role`, and an anti-vacuity column-existence check. Verified by mutation: with the migration removed 6 tests fail; with a bare-revoke variant a *different* 5 fail.

**Baseline regenerated** — a pure narrowing (the freeze guard passes silently either way; regenerated so the diff is the proof). 96 lines removed / 95 added: the `tpriv public.vendor_profiles|anon SIUD` fact is **gone**, and all 93 `col` facts move from `anon=SIU` to `anon=S` (21) or `anon=-` (72). Zero added lines grant anon any privilege it lacked. Facts 6198 → 6197.

**⚠ THE REMAINING HOLE — deliberately scoped out, not fixed.** `authenticated` still holds table-level SELECT and `vendor_profiles_public_read` includes it, so **any logged-in user — any couple, any rival vendor — can still read every verified vendor's TIN and registered address** with nothing but the publishable key and their own login. It is not closed here because `apps/web/app/api/profile/export/route.ts:229` does `.select('*')` on the session client for the RA 10173 data-subject export, and Postgres `SELECT *` requires SELECT on every column — any column-level grant to `authenticated` 42501s a compliance obligation. Three more session-client readers break the same way, and `apps/web/lib/vendor-profile.ts:141` retries on ANY error, so a permission denial there degrades silently into a legacy-shaped row rather than surfacing. Follow-up must enumerate that export first. **Deadline: before any vendor populates `tin_number` or `registration_number_raw`** — until then it is latent; after that it is an actual disclosure.

**Named follow-ups (NOT folded in — this migration's virtue is a provably-zero blast radius):** `platform_settings` (🔴 same defect with **live** data — Setnayan's own `business_tin`, `bdo_account_number`, `gcash_number` are populated in prod and anon-readable today; outranks this PR), the `authenticated` half of `vendor_profiles`, `vendor_reviews` + `feature_reviews` (0 rows today, so free to fix now), the seven inline-subquery policies (would let `user_id` come back out of the grant), `setnayan_pay_methods`, and the `view`-row shape in the exposure generator.

**NOT APPLIED TO PROD.** Must be dispatched, then the grants **verified as objects** — `schema_migrations` can report APPLIED while the DDL never landed.

SPEC IMPACT: None — grant narrowing, no product-surface change. (One latent product question surfaced for the owner, changing nothing here: `contact_email` / `contact_phone` / `hq_address` are rendered publicly on `/v/[slug]` today and `contact_email` is column 11 of `vendor_market_stats`, so it stays in the grant. It doubles as the account-linking key — `lib/vendor-invites.ts:267,:441` do `.ilike('contact_email', email)` — so publishing it lets a stranger enumerate which addresses have a vendor profile, which sits awkwardly beside the deliberate off-platform-contact block in chat (PR #3606).)
