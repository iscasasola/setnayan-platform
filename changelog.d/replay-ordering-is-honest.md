## 2026-08-31 · fix(tests/db): the replay stops letting an OLD migration overwrite a NEWER one — the oldest file was winning

**`apps/web/tests/db/replay-migrations.ts` reordered the corpus, and the reorder reached money.** `createReplayedDb()` applied migrations in filename order, caught every file that threw, rolled it back into a `deferred` map — and then retried that map to a fixpoint **after every later-numbered migration had already run**. Seven files took that path on a normal run. **THE OLDEST FILE WON.**

**All seven cascaded from ONE.** `20260530010000_iteration_0006_v2_1_amendment_2.sql` (index 116) fails at its own position with `relation "public.vendor_billing_catalog" does not exist` — that table is created by `20260631000000_v2_pricing_table_alignment.sql` (index 187). It was therefore replayed after index 1269, and it carries:

```sql
UPDATE public.vendor_billing_catalog SET price_php = 2499.00  WHERE sku_code = 'pro_vendor_monthly';
UPDATE public.vendor_billing_catalog SET price_php = 24999.00 WHERE sku_code = 'pro_vendor_annual';
```

...which overwrote the 2026-08-27 owner price sheet (`20271171000513`, index 1212). That file also **creates** `vendor_branches`, `vendor_token_boosters` and `vendor_profiles.name_revealed_at`, so the other six deferrals (`20260530030000`, `20260825000000`, `20270430989880`, `20271014385411`, `20271145190664`, `20271179754895`) were all downstream of this one file being held to the end.

**Measured, three ways, before anything changed.** (1) The replay returns `pro_vendor_monthly = 2499` / `pro_vendor_annual = 26000 → 24999`. (2) Diffing the finished replay against the price sheet's **own** eight-rung postcondition: six rungs match, and the only two that differ are **exactly the two rows `20260530010000` writes** — `pro_vendor_monthly ₱2,499 vs ₱2,500` and `pro_vendor_annual ₱24,999 vs ₱26,000`. (3) Re-running `20271171000513` against the finished replay raises its own guard, `a rung the owner left alone has moved`. (The retry loop was instrumented to print the seven files; the patch anchor `deferred.delete(f);` has **2** occurrences and the log was verified to land on the first — a patch that silently misses its anchor prints nothing, which reads exactly like "no retries occur".)

**🔑 NOTHING IN `supabase/migrations/` WAS WRONG.** Production applied each file once, when it was authored, and never re-ran a 2026-05-30 seed after a 2026-08-27 reprice. The defect was entirely in the harness — which is why no test that READ a price could have found it: every such test read the number the harness itself produced.

**The fix — drain a deferred file EAGERLY, at the earliest index that works.** Ordering now lives in an exported `replayInFilenameOrder(files, port)`: after every *successful* apply, the deferred set is retried to a local fixpoint **before advancing**. `20260530010000` now lands immediately after `20260631000000` (index 187, not 1269), so every higher-numbered migration still runs after it and the last writer to a row is the highest-numbered one — the same last-writer-wins production has. A failed apply rolls back and changes nothing, so the drain only runs after a success and no final fixpoint pass is needed.

**The two designs that were rejected, and why.** *Re-apply the later files a deferred file could have clobbered* — migrations are not idempotent (re-running `20271171000513` does not repair the state, it RAISES), and "could have clobbered" is not knowable without executing the file. *Fail loudly instead of reordering at all* — that reds 1,924 db tests on arrival for a corpus that genuinely is back-numbered, and a guard red on arrival gets deleted. Loudness was kept where it is affordable instead: every out-of-order landing is now REPORTED in `ReplayResult.outOfOrder` (file · index · where it landed · why) and pinned by a test.

**Result: out-of-order files 7 → 2**, both now landing at index 187 instead of after the corpus. Re-measured on the rebased base (corpus of 1271 after #5030): main's harness still retries the same 7 last; this one lands 2 out of order. `applied`/`total`/`skipped` unchanged at 1271/1271/2 both ways.

**The two Pro Vendor rows reconciled with NO new migration**, and both were therefore DELETED from `MIGRATIONS_DISAGREE_WITH_PRODUCTION` in `llms-fixture-matches-the-catalog.db.test.ts` — that list's own staleness guard requires removing an entry that stops diverging. **The list is now EMPTY and all 41 rows are compared**: #5030 closed `CUSTOM_QR_GUEST` and `SEATING_3D` by forward-dated migration `20271184674948` while this branch was open, and its docblock said of the remaining two — correctly — *"THE REMAINING TWO CANNOT BE FIXED BY ANY MIGRATION … the fix belongs in the replay's retry ordering."* That is this change. Both of #5030's rows were **re-measured on the rebased head**, not inherited: `CUSTOM_QR_GUEST` = ₱0 active and `SEATING_3D` = ₱1,500 active still hold under the new ordering.

The removed entries were not wrong when written; every figure in them was measured. What was wrong was the inference *"the replay says ₱24,999, therefore the migrations say ₱24,999"* when the replay was the thing at fault. **An exemption list records a measurement, never a diagnosis.**

**New guard — `apps/web/tests/db/replay-order-is-honest.db.test.ts` (7 tests).** Three drive the ordering engine over a four-file fake corpus where an old file writes a price and a new one reprices it (the real corpus takes ~8 s and cannot be made to say "an old file overwrote a new one" on demand). Four run the real corpus: the out-of-order set is pinned; the write-target reader is proved non-empty before it is trusted; **the invariant itself** — no deferred file may land after the last migration that writes a table it also writes (the general statement of the bug, not `assert pro_vendor_annual === 26000`, which would pass again the moment a different old file clobbers a different new one); and the eight rungs are checked against the price sheet's own postcondition.

🪤 **The repo's own guard caught a silent hole in the new test, and it was a real one.** The write-target reader first used the two-replace idiom `.replace(/\/\*[\s\S]*?\*\//g,' ').replace(/--[^\n]*/g,' ')`, and `scripts/lint-one-comment-stripper.mjs` failed the build for it — correctly: a stray `/*` in prose opens a comment that closes at the next real `*/` and blanks every line between, so the reader would have seen FEWER write targets and the invariant would have passed against a blank. It is now one pass **line by line**, truncating each line at its first `--`, so the failure cannot cross a line boundary by construction. Block comments are deliberately left in — prose that says `UPDATE public.x` only ever ADDS a target, which makes the invariant stricter, and stricter is the loud direction. Cross-checked against the strictest possible reader (no comment handling at all, which cannot miss anything): both read the same 3 (file · table) pairs with a later writer and both find 0 violations.

**Mutation-tested, 3 mutants, all killed** — anchor occurrence counts printed before → after each time. (1) Restore fixpoint-at-end (`if (!ok || deferred.size === 0) continue;` 1 → 0, mutant 1): **5 of 7 fail**. (2) Weaken the drain to every 100th index: **3 of 7 fail** — caught by the pinned-landing test, which the price assertion alone does NOT catch. (3) Blind the reporting (`outOfOrder: []`): **3 of 7 fail**, including the anti-vacuity assertion firing with *"the invariant below is vacuous"*.

**Blast radius, measured both ways on the full suite, re-run on the rebased base** — before (`origin/main` e2ca0c0c7): 1924 tests, 1924 pass, 0 fail, exit 0. After (ec89a9949): 1931 tests, 1931 pass, 0 fail, exit 0. Test NAMES were diffed, not counted: 7 present after and not before — exactly the new file — 0 present before and not after, 0 status flips. **Nothing else moved.**

**Cost, reported rather than absorbed.** Replay time rises ~6.0 s → ~7.8 s (+1.8 s, median of 3 each): the eager drain re-attempts the two `ALLOWED_SKIP` files that can never apply after every subsequent success (865 and 679 attempts; 2,951 apply calls for 1,270 files). Whole-suite wall clock is too noisy on this machine to pin — two before/after pairs gave +29 s (+5.8%) and +189 s (+40%), and two AFTER runs of near-identical code differed by 131 s — so the per-replay figure is the reliable one. Capping the retries would cut it, but a cap can silently delay a landing past a later writer, which is the same defect class, so it was not taken.

SPEC IMPACT: None — no product behaviour, schema, or price changes. `supabase/migrations/` is untouched; no migration was added or edited. This corrects what a database built FROM those migrations comes up with, which now matches production for the two Pro Vendor rungs.
