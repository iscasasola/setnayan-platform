## 2026-07-26 · feat(ci): THE FREEZE — commit the anon/authenticated exposure surface and fail CI when it widens

Seven production vulnerabilities were found on 2026-07-26 and every one was the same mistake: the UI treated as the security boundary while the database sits on the internet behind a published anon key. R2 presign signing any key; a guest reading the couple's whole `events` row (QR master token + Google OAuth token); birth dates and budget still readable because RLS is ROW-level and cannot hide a column; `estimated_pax` from the submitted form turning ₱2,800 into ₱0; `requested_total_php` from the client; `event_type` host-writable while Setnayan AI priced off it live; a PATCH-able NSFW verdict.

None were caught, and the reason was not carelessness — **nobody knew what the reachable surface was.** A new table ships with Supabase's stock `GRANT ALL ... TO anon, authenticated`; a policy gets relaxed to `USING (true)` to unblock a demo; a sensitive column lands on a table strangers already read. Nothing was watching any of it. Measured starting position: 368 tables, RLS on all 368 (good), but 361 granting SELECT+INSERT to **anon**, 360 granting INSERT/UPDATE/DELETE to **authenticated**, and `relforcerowsecurity` on **zero** — so RLS policies are the only gate, with no defence in depth.

**What landed — the surface is now a committed file, and a test diffs it every PR.**

- `supabase/security/exposure-surface.baseline.txt` — 6,150 sorted, deterministic facts (575 KB). One line per capability: `schema` USAGE · `rls` (tables with RLS OFF) · `rlsforce` (the protection, when present) · `tpriv` table×role×privilege · **`col` per-column S/I/U for both roles** · `policy` with its **full `USING`/`WITH CHECK` text verbatim** · `view` incl. `security_invoker` state · `func` incl. `secdef` + `search_path` pinning. Policies cover `public` AND `storage` — our own migrations write RLS on `storage.objects`, and a bucket policy relaxed to `true` is the same bug as a table policy relaxed to `true`; storage's platform-managed table/column grants are excluded because the replay stubs that table and would report fiction. `col` exists because RLS cannot hide a column (the SEC-2b shape); the predicate is stored verbatim, not hashed, because relaxing `event_id IN current_event_ids()` to `true` changes no grant, no command and no role — the text is the only place it shows.
- `apps/web/tests/db/exposure-surface.ts` — collector, canonical renderer/parser, and an **asymmetric differ**. Widening fails; narrowing passes and prints a note. The asymmetry is the load-bearing design decision: a guard that makes tightening red gets deleted within a month, and then protects nothing. One honest exception — a predicate changing from one non-trivial expression to another cannot be mechanically proven tighter, so it is reported for review; the two decidable cases (becoming `true`, ceasing to be `true`) are decided.
- `apps/web/tests/db/exposure-freeze.db.test.ts` — rides the existing `tests/db/*.db.test.ts` glob, so it gates PRs through `test:db:ci` with no new infrastructure.
- `scripts/lint-exposure-baseline.mjs` + new `lint exposure baseline` CI job — pure node, no DB. Closes the two ways a file-based guard dies quietly: the baseline gets **gutted** (header fact-count vs body, per-kind floors, canonical order, unique keys), or the guard gets **unwired** (asserts the test file exists, still matches the glob, and that `package.json` + `ci.yml` still invoke it).
- `pnpm --filter @setnayan/web exposure:baseline` regenerates from the migration replay. No Docker, no network, no credentials, never touches prod.

**Two real defects found while building it, both fixed in the replay harness (`apps/web/tests/db/replay-migrations.ts`).**

1. **The harness ended with `GRANT ALL ON ALL TABLES IN SCHEMA public TO anon, authenticated`, applied AFTER the migrations — silently undoing every `REVOKE` a migration performed.** The `20271005100000`/`20271007100000` events column lockdown (SEC-2b, `master_qr_token` + the OAuth token revoked) was live in prod and *invisible in replay*. Every DB test in this repo has therefore been running against a schema more permissive than production. Replaced with `ALTER DEFAULT PRIVILEGES` in bootstrap, which is what Supabase actually does — stock-granted at CREATE time, minus whatever migrations take back.
2. **🔴 `REVOKE ALL ON FUNCTION f(...) FROM PUBLIC` does not lock anon out on Supabase.** Supabase's default privileges give `anon` and `authenticated` their **own explicit** `EXECUTE` ACL entries at CREATE time, and those are not part of `PUBLIC`. Verified against prod 2026-07-26: `purge_expired_chat`, `claim_unlock_vendor_event`, `redeem_vendor_token_voucher`, `admin_override_publish_review` and `vendor_set_booth_studio_content` all use that idiom and are **all still anon-`EXECUTE` in prod** (`proacl {postgres=X,anon=X,authenticated=X,service_role=X}`), while functions written `REVOKE ... FROM PUBLIC, anon, authenticated` are correctly locked to `service_role`. Modelling this in the harness moved the callable-RPC count 203 → 214 — the 11 recovered functions are the dangerous ones. Documented with a warning in the README so the next migration reaches for the form that works.

**Fidelity — the replay-derived baseline was reconciled line-by-line against prod.** Views matched **byte-for-byte** (md5 `f869b6ac…`, 9/9, including `vendor_completed_events honours_rls=NO`). `schema` 4=4, `rls` 0=0, `rlsforce` 0=0. Every remaining difference is fully explained by objects that exist in prod but are created by **no migration**: tables `event_service_deliveries` + `pioneer_incentive_logs`, and functions `confirm_guest_delivery`, `list_vendor_delivery_bookings`, `undo_guest_delivery`, `get_vendor_mood_board`, `rls_auto_enable` — applied out of band. `tpriv` 719 vs 723 (= 2 drift tables × 2 roles); `policy` 803 vs 804 (= 1 policy on a drift table); `func` 214 vs 218 (= 5 out-of-band, −1 replay-only overload prod dropped); `col` 4,398 vs 4,407. Back-filling migrations for those objects would bring them under the guard; noted in the README, not done here.

**Proof it is not vacuous** (this repo has shipped vacuous DB tests twice — an owner connection skips RLS, so the assertion passes regardless): four defences, each an assertion rather than a comment. **Floors** per fact kind, so a half-collected surface cannot look clean. **Baseline integrity** — must exist, parse, be canonically sorted, have unique keys, and match the fact count in its own header. **Behavioural probe** — `SET ROLE authenticated`, first asserting the role is not the table owner, not superuser and has no `BYPASSRLS`, then confirming a column the surface calls withheld is really refused and one it calls readable is really allowed. **Neutralisation** — the differ is fed 17 synthetic widenings and 9 narrowings and must classify every one; delete the guard logic and those fail. No skip path exists: PGlite is in-process, so "no database" is unreachable, and nothing is swallowed by a try/catch.

Demonstrated failing on a synthetic widening (a doctored baseline; the message names the object, explains the risk, and gives the two legitimate ways forward), passing on a narrowing, and passing clean on the real schema. `tsc --noEmit` clean; unit suite unchanged against base.

SPEC IMPACT: None — CI/test infrastructure only, no schema change, no migration, no product surface. The two prod-vs-migration drift findings and the `REVOKE ... FROM PUBLIC` trap are logged in `supabase/security/README.md`; a `DECISION_LOG.md` row is owed if the owner wants the REVOKE idiom recorded as a standing engineering rule.
