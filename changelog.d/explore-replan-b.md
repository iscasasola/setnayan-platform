## 2026-07-27 · feat(vendors): Explore Replan slice B — Coverage Strip v2 (Lucide icon tiles + state rings + count badges + NEXT flag + progress ring), folder-head summary pills, and the page-level ⓘ (flag-dark)

Second slice of the Explore Replan wave (`Explore_Replan_BUILD_SPEC_2026-07-27.md` §3 PR-B, decisions #5 and #8, plus the §11 ⓘ documentation contract). The bench already had a "From your plan" chip strip — a flat, unordered row of the couple's onboarding category picks, each chip carrying one binary dot (any picks / none). It told them *what* they planned; it never told them *where they stood* or *what to do next*. This upgrades that same strip in place.

**Extend, never re-draw.** The `.plan-strip` shell, the `plannedList` derivation and the whole `openPlan(folder, tile, slug)` navigation machinery are UNTOUCHED — the chip strip is now the flag-OFF branch of a ternary and the icon strip is the flag-ON branch, both calling the same `openPlan`. No new component file, no new route, no new query, no schema change.

**Coverage Strip v2** (`_components/shortlist-categories.tsx`). One round Lucide icon tile per in-plan category, with a two-line label beneath it:

- **State** derives from data the bench already holds: `covered` (slice A's `coveredByTile`) > `locked` (a considered vendor in a locked status) > `picked` (a considered vendor pinned in `event_build_picks`) > `exploring` (any considered vendor) > `empty`. Rendered as `st-*` classes — dashed ring / gold solid / heavy gold+shadow / green.
- **Badge** on the icon's corner: `✓` when covered, else the LOCKED count, else the build-candidate count, else nothing. Locked outranks build so a contracted vendor is never hidden behind a candidate number.
- **NEXT flag** on the first not-covered tile in the ordered list.
- **Header**: "Covered X of Y" (Y = in-plan categories) plus a 34×34 SVG progress ring whose `stroke-dashoffset` animation is disabled under `prefers-reduced-motion`.

**Icons are Lucide, not emoji.** The playable prototype draws ⛪ 🎂 🍽️ — those were placeholders for the design conversation. Production maps every tile to a Lucide component in a NEW `lib/taxonomy-icons.ts`: an exhaustive `Record<WeddingTile, LucideIcon>` (no index signature), so adding a taxonomy tile is a compile error until it gets an icon. **Why not beside `WEDDING_TILE_LABEL` in `lib/taxonomy.ts`, as the spec suggested:** taxonomy.ts is pure data + types with zero runtime dependencies and is imported by server resolvers, RSC pages, and plain `node:test` suites that run outside a bundler; a tile→icon-COMPONENT map is a runtime `lucide-react` import and would drag the icon package into all of them. The separate module keeps taxonomy.ts dependency-free and sorts next to it. A few icons repeat across the four attire tiles and the two insurance tiles — Lucide has no distinct glyph for "groom's barong" vs "men's attire", and an honest repeat beats an unrelated one; the label disambiguates.

**Urgency ordering** (new `lib/coverage-strip.ts`, pure + fully unit-tested). Sort keys, in order: covered sinks right → `timelineStatusOf` rank (overdue → due_soon → start_now → upcoming → locked) → longer lead time first (an earlier lock-by floor is the more pressing decision at equal status) → taxonomy order. `timelineStatusOf` and a new `lockLeadDaysFor` helper are now EXPORTED from `lib/vendors-plan-budget.ts` (visibility keyword only, zero behaviour change) so the strip reads the accordion's own planning clock and the two can never drift.

**⚠ The tile→plan-group bridge is MANY-to-one, and the code says so.** `PlanGroup.catalogTile` is not unique across `PLAN_GROUPS` — `ceremony_venue` is claimed by both the `ceremony_venue` and `officiant` groups, and `reception` by more than one. `planGroupsForTile()` therefore returns an ARRAY; urgency takes the most urgent status among them and lead time takes the longest. Treating it as a bijection would have silently dropped one group's deadline. There is a regression test asserting the multiplicity itself, so a future taxonomy edit that accidentally makes it 1:1 (or 1:many the other way) fails loudly.

**Folder-head summary pills.** Each folder head swaps its "N considering / N categories" meta for "● N locked · N to decide · ＋N more" (or "✓ All covered"). Every number is computed from data the surface already has — locked = locked considered vendors anywhere in the folder; to-decide = PLANNED categories that are neither covered nor holding a lock; "＋N more" = categories in the folder that are NOT in the couple's plan, i.e. the pool PR-C will make interactive (presentational here). Computed over the FULL folder, not the search-filtered slice, so the numbers stay true while a query narrows the visible rows.

**Page-level ⓘ** (§11.1). One real `<button>` beside the "Browse the bench" heading in `services-takeover.tsx`; its panel carries what the page does, what the Coverage Strip means, the lock handshake in one line, and the full state-glyph legend (○ ◔ ◕ ● ✓ –). Dismissible by the toggle, a close button, or Escape; state is never persisted (it is help, not a setting); rendered with `<span>`s because it lives inside an `<h2>`, which only admits phrasing content. **Every ⓘ string lives in the new `lib/explore-info-copy.ts`** — none inline in JSX, per §11.3 — including the per-category `categoryHintForTile()` resolver that PR-C will hang the per-tile ⓘ on. The handshake line already reflects the §7 amendment (a lock is a REQUEST until the vendor accepts payment); it deliberately does not say "it's final".

**Data plumbing, no new queries.** `vendors/page.tsx` passes two values it had ALREADY resolved for `buildPlanBudgetModel`: the flattened `event_build_picks` vendor ids and `daysUntilWedding`. Both props are optional with inert defaults.
