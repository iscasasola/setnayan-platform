## 8 · Traps measured during the handover (2026-11-21/22)

1. **GitHub retargets a stacked PR's base by itself** when its parent merges and the parent branch is deleted. Both C
   and D already showed `base: main`. Check before running `gh pr edit --base main`.
2. **Two sessions drove the same two PRs at once.** The original builder kept re-syncing while a handover session did
   the same thing. Neither broke anything, because both used merge commits on top of each other, but the second
   session's STATUS named a head that was already superseded and had to be corrected.
   - **Before you post a STATUS, re-read the PR's head SHA.**
   - **Run one driver per PR.**
3. **The whole preflight takes ~38 min on a 4-core cloud container.**
   - ~24 min of that is the whole-tree guards (785 files / 5,503 tests).
   - ~11 min is the source-scanning DB tests.
   - The quick half (`--only guards,lint,types,pins`) took ~4 min.
   - Never run two at once.
4. **The stop hook asks you to push unpushed commits before the preflight is finished.** The repo rule (whole
   preflight before every push) wins. Wait for it, then push.
5. **CI on these PRs took ~35–55 min wall time** with runners partly queued. `DB replay (n/10)` jobs sat queued for
   15+ min before they started. Queued is not stuck.
6. **A pre-merge check catches nearly everything here:**
   - `git merge-tree --write-tree origin/main <branch>` shows the conflicts;
   - `comm -12` of the two `git diff --name-only <mergebase>` lists shows the semantic overlap.
   For C and D against 72 new `main` commits, the only overlap was the two generated files.
