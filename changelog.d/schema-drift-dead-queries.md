## 2026-07-27 · fix(db): the run-of-show clash check queried a table that does not exist — plus the guard gap that hid it, plus a runtime backstop

Follow-on to the 2026-07-26 phantom-column sweep (#3777 · #3782). A full re-audit of every `.from().select()` in `apps/web` against **production** `pg_catalog` (2,604 table/column pairs over 3,283 sites) found the batch-1/2/3 fixes complete — 15 of the 16 drifted columns were already corrected on `main`. One survived, and it survived for a structural reason worth fixing permanently.

**The live defect — `lib/setnayan-ai-snapshot.ts`, GRD-06.** The Setnayan-AI run-of-show clash rule read `.from('schedule_blocks')`. There has never been a bare `schedule_blocks` relation in production; the real one is `event_schedule_blocks`. PostgREST answered `42P01 undefined_table` on every call, supabase-js resolved `{ data: null }`, and the site's `?? []` handed GRD-06 an empty block list — so the overlap rule could not fire and reported "no clashes" for **every event**, indefinitely. All four selected columns (`label`, `start_at`, `end_at`, `parent_block_id`) exist on `event_schedule_blocks` unchanged, so the fix is the table name alone.

**Why the phantom-column guard shipped green over it.** `findPhantomColumns` does `if (!table) continue` — a site whose TABLE cannot be resolved is skipped entirely rather than flagged. The guard asks "is every column real?" and never asks "is the table real?", so a query naming a relation that exists **nowhere** was invisible to it by construction.

**The ratchet that closes it — `select-column-scan.test.ts` T11/T12.** T11 fails CI when a `.from()` names a relation no migration declares; T12 enforces reason-carrying entries, the shrink-only rule, and staleness. `KNOWN_UNRESOLVED_TABLES` pins the 11 currently-unresolvable names with `KNOWN_UNRESOLVED_CEILING = 11` — 7 matviews, 2 views, `reel_music_tracks` (an ordinary table `readSchema()` genuinely misses — a real parser gap, logged not papered over), and `t` (the scanner reading the literal `.from('t')` in its own doc comment). **Every one was verified present in prod via `pg_class.relkind` on 2026-07-27**, which is what makes the allowlist safe and lets T11 flag the one relation that truly does not exist. Anti-vacuity was proven by negative control, not assumed: re-pointing the query at `schedule_blocks` fails T11 with the exact offender and `file:line`, and restoring it passes.

**The runtime backstop — `lib/supabase/db-error-log.ts`.** Static guards compare code against migrations; they structurally cannot see RLS denials, interpolated selects, filter-only column references, or failed writes. Both Supabase clients now pass a `global.fetch` wrapper that reports any non-2xx `/rest/v1/` or `/storage/v1/` response, so a failing query announces itself instead of rendering as an empty list. Hooking at the fetch layer rather than proxying `.from()` is deliberate: it cannot alter query semantics across ~3,000 call sites, and it covers strictly more ground (writes and RPCs are just non-2xx responses too). **RA 10173:** the query string is stripped from the log (it carries filter values — emails, phone numbers) and the error envelope's `details` field is never read (it can echo row values); only `code` / `message` / `hint` are logged, which name schema, not people. Identical failures collapse to one line, bounded at 500 distinct keys.

Tests — new `lib/supabase/db-error-log.test.ts` (7 cases): a 200 passes through untouched; a 4xx logs **and** leaves the caller's body unconsumed (the `clone()` contract); PII from both the query string and `details` is asserted absent while the relation and column survive; `/auth/v1/` refresh failures stay unlogged; repeats dedupe; a huge non-JSON error page is capped; and a throwing log sink never propagates to the caller. Full unit suite green (4,339), typecheck + lint clean on all touched files.

**Honest limits.** This audit covered `.select()` column and table references only. Bad columns in `.eq()` / `.in()` / `.order()` filters and in `.insert()` / `.update()` payloads fail identically and are **not** yet statically guarded — `lib/ghosting.ts` (fixed in batch 2) named its phantom column in both a select and an `.in()`, so that class is real. Those are now caught at runtime by the fetch logger, but not before merge.
