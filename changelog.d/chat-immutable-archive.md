## 2026-07-24 · feat(chat): archive-not-delete + immutable messages — couple↔vendor chat is an evidence layer

The couple↔vendor conversation is the dispute/evidence record AND the source of the couple-confirmed booking amount, so it must never be destroyed by a user. Two changes make that a schema invariant, not just an app convention.

**1. Archive, don't delete (the destructive path).** `withdrawInquiry` (`app/dashboard/[eventId]/messages/actions.ts`) — the couple's remove-vendor / withdraw-inquiry path — HARD-DELETED the whole `chat_threads` row (cascading `chat_messages` + `chat_thread_reads`). It now stamps a new `chat_threads.archived_at` instead: the thread + every message is preserved and merely folded out of the couple's ACTIVE list into the existing "Archived" section (same fold the `displaced` inquiry already uses), on both the couple page (`messages/page.tsx`, with a "Removed" badge) and the vendor inbox (`vendor-dashboard/messages/surface.tsx`). The `thread.event_id === eventId` defense-in-depth re-check and fail-soft redirect are preserved; the action is now idempotent. Re-adding the vendor RESUMES the same thread: both upsert paths — `startThreadByVendorEmail` and the marketplace `submitInquiry` (`app/v/[slug]/inquiry-actions.ts`) — now set `archived_at: null` on the `(event_id, vendor_profile_id)` upsert, so a removed conversation returns with its full history rather than being orphaned or duplicated. `archived_at` is orthogonal to `inquiry_status`, so a removed-then-re-added `accepted` thread resumes accepted.

**2. Immutability at the RLS layer (defense-in-depth).** The canonical `chat_threads_member_write` policy was `FOR ALL TO authenticated`, which INCLUDED DELETE — that is what let the old hard-delete run straight through PostgREST. Migration `20270926679942_chat_thread_archive_immutable.sql` splits it into explicit INSERT + UPDATE policies (identical predicate: couple OR own-vendor OR assigned-agent) with NO `FOR DELETE` policy, so DELETE is now denied-by-default for every authenticated user — the same append-only posture `chat_messages` already had (INSERT+SELECT only; verified: no per-message edit/unsend/delete affordance exists anywhere in the app, and none was added). The only thread removers remain the service-role paths that bypass RLS: `purge_expired_chat()` (retention sweep) and RA 10173 admin erasure. The migration also adds a partial `chat_threads_active_idx` for the `archived_at IS NULL` active-list scan, and heavily documents that this thread-level `archived_at` is distinct from the per-user Viber marker `chat_thread_reads.archived_at`.

**Retention unchanged.** `purge_expired_chat()` anchors on event age + absence of an `orders` row; it does not read `archived_at`, so archive is a visibility/lifecycle marker, never a legal hold. New DB test `tests/db/chat-immutable-archive.db.test.ts` (7 cases, real RLS via the PGlite migration replay) proves: archive preserves thread + both messages; couple CANNOT DELETE a thread nor edit/delete a message (0 rows affected); the `archived_at IS NULL` predicate folds the thread out of the active list; re-add (archived_at → NULL) resumes the SAME thread with full history; and the retention sweep still purges an old order-less thread while RETAINING one whose event carries an order. Typecheck + lint clean.

SPEC IMPACT: Chat is now an immutable, append-only evidence layer. The couple's "remove vendor / withdraw inquiry" action ARCHIVES (hides + re-openable) instead of destroying the conversation; a chat thread can no longer be hard-deleted by any user (RLS DELETE removed), only by the service-role retention sweep or RA 10173 erasure. This corrects the stale `withdrawInquiry` docstring claim that "a withdraw is a remove" and aligns with the migration-20261126000000 design intent ("Status-flip, NEVER hard-delete").
