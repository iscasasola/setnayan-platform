## 2026-08-10 · fix(retention): the 3-month full-res floor counts from the event's END, not its first day

Owner correction #4 of 2026-08-10 (`Papic_Page_Redesign_Brief_2026-08-10.md` §4, executed as PR 9 of `PAPIC_THREE_ROOMS_BUILD_PLAN_2026-08-10.md` §B): *"3 months after the event **ends**."*

**The defect.** `papic_events_past_fullres_clock(p_retention_days, p_post_event_days)` — the single function that decides whose full-resolution originals may be replaced by their compressed copies — expressed its floor as `e.event_date + p_post_event_days`. `events.event_date` is the event's FIRST day. `events.event_end_date` (added 2027-08-07 by `20270807254184`, `NULL` = single-day) existed the whole time and was consulted by nothing in that function. For a one-day wedding the two are identical, which is why nothing ever showed; for a multi-day celebration — travel is the multi-day type — the closing day's originals became compressible early by exactly the length of the event. A ten-day trip's last night lost its print-quality file nine days before the promise ran out, and the symptom is an ABSENCE: the gallery keeps working, because the compressed copy is what replaces the original. Same silent family as the phantom column, the phantom enum value, the phantom RPC argument and the blocked iframe. Latent in production today — no live event carries a differing end date.

**The fix.** New migration `20271126998711_retention_floor_counts_from_event_end.sql` replaces the function body (`CREATE OR REPLACE`, identical signature / volatility / security / return type / grants, so PostgREST argument resolution and every existing `.rpc()` call site are unaffected). The applied `20271102113000` is NOT edited — the correction ships forward. The date term becomes `GREATEST(COALESCE(e.event_end_date, e.event_date), e.event_date) AS event_last_day`:

- **COALESCE** is the owner's stated fallback — use the end date when there is one, otherwise the start date. Single-day events keep today's behaviour exactly.
- **GREATEST** is a one-way valve, not decoration. `events_end_date_after_start` is a CHECK, and a CHECK can be dropped, added NOT VALID or sidestepped by a backfill; a bare COALESCE would then hand the floor an end date EARLIER than the start and expire those originals early. Wrapped in a GREATEST against the start date, a malformed end date can only ever be ignored — this term can only ever KEEP files longer.
- Postgres `GREATEST` ignores NULLs, so an event carrying only an end date floors on it rather than collapsing to "no floor at all". The NULL escape hatch (`f.event_last_day IS NULL` → fall back to the first-capture clock alone) moves to the same derived term, so the two cannot disagree.

Deliberately NOT re-litigated: the `::timestamptz` cast and the 92-day figure. 92 is the longest three-calendar-month span (1 Mar → 1 Jun) and already absorbs the offset a DATE cast can introduce.

**Every site that computes or describes the floor was swept, not just the SQL.** `lib/daily-email-jobs.ts` needed no behavioural change and that is the point — it calls the SAME rpc with both offsets pulled back by the lead time, so the warning email followed the correction with no edit. A hand-typed copy of the arithmetic there would have started warning couples about a compression date the sweep no longer used, and warning LATER than the sweep runs is the one direction that costs someone their originals; a new executing assertion proves the pulled-back call stays a superset of the sweep's. Comments corrected in `lib/papic-fullres-drop.ts` (its guard list still read "at least 30 days past its event date" — stale on both halves), `lib/papic-fullres-drop-core.ts`, `lib/daily-email-jobs.ts`. Copy corrected in `app/privacy/page.tsx`, `app/dashboard/[eventId]/studio/photo-delivery/page.tsx` and `lib/data-subject-register.ts` — all now say the floor runs from when the event *ends*. The Papic page's own event select needed no change: nothing on that route renders a retention date, so it has no reason to read the end date.

**Guards.** New `apps/web/tests/db/papic-fullres-clock-event-end.db.test.ts` (9 cases) replays every migration into an in-process PGlite and CALLS the function on real multi-day, single-day, backwards-end-date, end-date-only, no-date and no-capture events — semantics, not source text. `lib/papic-fullres-clock.test.ts` was re-pointed, never loosened: it now finds the LAST migration that defines the function instead of reading `20271102113000` by name, because a name-pinned guard would have gone on asserting a superseded body, green, describing a rule the database no longer runs. Its floor-arithmetic regex moved to the new term with word boundaries intact.

**One guard was found broken by the sabotage run and widened.** The inherited tautology check matched `OR TRUE` only. Writing `TRUE OR f.event_last_day IS NULL` neuters the floor identically and went straight through — 16/16 green while a real Postgres run of that same body expired four events that must not have been. `OR` is commutative and the guard was not; it now matches both orders. The executing test caught it either way, which is why it is the primary one.

It is now "3 months after the event ENDS" — the end date where the celebration spans several days, else the start date.
