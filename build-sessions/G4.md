## 2. The delta

1. **`all_vendors` = verified only.** Wherever `getLiveVendorFreeWindows` /
   `getPromotedVendorTierNow` resolve for a vendor, the promotion applies only if that vendor's
   `verification_state = 'verified'`. Unverified and pending never qualify. A db or unit test
   proves a pending vendor gets nothing from an `all_vendors` window.
2. **New audience `new_verified_vendors`** — a vendor qualifies when BOTH their sign-up and their
   doc approval fall inside `[starts_at, ends_at]`, evaluated statelessly at gate time. No
   per-vendor row, no job, no trigger — the same pattern the date windows already use.
   ⚠ **The CHECK re-lists its vocabulary** (`grep -n "audience_type" supabase/migrations/*promo_free_windows*`).
   Memory `a-re-listed-check-vocabulary-drops-a-later-value`: the failure fires only at ALTER
   validation against real rows; the PGlite replay catches it. Also extend — never bypass —
   the `(audience_type = 'all_vendors') = (promoted_vendor_tier IS NOT NULL)` constraint so the
   new value carries its own rule (a tier is required for it too; decide and encode it).
   Migration via `pnpm migration:new`; never a hand-typed prefix.
3. **Deal length per vendor is a SEPARATE control from the window.** The window says who gets
   in; the deal length says how long each qualifying vendor keeps it (28 / 56 / 84 days from
   qualification, or until a fixed date). If `promo_free_windows` has no column for that, add
   one — nullable, with the existing `ends_at` as the default meaning. The copy must say the
   difference out loud: *"How long each qualifying vendor keeps the deal — the window above
   only controls who gets in."*
4. **`/admin/gifts` grows a "Deals" section** (same page — the owner asked for ONE page):
   a creator (Who: all verified vendors / registers + submits docs in this window / segment —
   the third greyed as "not built"; Window; What's free — multi-select from
   `vendor_billing_catalog` with prices READ FROM THE TABLE; Deal length; Reason, required and
   logged) writing through the EXISTING `free-windows-actions.ts` — extend it, do not fork it —
   and rows in the unified list typed `window`, next to the single-vendor rows. The read side
   is a second reader or a view; never a third table.
5. **Provably inert while the flag is off:** a test that, with `PROMO_FREE_WINDOWS_ENABLED`
   unset, a live `new_verified_vendors` window grants nothing to a vendor who qualifies.
6. **OPEN #3 from the plan — measure, don't assume:** does the `price_php > 0` CHECK on
   `vendor_billing_catalog` (migration slug `v2_pricing_table_alignment`) block anything here?
   Tier promotion moves `tier_state`, never a price, so probably not. If any part of your
   design needs a zero-price catalog row, STOP and put it in the PR body as an owner question.
