## 2026-07-25 · feat(vendor): two-ring reach + server-enforced free transport (flag-dark)

Owner-locked model `Vendor_Monetization_Model_LOCKED_2026-07-25.md` § 6 — "Reach: two rings, free-transport ENFORCED". Ships entirely behind a NEW flag `NEXT_PUBLIC_VENDOR_REACH_RINGS_V1`, **default OFF**; with the flag off nothing renders, no new column is read or written, no extra query is issued, and every proposal is composed and totalled exactly as it is today.

**The model.** The EVENT VENUE decides the ring:

- **Ring 1 "free travel"** — served + discoverable, and a quote sent for a venue inside it has its transportation line **rewritten to ₱0 on the server**. The couple's quote carries a "Free Transportation" line.
- **Ring 2 "willing to travel"** — discoverable; the transportation line stays as the vendor composed it.
- **Beyond Ring 2** — the vendor is not shown to that couple. *(Not wired — see "Not wired" below.)*
- Vendors set both rings; the Ring-2 outer bound is **tier-capped: Free/Solo 30 km · Pro 60 km · Enterprise/Custom 100 km.**

**What landed**

- `lib/vendor-reach-rings.ts` — the pure resolver (no env, no clock, no I/O): the `RING2_CAP_KM` ladder, `resolveRingRadii` (clamping), `resolveReachRing` (ring verdict + `transportLocked` + `discoverable`), `parseRingSettings`, `ring2ColumnValue`, `resolveTierForRingSave`, `enforceFreeTransport` and `applyFreeTransportToQuote`. Reuses `haversineKm` from `lib/geo.ts` and `asVendorTier` from `lib/vendor-tier-caps.ts`; **no new geo columns and no new distance math.**
- `lib/vendor-reach-rings-flag.ts` — the flag, in its own module so the resolver stays `tsx --test`-friendly.
- `lib/vendor-reach-rings.server.ts` — the DB half. Reads the ring columns in their OWN narrow query (never folded into `FULL_VENDOR_PROFILE_SELECT` — PostgREST answers an unknown column with 42703 and nulls the whole row) and short-circuits to `null` before issuing anything while the flag is dark.
- **`sendCustomProposalCore` (`lib/proposal-send.ts`) now calls `applyFreeTransportToQuote`** — the single server-side chokepoint every vendor-authored quote passes through, web action and native endpoint alike. This is what makes the ₱0 lock an enforcement boundary rather than a UI affordance: the Proposal Maker composes line items in the browser and POSTs them as JSON, so a crafted request could otherwise hang a ₱15,000 "Transportation" line on a quote for a venue the vendor themselves declared free-travel. The line is rewritten to ₱0 **and the total is recomputed from the rewritten lines**, so `total_centavos` can never disagree with the itemization the couple accepts.
- Migration `20271003528118_vendor_reach_rings.sql` — `vendor_profiles.reach_ring1_km` + `reach_ring2_km` (nullable INT, 0–100 CHECK, partial index). Fail-safe defaults: NULL Ring 1 → 0 km → **nothing is ever forced to ₱0** (a vendor opts IN to free transport); NULL Ring 2 → the tier cap, so discovery never narrows on deploy. Unchanged by this round.
- Vendor settings — new `app/vendor-dashboard/shop/_components/reach-rings-card.tsx` (two sliders + the two-ring map) and `shop/reach-actions.ts`. `ReachMap` grows an optional `freeRadiusKm` inner ring; every existing caller renders unchanged.

**Fixes applied after the 2026-07-26 ship-readiness review** (all six reviewer-CONFIRMED defects; each fix was falsified by reverting it and observing the named test fail):

- **A paid upgrade delivered no extra reach, permanently (HIGH).** The settings card is seeded with the *derived* radius, so any save wrote the tier cap into `reach_ring2_km` and destroyed the NULL "follow my plan's cap" sentinel. A Solo vendor who saved once, then bought Pro at ₱2,499/28d for the advertised 60 km, was clamped to `min(30, 60) = 30` forever — under a card reading "Upgrade to reach farther." `ring2ColumnValue` now collapses at-or-above-cap to NULL, `parseRingSettings` returns `ring2Store`, and the action persists **that**, never `ring2Km`. A deliberately narrower ring still stores as an absolute number.
- **`enforceFreeTransport` had zero call sites (HIGH).** The previous fragment claimed free transport was "ENFORCED" when it was a disabled `<select>`. Now wired into `sendCustomProposalCore` (above). The claim and the code match.
- **Venue trilateration — DESCOPED (HIGH).** The vendor controls both the threshold (their own Ring-1 slider) and the origin (their own HQ pin), and the thread page recomputed the ring live on every load — so ~6 saves plus two HQ moves pinned the couple's venue to ~1 km, in ~20 in-UI clicks, against a location the couple never disclosed. **Removed**: the `transportRing` prop on `ProposalMaker`, the free-travel/Ring-2 banners, the disabled transportation `<select>`, and the `resolveThreadTransportRing` call on the vendor thread page. `app/_components/proposal-maker.tsx` and `app/vendor-dashboard/messages/[threadId]/page.tsx` are now **byte-identical to `main`**. The ring is resolved only inside the server send path and discarded there. Making the ring safe to *show* needs a snapshot-at-accept design (freeze it from inputs the vendor can no longer move); that is not in this branch.
- **Ring-2 slider `min={0}` (MEDIUM).** Zero means "invisible to every couple", and per the defect above it was permanent. `RING2_MIN_KM = 1`; `parseRingSettings` rejects anything below it with a message pointing at Profile → Visibility, and the slider starts there.
- **A transient tier-read failure durably downgraded a paying vendor (MEDIUM).** `asVendorTier(null)` is `'free'`, the smallest cap on the ladder, so a PostgREST blip clamped an Enterprise vendor's 100 km to 30 and wrote it. `resolveTierForRingSave` now aborts the save instead of guessing.
- **Zero tests on the three files where the defects lived (TESTS).** New `lib/vendor-reach-rings-review-fixes.test.ts` (22 cases) covers all of the above, including the end-to-end "save at the Solo cap → upgrade to Pro → actually get 60 km" money path, the re-total invariant, and source-text guards that go red if the enforcer loses its call site, if the action writes the derived radius again, if the slider floor returns to 0, or if the ring verdict is re-introduced into a client surface.

**Why the ring columns are deliberately NOT in `guard_vendor_profiles_entitlement`:** they are a vendor PREFERENCE, not a paid entitlement — the vendor is supposed to write them. The paid thing is the CAP, and the cap is applied at **read** time by `resolveRingRadii`, so a Solo vendor who PATCHes `reach_ring2_km = 999` through PostgREST still resolves to 30 km. Clamp-at-read, not trust-the-column. The DB test pins this decision so a future "hardening" that adds them to the guard fails loudly instead of silently killing the settings card.
