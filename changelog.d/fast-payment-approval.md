## 2026-07-24 · feat(admin): fast payment approval — batch + one-click on clean matches

`/admin/payments` reconciliation was ~2 clicks per payment, one at a time, no bulk, no keyboard. The owner wants faster approval WITHOUT dropping the human money-verification step (there is no bank/GCash feed yet, so auto-approving on a screenshot + reference string would approve faked payments). This speeds the UX while keeping the admin in the loop — batch/one-click is the admin ACTING on rows they reviewed, never the system auto-approving on load.

**Decisive-match predicate (`lib/orders.ts`).** New pure `referenceContainsCode` + `isDecisivePaymentMatch`. A pending payment is a "clean match" iff its reference number contains the order's reference code (case-insensitive) AND this SINGLE transfer fully reconciles the gross owed (`orderReconciledToPaid`). It is a deliberate STRICT SUBSET of `approvePayment`'s shortfall guard: `owed` is computed the exact same way the guard computes it (`orderGrossOwed`, same args, same unset⇒0 VAT rate), so a decisive match here always clears the guard there; it tests THIS payment alone against the full owed (prior matched payments only make the real guard more likely to reconcile); a null requested total (ad-hoc order) is never decisive. A partial/short transfer is NOT clean.

**Queue UI (`app/admin/payments/page.tsx`).** Clean matches are computed server-side, badged ("Clean match"), and sorted to the top. Decisive rows get a genuine ONE-CLICK approve (a plain single-submit form, no confirm modal) that posts to the SAME `approvePayment` with `promote_order` forced on; non-decisive / shortfall rows KEEP the full `ConfirmForm` modal. Each decisive row also carries a batch checkbox.

**Batch approve (`actions.ts` + `_components/batch-approve-controls.tsx`).** A sticky bar + "Approve N selected clean matches". `batchApprovePayments` RE-VERIFIES every submitted id server-side as a decisive clean match (`isPaymentDecisiveById`) before any write — a non-clean / shortfall / already-resolved row is skipped, never force-approved — then approves each through the SAME money path as the single action, aggregating per-row success/skip/failure into an inline notice. No select-all-and-force; "select all" only ticks already-clean rows.

**Shortfall guard preserved.** `approvePayment` was refactored into a thin wrapper over a new `approvePaymentCore` so single + batch drive one code path. Core is the prior body verbatim except two exits: the shortfall `redirect(...)` became `return { ok:false, shortfall }` (wrapper redirects with the same warn notice; batch counts it as a failure — order NOT promoted), and the trailing revalidate became `return { ok:true }` (callers own revalidation). Every guard is intact: pending→matched state-machine flip, the sum-of-matched-vs-`orderGrossOwed` shortfall check, `shouldProvisionOnApproval` gating (provisioning fires only when promoted AND fully reconciled), receipt/payout idempotency. A short payment can reach a clean-match/batch write path only via a hand-rolled POST, and even then the core's own shortfall guard refuses to promote it.

**Cosmetic doc fixes (`inbox-matcher.tsx`).** "8-char Crockford" → "'SN' + 8 uppercase hex" (actual `reference_code` format); removed the misleading "4-tier" label on this client slice (it is a 2-tier reference→amount helper; the 4-tier `match_inbox_to_order` is the separate server matcher).

Tests: `lib/orders.test.ts` gains `referenceContainsCode` + `isDecisivePaymentMatch` coverage — clean full match true; SHORTFALL/partial excluded (the batch-safety case); reference mismatch / missing reference / null total false; ₱1 tolerance still decisive; vendor VAT-inclusive full-pay decisive; voucher-discounted owed nets the discount. Full unit suite green (3028), typecheck + lint clean. Keyboard shortcuts (optional) skipped to keep the money-code surface small.

SPEC IMPACT: None — app-layer UX + a pure predicate; no schema change, no pricing/SKU/flow change. The apply-then-pay manual money-verification model (CLAUDE.md "Payment system") is unchanged; the human still verifies each transfer before approving.
