# MB16 — Vendor Colour Access

**Goal:** a supplier or coordinator can be given standing permission to adjust colour within
their own lane, the couple always sees what changed, and any single change can be undone
without touching that person's ongoing access.

**Model:** Opus · high effort — a new write path into `role_palette`/`reception_design` that
must never widen the RLS boundary those tables have held since day one; the class of mistake
here is exactly the shape this project has spent all day hunting down.
**Size:** 1.5 days. **Depends on:** MB2 (part registry), MB5 (`touchedRoles`), MB10
(`lib/moodboard-gallery.ts`, `MOODBOARD_SLOT_TRADES`), MB12 (notification + email-allowlist
pattern, the client/server boundary lesson below). All four are merged.

## Part 2 — the access model (owner-decided, 2026-09-04, over several rounds — this is final)

**Not a per-change approval. A standing, revocable grant, scoped to a lane.**

- A vendor's lane is derived from their trade: florist → floral parts only; an attire maker →
  attire parts only; a **stylist** → their own decor parts **and the couple's five main
  colours** (the one exception — a stylist shapes the whole look, so their lane is wider).
- **A coordinator is not one lane.** They can hold **several domains at once**, each an
  independent grant: reception decor, main colours, florals, attire. The couple grants only
  what they choose — this is NOT all-or-nothing.
- **Once granted, no per-change approval.** The person can make as many changes as they want
  within their lane without asking each time.
- **Every change notifies the couple.** Reuse MB12's notification + email-allowlist pattern —
  a notification with no allowlist entry reaches nobody, which is the exact gap MB8 found and
  fixed for payments. Do not repeat it here.
- **The couple can reject any single change.** Reverts that one change to its prior value.
  Does **not** revoke the person's ongoing access — they can keep making changes afterward.
- **The couple can turn a person's access on or off at any time**, independent of any reject.
  Three separate controls, none affecting the others: the toggle, the notification, the reject.

## 🛑 The boundary that must not move

`events.role_palette` and `events.reception_design` are writable **only** by the couple today
— confirmed by querying production directly:

```sql
select policyname, qual from pg_policies where tablename='events' and cmd='UPDATE';
-- couple_can_update_event: event_id IN (current_couple_event_ids()) OR is_admin()

select pg_get_functiondef(oid) from pg_proc where proname='current_couple_event_ids';
-- SELECT event_id FROM event_members WHERE user_id=auth.uid() AND member_type='couple'
```

**Do not widen this RLS policy.** A vendor or coordinator's write must never gain raw UPDATE
access to `events`. Instead, follow the exact shape MB8/MB9 already proved: a `SECURITY
DEFINER` function that checks the grant, performs the write internally, and logs it — the same
pattern as `moodboard_begin_render` and `moodboard_set_share_consent`. The couple's own RLS
boundary stays exactly as narrow as it is today; the function is the sanctioned door, not a
wider window.

**Reuse `event_render_share_consent`'s shape as your starting point** (migration
20271201395665_moodboard_paid_render_pipeline.sql) — PK, boolean, timestamps, and a **named**
CHECK constraint (the Ugat schema-claims guard asserts constraints by name; an autonamed one
renumbers the moment a second lands on the table). Your table needs a composite key —
`(event_id, vendor_id, domain)` for vendors, and coordinators need their own row shape since
they are keyed by `user_id` within `event_members`, not `vendor_id` — RULE 0 this before
designing the schema; do not assume one table fits both cleanly without checking.

## Delivers

1. Migration: the access-grant table(s) (vendor lane + coordinator multi-domain), a
