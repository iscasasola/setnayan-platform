## 2026-07-31 · feat(create): ask WHO before WHAT, and stop opening the calendar on today

Two things the approved home-redesign prototype (`06_Prototypes/User_Home_REDESIGN_2026-07-30.html` — `createSheet` / `typeSheet` / `formSheet` / `syncChips`) settled and the live app never got.

**1 · The who-first step (`/dashboard/create-event`).** Sixteen type tiles is a wall; the same sixteen arranged around one named person is a short, obvious list. So the create page now asks **"Para kanino ito?"** before it asks what kind of event it is. This is the only place that question CAN come first — with `NEXT_PUBLIC_EXPERIENCE_QUIZ_ENABLED` on (it is, in prod) picking a non-wedding type immediately `router.replace`s into `/onboarding/[type]`, so anything downstream of the grid is already type-committed. The inline form below the grid is *not* the path most people take, and a who-step built there would have been a screen nobody reaches.

- Roster is REAL: `users.display_name` for "You", the account's alaga rows for the rest, plus an always-present "Someone else". No demo people. When the counsel-gated People layer is off, that is just You + Someone else — and both deliberately leave the grid exactly as it is today, because neither carries anything we can measure.
- The answer SORTS, it never locks: it feeds the picker's already-shipped `hiddenTypeKeys`, whose "show all event types" expander stays the standing doorway (owner 2026-07-17, hidden ≠ locked). A pet / a business / a car folds away the person-only life types (`wedding · debut · christening · graduation · gender_reveal`) but keeps birthday — a dog's birthday party is an ordinary Filipino celebration. A named alaga with a birthdate on file uses their OWN measurement instead of the whole household's, plus the one hard fact a stored birthdate settles: under 18 folds away `wedding` (Family Code Art. 5 — a marriage below 18 is void). No birthdate on file narrows nothing, per person — the same fail-open posture as `hiddenMeasuredTypes`.
- **Picking "You" leaves `honoree_label` EMPTY, on purpose.** The unlabeled slot has always meant the account holder; stamping your own name there would silently open a *second* one-in-planning slot beside every unlabeled event the account already has. Picking a named alaga prefills the label instead.
- The answer is carried into `/onboarding/[type]` through **sessionStorage, not a query param** (`lib/onboarding/honoree-handoff.ts`, single-read, 10-minute TTL). It is a person's first name: a URL would put it in browser history, in the `Referer` of every subsequent request, and in access logs. The wizard consumes it to pre-answer its own "Who are we celebrating?" screen instead of asking one screen later what was just asked.
- The alaga read is now ANDed with the `dependent_minor_profiles` data-privacy control on top of the env flag, matching the strictest shipped posture (`dashboard/(account)/year/page.tsx`) — it returns NAMES now, not just dates. A tighter gate makes the grid hide *less*, which is the module's documented fail-open direction, never a new denial.
- The page's `<h1>` + notices moved into the picker so the heading is the step's own question; the samahan banner / error alert keep their shipped position directly beneath it. The samahan and QR-preselect paths skip the who step entirely (a community event has no personal celebrant; a QR already knows the type).

**2 · Anchor-vs-celebration chips (`/onboarding/[type]` date step).** `events.anchor_date` (what it commemorates) and `events.event_date` (when it is held) both shipped in #3955 and the wizard writes both — but the date step still asked "When is it?" over a blank `<input type="date">`, which every browser opens on **today**, the one month the event has nothing to do with. With an anchor on file the step now reads *"**Your 12th anniversary** falls on **Sat 12 Jun 2027** — you can celebrate any day"* over the real question, **"When are you celebrating?"**, with `On the day` / `The Saturday after` / `Another day`. The chips are a VIEW of the date field, never parallel state, so whatever the calendar lands on re-lights the matching chip; "Another day" seeds the anchor day and opens the picker there rather than blanking it. **No anchor → the step is byte-identical to today** (no context line, no chips, no seeded value), which today means every type except an anniversary whose anchor the user actually typed.

New pure, tested modules: `lib/anchor-celebration-dates.ts` (the nearby-Saturday derivation — plain UTC arithmetic, `null` when the anchor IS already a Saturday, month/year/leap rollovers asserted; plus a locale-free day formatter so server and client can't disagree) and `lib/create-subjects.ts` (the subject roster + what each folds away). 31 new unit tests.

No migration, no RLS change, no pricing or entitlement change. Nothing here asks for or stores a birthdate — the only birthdates in play are ones a guardian already recorded on an alaga.
