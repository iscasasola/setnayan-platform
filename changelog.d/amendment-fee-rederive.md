## 2026-07-24 · feat(booking-fee): re-derive the 5% fee on a post-lock price change (dark)

The Booking Fee is computed ONCE at LOCK off the couple-confirmed `event_vendors.total_cost_php` (migration `20270927120000`). But an accepted change-order / proposal amendment can RAISE or LOWER that agreed total AFTER the lock, and the frozen fee kept charging the stale number. This tracks the fee to the FINAL agreed price — entirely in the FEE lane, without touching the amendment / change-order app flow (owned by a parallel session).

**Detection = a DB trigger, not an app hook.** New migration `20270930120000_booking_fee_rederive_on_amendment.sql` adds `AFTER UPDATE OF total_cost_php ON event_vendors` (WHEN the value changed AND the row is `contracted`/`deposit_paid`/`delivered`/`complete`). It fires no matter WHO moved the price — the amendment-accept RPC, `respond_vendor_proposal`, a change-order settle, or a manual admin edit — so no amendment code is touched. Fail-soft: any error becomes a `WARNING` and never rolls back the caller's amendment.

**Ships INERT / behind `NEXT_PUBLIC_BOOKING_FEE_ENABLED`.** The re-derive only ever acts on a booking that already carries a `primary` fee charge, and charges are minted only by the flag-gated LOCK path (`collectBookingFeeAtLock` returns `{disabled}` before the RPC when the flag is off). So while the flag is off — current prod — no booking has a charge, the trigger universally no-ops, and `event_vendors` UPDATEs are byte-identical to today. "Charge exists" is the DB-native proxy for "the fee was on when this booking locked"; the first fee for a booking is only ever minted at lock, never by an amendment.

**Honest adjustment by settlement state (LIVE money):**
- **primary charge still PENDING (unpaid)** → update its amount to the new 5% in place, and sync its QR order/payment. Amended to ₱0/barter → clear it (paid at 0) and cancel the order.
- **primary charge already PAID (settled)** → never rewrite the settled charge. New fee > already-paid → open ONE supplementary `amendment_delta` charge for the difference + its own vendor QR order (settled by the same `vendor_booking_fee__{id}` sku-activation bridge, unchanged). New fee < already-paid → record an audit-only `amendment_credit` row for the overpayment; **NO auto-refund** (money settles off-platform; a refund is a manual ops decision, never a silent move).
- **free-5 booking** → stays free at ANY amended total. Off-platform / no-marketplace-link → never billed.

**Idempotent + no double-charge:** amounts are compared before every write; partial unique indexes enforce one live `primary` / one pending `amendment_delta` / one `amendment_credit` per `(vendor × event)`. Re-running on the same total is a no-op. Schema is additive on `booking_fee_charges` (`kind`, `parent_charge_id`, `credit_centavos`); the one-live guard is re-scoped to `kind='primary'` so a paid primary and a pending delta coexist. All money writes stay in SECURITY DEFINER functions granted to `service_role` only (RLS-safe; no new client surface).
