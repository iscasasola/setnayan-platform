## 2026-11-23 · fix(plans): Apple-billed shop plans: the server names the shop, and an early refund sticks (follow-up to #8166)

Two faults found in Ship's review of #8166, fixed together (migration `20271360318379_apple_plan_token_binding_and_early_reversal.sql`).

- **Order of delivery.** Apple does not promise to deliver notifications in order. A REFUND or REVOKE that arrived before its SUBSCRIBED used to answer "never granted" and keep nothing, so a later or retried SUBSCRIBED switched on a plan whose money had already gone back. Every REFUND / REVOKE is now kept in `vendor_app_store_reversals`, whether or not anything was granted, and `app_store_supplier_plan_apply` grants nothing for a refunded transaction, or for any transaction bought before a REVOKE of its subscription. A purchase after a revoke is new money and grants as usual. The app's confirm of such a transaction says "refunded", so the phone finishes it.
- **Which shop.** The phone used to send the shop's own id as Apple's `appAccountToken`, and a notification trusted it, so a payer could tie a plan and its Apple billing to another shop. The server now issues the token when a plan purchase starts (`startAppStorePurchase` → `startSupplierPlanForUser`, folded in; server actions unchanged), only for the shop the signed-in person manages, and keeps the pairing in `vendor_app_store_plan_tokens`. A notification grants only to that pairing; a token we never issued grants nothing and is logged for a person. The plan door no longer sends a shop. A purchase made before this change (its token is the shop id) still lands through the app's own confirm when the session proves the person manages that shop, never from a notification alone.

SPEC IMPACT: None. Hardens spec item D ("one subscription = one shop") as written.
