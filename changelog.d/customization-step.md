## 2026-07-27 · feat(vendor-services): ★ Customization step in the service wizard — the shipped package machinery, pointed at one service (flag-dark)

**The couple meets ONE card, so the vendor meets ONE maker.** The package machinery (choices, options, pick-N, follow-up branching, extra-hour caps) has shipped for a while, but it lives on its own route at `/vendor-dashboard/packages`, behind its own navigation, describing a "package" the vendor never set out to build. A vendor publishing a service card had no way to say what a couple may change about it. This adds a **★ Customization** step to the guided service wizard, positioned AFTER "Value & media" and BEFORE "Comes with" / "Review & publish" — **no new tables, no new migration, no second validator.**

**What was reused, unchanged.** `DraftItem` / `DraftOption` / `validatePackageDraft` / `planItemInsertOrder` (`lib/package-authoring.ts`), `savePackage` + `writeItems`' level-by-level insert (`vendor-dashboard/packages/actions.ts`), `autoName` + `findVendorTextViolation`'s `'card'` profile (`lib/service-text-integrity.ts`), and `PACKAGE_CANONICAL_TO_VENDOR_CATEGORY` (`lib/vendor-packages.ts`). **`package-editor.tsx` is untouched** — nothing was moved out of it, and its route behaves exactly as before. The DELTA is the vendor-facing VOCABULARY (four zones instead of an "inclusions" list) and the three branching controls the shipped editor never grew a UI for: pick-N, follow-ups, and the extra-hour cap.

**Serialisation — ONE hidden JSON field (`customization_draft`), not the shipped index-aligned repeater.** The wizard is one `<form action={commitVendorService}>` with every step mounted at once and hidden with the `hidden` attribute, so all inputs post together — whatever this step adds has to serialise into that same FormData. The `service-list-editors.tsx` `getAll()` idiom is correct for FLAT lists and cannot express this: the structure is recursive (options nest in lines; a follow-up names one option on another line by ref), and parallel `getAll()` arrays only align when every row contributes one entry per field, which stops being true the moment line 1 has two options and line 2 has five. Recovering the tree would mean encoding refs inside field NAMES — a second serialisation format wearing a costume. JSON round-trips `DraftPackage` exactly, so what the client validated is byte-for-byte what the server validates again.

**The cost of JSON is paid in `parseCustomizationDraft`, which is TOTAL.** It does not throw for any input — the caller is a server action whose only failure mode is a redirect, and an exception escaping there is a 500 on a form the vendor just spent ten minutes filling. It refuses a wrong version (a stale tab across a deploy would otherwise post a shape that parses into a different meaning, and the write path deletes and re-inserts wholesale), duplicate item/option refs (a duplicate hides a line from the parent/cycle guards that stop a follow-up being written as a top-level line every couple pays for), and an oversized payload. **Absent is not malformed:** a missing/blank field returns `ok: true` with an EMPTY list and NO package is written — an empty-but-real package renders an empty configurator on the couple side. Every `error` on every read added is checked.

**Parse EARLY, write LATE.** Every bounce in `commitVendorService` is a `redirect`, so the parse, the card-text gate (customization lines routed through the SAME `findVendorTextViolation` batch — no new profile), the missing-price check and `validatePackageDraft` all run before the first write, while a bounce is still free. `savePackage` runs only after `save_vendor_service` succeeds. A late failure does NOT route through `back()` — the service is already saved and `back()` re-renders the wizard on the claim path, which would invite a duplicate service; it redirects with a sentence naming both halves ("Your service was saved, but its customization options were not: …").

**Owner locks honoured.** (1) **The vendor never types "included"** — the option price is amount-only with a static `+₱` prefix and live thousands-grouping (`80000` → `80,000`); 0 or blank shows nothing and reads "included" from the PLACEHOLDER, so the word can never be typo'd into a number. (2) **A blank name is auto-named, never refused** — the field's placeholder shows the exact `autoName()` string the server will write, and the save reports the count back through `?autonamed=N` on the services banner. Blanks are named BEFORE validation because `validatePackageDraft` refuses a blank `service_description` and `savePackage`'s own auto-naming runs after it — naming in the wizard's own path leaves the packages route's behaviour exactly as it was. (3) **A follow-up is structurally forbidden from being required or default-included** (`vendor_package_items_followup_not_default_included_ck`): `allowedLineStates()` never offers those two states for a follow-up, and `applyLineState()` treats a forced transition as a no-op rather than a throw. Even promoting a follow-up to a CHOICE keeps it out of the price, where a top-level choice would go in.

**How a service resolves to its package row — IT DOES NOT, and this slice does not invent one.** `vendor_packages` (migration `20260604110000`) carries `vendor_profile_id` + `primary_canonical_service` and nothing that could name a service. So the step CREATES a one-service package anchored to the service's category, which is sound because the wizard is CREATE-ONLY (`/services/new/[category]` is its single mount) — one run mints one package and no path can fork a second. It is sufficient for authoring and **insufficient for editing**; the smallest honest fix is documented in `lib/service-customization-draft.ts` as one nullable `vendor_packages.vendor_service_id UUID REFERENCES vendor_services(...) ON DELETE CASCADE` (additive, idempotent, every existing reader unaffected). Also found: the two category namespaces are NOT the same (`vendor_services.category` is the legacy enum, `canonical_service` is the 0044 taxonomy — `photographer` vs `photography`), and only the canonical→category direction shipped. `canonicalServiceForVendorCategory()` DERIVES the inverse from the shipped map with a first-declared-wins tie-break (that map is written anchors-first, so `venue` resolves to the broad `reception_venue`, not a leaf), and falls back to the category's own string on a NOT NULL TEXT column.

**Flag-dark behind the EXISTING `packageAuthoringEnabled()`** (`NEXT_PUBLIC_PACKAGE_AUTHORING`, off in prod) — no new flag. Off ⇒ the step is absent from the sequence AND unmounted, so it contributes no field, and the server block is inert. `serviceWizardSteps()` is extracted as a pure function so the flag-off guarantee is asserted on step IDs and step COUNT without rendering React.

**Files.** New: `lib/service-customization-draft.ts` (wire format + defensive parser + line-state machine + amount formatting + the service→package bridge), `app/vendor-dashboard/services/_components/customization-step.tsx` (the step; renders no `<form>` of its own — see `scripts/lint-nested-forms.mjs`), `lib/service-customization-draft.test.ts`. Edited: `service-wizard.tsx` (step entry + mount), `services/actions.ts` (parse-early / write-late in `commitVendorService`), `services-manager.tsx` (the `autonamed` half of the saved banner — six lines, not a fifth editor; the `Vendor_Package_Authoring_RECOMMENDATION_2026-07-26.md` §6 PR5 blocker is honoured by extracting the editor as its own component instead).
