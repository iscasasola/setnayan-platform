## 2026-08-27 · fix(admin-search): the assistant was unreachable for the exact sentence it exists to answer

The owner typed the spec's own flagship example — *"add a new category on the taxonomy service"* — into the admin ⌘K box the day after PR #4888 shipped, and it just navigated straight to the Taxonomy page. No form, no questions. This is the case the fill-a-form ask flow (#4888) exists to handle.

**Root cause, verified before fixing, not assumed from the bug report.** `matchJobs()` (`lib/admin-map/match-job.ts`) correctly finds no deterministic job for that sentence — "add / new / category / taxonomy / service" shares no real word with `createCanonicalLeaf`'s own phrase or fields, and its own test (`match-job.test.ts`, "a genuine semantic gap is left honestly unanswered here") already pins that this is deliberate: the AI step is what's supposed to bridge it.

The actual defect was one layer up, in `admin-command-palette.tsx`: the "Ask Setnayan" button only ever rendered inside the `hits.length === 0` branch. "Taxonomy" is a literal page name, so the deterministic page ranker (`rankBySentence`) always finds a hit for this query — `hits.length` is never 0 — so the assistant step could never be reached for the one case the owner actually hit. `rank-by-sentence.ts`'s own docblock even lists this exact sentence as a "now answers" success story for the PAGE search, without noticing it had just sealed off the escape hatch for the FORM search.

**The fix.** A second, deliberately quieter "Ask Setnayan" offer now renders alongside the top page hit whenever (a) no deterministic job already matched — a real job match is strictly better and needs no AI — and (b) the query reads as a sentence describing a task rather than a two-word lookup (`searchTokens(q).length >= 3`, the same 2-vs-more line `match-job.ts`'s own `MIN_SHARED_WORDS` already draws one layer down). Clicking it runs the exact same remembered-then-AI chain the "nothing matched" panel already used (`ask-the-admin.ts`, unchanged) and, if the answer names a form-driven job, opens the same fill-the-form sheet — never a submit, per the one-person admin plan (2026-07-11).

**What does not change.** Typing "papic pricing" or "vendor payouts" still shows only the plain page hit — no AI offer, no nag. Pressing Enter still navigates to the top hit by default; the assistant is an additional path, reached only by clicking the new secondary offer. No job-matching threshold changed, no generated file touched (`admin-jobs.generated.ts`, `admin-routes.generated.ts` untouched), and the assistant still only ever returns a destination — it cannot act.

**Test.** `app/admin/_components/admin-ask-escape-hatch.test.ts` (new) re-derives the palette's gate over the real ranker/job-matcher/tokeniser and the real destination list — not a source-text guess — and pins: the flagship sentence has a page hit AND the assistant stays reachable; ordinary short lookups ("papic pricing", "taxonomy", "pending") never show the offer; a sentence a real job already answers doesn't also nag; and the palette's shipped source still wires the gate this test computes.
