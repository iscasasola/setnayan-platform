## 2026-09-09 · fix(story): bound the day's timeline to the event's own days; bar heights come from a count, not a capped row read

**The bug (Design_Editorial_By_The_Minute_2026-09-07 03 §3 · 08 steps 0.2 + 0.4):** `apps/web/app/[slug]/_components/editorial/data.ts` read "As the Day Unfolded" as `.from('papic_photos').order('captured_at', {ascending:true}).limit(EDITORIAL_TIMELINE_PHOTO_CAP)` (cap 48) with **no lower bound on `captured_at`**. Papic cameras may shoot up to 6 months before the event (`PAPIC_CAPTURE_MONTHS_BEFORE`), so a ~100-capture prenup/despedida shoot filled the entire 48-row cap and the wedding day itself rendered no photograph. The same bug existed in the parallel `papicClipRows` read and in `loadEditorialChaptersForEditor` (the couple's own curation editor, which mirrors this read so its suggested leadIds line up with the public page's).

**Fix:**
- new `lib/story-day-window.ts` (`storyDayWindow`, `storyDayList`, `manilaDayOf`, `allocateChapterCounts`) — pure, unit-tested, reuses `papic-window.ts`'s existing Manila-calendar (+08:00, no-DST) date math rather than inventing a second one;
- both `papicClipRows` and `timelinePhotoRows` (and their mirror in `loadEditorialChaptersForEditor`) are now bounded to `[events.event_date 00:00, events.event_end_date 23:59:59]` in Manila time — unbounded only when the event has no `event_date` at all (unchanged prior behaviour for that edge case);
- **multi-day (08 step 0.4):** "As the Day Unfolded" chapters are now built PER MANILA CALENDAR DAY, not as one flat decile split across the whole event — a flat split could merge a day-1 evening item and a day-2 morning item into the same chapter at a decile boundary. `allocateChapterCounts` shares the existing `EDITORIAL_DAY_CHAPTER_CAP` (10) across days by largest-remainder proportional split, giving every non-empty day at least one chapter when there's room;
- new migration `20271214524793_story_dial_bucket_counts_rpc.sql` adds `story_dial_bucket_counts(event_id, window_start, window_end, bucket_minutes)` — a zero-filled `generate_series` COUNT aggregate for the future dial's bar heights, so heights come from a real count rather than the capped row read (no `generate_series` bucket-count RPC existed in this repo before). Does **not** yet apply the RA 10173 consent veto — that gate is 09 session S3's (guest-layer visibility before publish), noted inline so a future caller doesn't treat the raw count as guest-safe.

Tests: `lib/story-day-window.test.ts` (15 cases, run under Asia/Manila, America/Los_Angeles, Pacific/Auckland — the wall-clock-vs-instant trap the design doc calls out); `tests/db/story-day-timeline-bounds.db.test.ts` against the full PGlite-replayed schema (100 seeded pre-day captures + day-1 + day-2 captures on a 2-day event) — asserts the pre-day captures never appear in the bounded window, a day-2 capture never counts inside a day-1-only window, hidden/unscreened captures stay excluded, and the bucket counts hold every in-window capture even though 100 ≫ the 48-row cap.

SPEC IMPACT: Design_Editorial_By_The_Minute_2026-09-07/08_Build_Order.md steps 0.2 and 0.4 are now DONE (data-layer only — no UI dial exists yet; that's session S9, Phase 2). 03_Data_Requirements.md §3 ("the read that starves") is resolved for the timeline reads; the couple-editor mirror (`loadEditorialChaptersForEditor`) was fixed alongside it since it shares the exact same query shape and its leadIds must stay identical to the public builder's.
