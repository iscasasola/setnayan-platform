## 2026-07-28 · fix(vendors): the Vendors tab filtered `events_host` on the hidden bigserial — date, budget, venue coords and AI status have been dark

`app/dashboard/[eventId]/vendors/page.tsx` read the couple's event context with `.eq('id', eventId)`. Verified read-only against production `information_schema`: `public.events_host` carries **both** `id bigint` (the hidden surrogate, per the canonical-ID lock in `CLAUDE.md`) and `event_id uuid` — and the route param is the uuid. Postgres rejects the whole statement with `22P02 invalid input syntax for type bigint` (reproduced verbatim in prod against a synthetic uuid), so the select **never returned a row**. It was the only one of the 14 queries on that page not filtering on `event_id`.

**What that turned off.** One row carries `event_date`, `event_date_precision`, `estimated_budget_centavos`, `venue_latitude/longitude`, `event_type`, `ceremony_type`, `venue_setting`, `region`, `estimated_pax`, `mood_feel_key`, `date_mode`/`date_candidates`/`date_window_*`, `mood_board_updated_at`, `style_preferences` and `setnayan_ai_active`. With it null, the page ran as "a couple who has filled in nothing": the **Setnayan AI Unlock banner showed to couples whose AI is already active** (`shouldOfferSetnayanAiPurchaseForUser` treats a null event as not-owning), budget-fit and distance scoring had no inputs, the "add your venue to sort by distance" nudge showed on events that have a venue, and the same-date demand / "also eyeing" reads were skipped entirely because they are gated on `eventDate`.

**A sibling, same defect, also fixed.** `app/dashboard/[eventId]/find-date/page.tsx` filtered `.from('events')` on `.eq('id', eventId)` with the same uuid. "Find your date" therefore built its schedule matrix with `eventDate: null`. Both are now `.eq('event_id', eventId)`; `events.event_date` and `event_date_precision` are `SELECT`-granted to `authenticated`, verified in prod, so the base-table read stands as written.

**Swept for more.** All 204 `.eq/.in/.order/…('id', …)` filter sites in `apps/web` were extracted with the repo's own chain walk and cross-referenced against production column types. Every other site is correct: settings singletons key off an integer `id` (`.eq('id', 1)`), `social_publish_settings.id` is genuinely `boolean` (`.eq('id', true)` is the singleton-row idiom), `service_categories.id` is `text`, `demo_sessions` / `event_sponsors` / `event_paperwork` / `push_subscriptions` / `app_telemetry_logs` / `blacklisted_emails` have uuid `id`, and every remaining integer-`id` site passes a number (or a numeric string, which PostgREST casts). These two were the only mismatches.

**Made the failure loud.** Both call sites now check the destructured `error` and route it through `logQueryError` (`lib/supabase/error-detect` — console + Sentry, `graceful_degrade`), the existing repo convention. The page still renders; it just stops being indistinguishable from a genuinely blank event. The `createLoggingFetch` backstop in both Supabase clients already logged the HTTP failure, but nothing at the consumption site could tell "query failed" from "no data" — that gap is what let a one-word filter column survive.

**The regression guard — `query-column-scan.ts` PART 3 + `T11`–`T14`.** Extended the existing filter scanner rather than adding a parallel one. Parts 1 and 2 both ask *"does this column exist?"*, and `events.id` does — it is simply the wrong one, so neither could ever have caught this. PART 3 forbids any `.from('events'|'events_host')` chain from filtering on `'id'` at all: app code never holds an events bigserial, so the check needs no type inference and has no false positives to allow-list. Scope is deliberately the events family only — widening it to "every table with an integer id" would flag ~200 correct call sites and teach people to suppress it.

The new extractor strips comments first (`lib/security/source-text`), unlike the two older ones: `readChain` skips comments *between* links but nothing stopped `.from()` matching inside prose, and the PART 3 docblock quotes the exact chain it forbids — the guard reported its own docstring on the first run. Same class as the LEAK 3 false positive already pinned by T10. **Anti-vacuity proven, not assumed:** T12 asserts detection against the verbatim shape of both live defects, T13 pins the fixed shape and three non-events negatives, T14 asserts `events` really does carry both `id` and `event_id` in the migrations. **Mutation-tested:** reverting either one-word fix turns `T11 · no query filters the events family on its hidden surrogate 'id'` red with the exact `file:line`; restoring it passes.

No migration, no schema change, no feature-flag change — this fix is independent of `NEXT_PUBLIC_EXPLORE_REPLAN_ENABLED`.
