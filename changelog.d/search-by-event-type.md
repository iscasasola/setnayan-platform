## 2026-08-15 · feat(explore): you can search by the kind of celebration — the `?event_type=` filter finally gets a handle

Owner, 2026-08-15, on the browse page: *"they can also search by type of event."*

**RULE 0 changed the shape of this work, and the answer is the sixth gate with no handle.** The marketplace has had a complete event-type filter since Iteration 0041: `?event_type=` is shape-checked in `parseFilters`, validated against the live `event_type_vocab` (16 active kinds, admin-managed, zero deploys), applied as `event_types @> [key]` on `vendor_profiles`, mirrored in the broadened-count fallback that frames the empty state, preserved through every form on the page, and backed by an `EventTypeNotifyForm` for kinds with no inventory yet. All of it shipped. All of it worked.

**Nothing anywhere let a person set it.** Every `name="event_type"` in the public app is a *hidden input preserving* a value that was already there, or the notify-me signup. The only two ways the parameter was ever non-null: auto-applied from a signed-in couple's own primary event, or hand-typed into the address bar. The anonymous visitor standing on the browse page — the person the owner was looking at — could not reach it at all. Nothing was rebuilt; what shipped here is the missing half.

**The typed word now reaches the filter.** `applyMarketplaceTextSearch` gained a fifth axis beside business name / tagline / city / service: a token that names a kind of celebration resolves through the new `lib/event-type-search.ts` against the live roster and ORs in `event_types.ov.{…}` — the *same column by the same means* as the chip filter, so typing "debut" and picking Debut land on identical rows. Passed at **both** call sites: omitting the broadened one would let the widened count exceed the narrow count for an occasion word, and the empty state would offer to widen a search that was already wider.

**The vocabulary is passed in, never imported.** `event_type_vocab` is admin-managed and grows (9 → 16 since the 2026-06-13 cutover). A hardcoded list in the matcher would be a *second* vocabulary drifting from the admin-managed one — the exact disease `editorial-event-types.ts` was written to cure — and a newly launched kind would be silently unsearchable while the admin screen showed it live.

**Two handles, because one surface could not carry both.** The filter drawer gets an **Occasion** select — ported from the Faith section immediately below it, same `.input-field`, same prepended clear option, same hidden-input fallback, so the drawer keeps one control grammar. But the drawer belongs to the *vendor grid*: the bare `/explore` landing is catalog mode and renders no drawer at all, so the search hero gets an **Occasion** chip row of its own. Without it the one public page built for discovery still had no handle.

**No slice on those chips.** Every `enabled` kind renders. A `.slice(0, 6)` would decide in a source file which celebrations are worth showing and hide the rest behind nothing — there is no "all occasions" page to send anyone to, so a capped row is a silent boundary. Which kinds appear is a real product decision and it already has a home: the `enabled` lever at `/admin/event-types`.

**Three smaller things fixed on the way, all pre-existing:**

- **The drawer was silently dropping the narrow.** `filter-drawer.tsx` contained *zero* occurrences of `event_type` — so a couple whose own event auto-applied the filter, who then opened Filters and pressed Apply, lost it without being told. The new select (or its hidden fallback) now always carries it.
- **The applied-filter badge lied.** `countAppliedFilters` never counted the occasion narrow, so the badge read "no filters" on a grid silently scoped to one kind of celebration. Counted now, same honesty rule the faith narrow already had.
- **`/realstories` was about to file a debut under Wedding.** `eventType: it.eventType ?? 'Wedding'` was written when `showcase-db.ts` refused every non-wedding celebration in five places; those refusals were removed **the same day** (owner: *"each event they create will have an editorial not just wedding"*), so the first non-wedding editorial to publish would have been mislabelled in the one control whose whole job is to say what kind of celebration a story is. Now `null` — an unknown kind sits under "All" and joins no milestone rather than claiming the wrong one. ⏭ The real remedy is for `loadPublishedShowcases` to SELECT `events.event_type`; harmless today either way, the facet is behind `STORIES_SEARCH_MIN_POOL` and does not mount.

**The front-door placeholder was deliberately NOT touched.** The first cut added "occasions" to it — written against a base one commit stale, an hour after another session (#4458) made that placeholder DERIVED from `PUBLIC_SEARCH_NOUNS`, so the literal would have silently reverted a guard whose whole purpose is that the promise and the mechanism cannot drift. And once the mechanism was read, the addition was wrong on its own terms: those nouns are RESULT KINDS, each with a resolver emitting hits stamped with that noun. An occasion is an INPUT — nobody gets back "an occasion", they get back suppliers. A test now asserts it stays out. Discovery is carried by the two handles above.
