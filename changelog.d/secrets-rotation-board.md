## 2026-07-25 · feat(admin): Secrets & Rotation board — in-app secret rotation with alarms + Vercel API write-through + safe ENCRYPTION_KEY dual-key rotation

New admin surface `/admin/secrets` ("Secrets & Rotation"), registered in the admin nav beside Integrations and tiled on the `/admin` dashboard. It answers, in one screen, the question the owner previously had to reconstruct from Vercel + GitHub + four provider dashboards: **what keys does Setnayan hold, where does each live, how old is it, and how do I replace it.**

**The registry** (`lib/secrets/rotation-registry.ts`) is the single source of truth — 26 secrets across 9 groups, each with its store (Vercel env / in-app DB / GitHub Actions), env var names, rotation cadence, provider deep link, numbered plain-English runbook, and a blast-radius note. It is also the **allowlist**: every server action resolves the posted `secret_id` through `getSecretDef()` before touching anything, so a crafted form value can never select an arbitrary env var or DB column (same posture `lib/integrations/registry.ts` holds for the Integration console). It holds no secret values — only public metadata — which is why it stays importable by the test runner.

**Three control shapes per row.** Vercel-stored secrets are written straight into the project env through the REST API (`lib/vercel-env.ts`, mirroring `lib/vercel-domains.ts`) with a one-click "Redeploy production" to apply them. DB-stored secrets deep-link to the Integrations console card that already owns them (immediate, no redeploy) — and saving there now **stamps the rotation clock automatically** via a best-effort `stampRotation()` added to the existing integrations actions, so the board never nags about a key the owner just rotated. Everything else carries a runbook plus a "Mark rotated" stamp.

**Age + alarm** (`lib/secrets/status.ts`, pure): `lastRotatedAt` = max(our `platform_secret_rotations` row, newest Vercel env `updatedAt` across the secret's vars) — the env half matters because a secret rotated in the Vercel dashboard would otherwise read as "never rotated" forever. `computeStatus` → `ok` / `due-soon` (14-day window) / `overdue` / `manual` (no cadence) / `unknown` (scheduled but never recorded). Overdue + unknown raise a red banner listing the offenders.

**ENCRYPTION_KEY was a live landmine.** Rotating it naively made every stored integration secret and OAuth token permanently undecryptable — silently: transactional email would simply stop, with no error anywhere. Fixed with a **dual-key read**: `decryptToken` tries `ENCRYPTION_KEY`, then falls back to `ENCRYPTION_KEY_PREVIOUS` when set; `encryptToken` always writes under the primary, so data drifts forward on its own. `lib/secrets/reencrypt.ts` sweeps the remainder across all three ciphertext sites (`platform_integration_secrets` singleton · `events.photo_delivery_oauth_token_encrypted` · `vendor_ig_connections.access_token_enc` — the complete, grep-verified set of `encryptToken()` call sites), reporting `{ reencrypted, alreadyCurrent, failed }`; values that decrypt under neither key are counted and **left untouched**, never nulled. Exposed as an admin-gated button on the card and as `POST /api/admin/cron/reencrypt-secrets` (dual gate: admin session OR timing-safe `CRON_SECRET`, fail-closed). The card carries the 5-step runbook and refuses to let step 5 (delete the previous key) look safe before step 4 reports `failed = 0`.

The crypto primitives moved to `lib/encryption-core.ts` (pure, key-as-argument); `lib/encryption.ts` keeps its `import 'server-only'` and is now the env-reading wrapper. Wire format is unchanged and byte-compatible with everything already stored. Key caches are keyed on the raw env string, so a changed env var invalidates them automatically — no test-reset hook needed.

**Security contract, enforced throughout:** no secret value is ever logged, returned to the client, embedded in a URL, or rendered back. `listProjectEnvMeta()` picks fields explicitly (never spreads) so `value` cannot ride along; the DB read is a boolean presence map; the ENCRYPTION_KEY card shows two booleans. Inputs are write-only, `type="password"`, `autoComplete="off"`, and cleared when the action resolves. Error redirects carry Vercel error *codes* only. Self-generated secrets get a browser-side "Generate" helper (`crypto.getRandomValues`, 32 bytes base64) so the owner never needs a terminal.

Migration `20270930260000_secret_rotation_board.sql` adds `platform_secret_rotations` (secret_id PK, last_rotated_at, rotated_by, note) — bookkeeping only, never a value or a hash of one — with RLS enabled and **no policies**, the same deny-by-default service-role-only posture as `platform_integration_secrets`.

Tests — 3 new node:test suites (30 cases): registry integrity (unique/stable ids · vercel-api rows have writable env vars · db-paste rows deep-link the console · policyDays null-or-≥30 · every row has steps/impact/https provider link · the console column map only points at real ids · unknown ids resolve to `undefined`); `computeStatus` boundaries (exact-policy-age, the 14-day window edge, future timestamps, null-vs-NaN env timestamps not coerced to epoch); and the dual-key rotation (ciphertext under key A survives the swap to B, a fresh encrypt uses B only, post-sweep the previous key becomes unnecessary, neither-key throws rather than returning garbage, tampered auth tags rejected).

**Rider — quarterly BIR 2307 cron job resurrected** (migration `20270930270000_quarterly_2307_vault_auth.sql`): the job's `current_setting('app.cron_secret')` auth design was impossible to configure on Supabase (`permission denied to set parameter` for the postgres role on custom GUCs, both DB- and role-level — verified live), so the quarterly 2307 generation had **silently never run**. The job now reads its `X-Cron-Secret` from Supabase Vault (secret name `cron_secret`; already applied to the live DB 2026-07-25 via `cron.alter_job` — the migration makes it reproducible). The board's CRON_SECRET row documents the coupling: rotating CRON_SECRET must also update the Vault copy.
