## 2026-09-30 · perf(maker): Our Love Story and the Programme are instant — no render of the Maker per edit

Owner, 2026-09-30: *"editing Our Story and the Programme … so hard to edit … Takes so long to edit both. the delay of response is terrible"*; earlier the same day: *"every edit alteration … forces the whole screen to reload"*. Implements DECISION_LOG "EVERYTHING REBUILT IN THE MAKER IS INSTANT BY DESIGN" for the two editors, reusing the RSVP stage's mechanism (#6176 / `rd/maker-instant`: client draft copy, held + batched saves, the Apply count in the save's answer, revert-with-reason).

**Why they were slow (measured in the code):** every Love Story save (the words' "Save your answers", every moment Keep / Hide / Remove) was a server action ending in `landAfterWrite` → `revalidatePath` of the Maker route; every Programme edit (a name on blur, each − / + time step, the eye, a drag, a delete) ended in two `revalidatePath` calls. Inside a server action ANY revalidate makes the answer carry a whole render of the page it was sent from — the Maker (3–6 s on production) — and Next runs actions one at a time, so the next edit waited behind it; the render then moved the canvases' stamp and every stage canvas loaded again.

- **Our Love Story** (`love-story-live.tsx`, loaded with Details — never in the Maker's first load): ONE client copy of the story (`maker-draft-store`, key `events:love_story`) read by the scrapbook, the words panel and a stage's panel. Every change is applied with the server's own functions — `mergeStoryWords` / `patchStoryWord` (`lib/love-story-words.ts`) and `applyMomentIntent` (`lib/love-story-moment-intent.ts`), which `updateOurStory` and `loveStoryMomentAction` now call too, so the tap and the action can never disagree — drawn at once, and saved behind it through `hubDraftAction` intent=save (zero new server actions), batched (`makerLatestWrite`), `held` (no render). The words panel has no Save button: each box saves as it is typed and writes only its own key. A refused save puts the story back as it was saved, on the page and the canvas, and says so. A NEW photo and "Pick from our events" still go to the action (it screens / checks ownership).
- **The Programme** (Details › Schedule, `schedule-live.ts`): every rail write from the Maker is sent `maker_quiet` — the six edit actions revalidate nothing then (`revalidateScheduleUnlessMaker`); the standalone Schedule page is unchanged. A moment's name, place and note draw on the rail, the stage canvases and the Details list AS THEY ARE TYPED; typing and − / + taps are ONE save after the pause. A removed moment leaves the rail when its delete lands. A refused save goes back to the last value that DID save, naming the field.
- **The editor bridge** takes two new messages (`lib/maker-live-preview.ts`): `loveStory` (every scene's words, when, place) and `scheduleMoment` (a moment's name, time, place), laid on `[data-love-*]` / `[data-schedule-*]` on the guest page the server already drew. Editors in Details post through a window event the stage shell broadcasts to its frames (and re-sends to a frame that loads later). What the bridge cannot draw (a moment added / removed / hidden / moved; a time or visibility change) reloads the canvases ONCE after its save landed, double-buffered — the Maker itself is never re-rendered.
- **Sweep (part b):** Details › Words › Special message now saves as it is typed too (held, batched, on Details' card and the tapped scene at once). The remaining Maker edit paths that still ask for a whole-Maker render are LISTED in `the-love-story-and-programme-are-instant.test.ts` (`STILL_REFRESHES` — may only shrink) and in the PR body.
- Dev labs: `/dev/details-lab?item=love-story` (`&seed=1`, `&ms=`, `&refuse=1`) and `/dev/schedule-lab?maker=1` measure edit → visible and saves per burst without a database.
