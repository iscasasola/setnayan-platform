Owner 2026-08-09, verbatim grid:

| | whitelist (per date) | waitlist (per date) |
|---|---|---|
| Free | 1 | 0 |
| Solo | 3 | 1 |
| Pro | 5 | 3 |
| Enterprise | 10 | 5 |

**VOCABULARY FIRST — the two words look alike and mean different things**, and this project uses "whitelist" for *two unrelated features*. Owner-confirmed which one this is: **whitelist = the vendor's ACCEPTED-BUT-NOT-YET-LOCKED customers for a date** — pending demand, live candidates they're still pursuing, informational and never a hold on the date (`Service_Strategy/Service_Schedule_and_Quotation_Flow_2026-06-02.md` § T1.1). In code that is a `chat_threads` row at `inquiry_status='accepted'` whose event has no live booking with them — the exact set `vendor-dashboard/clients/surface.tsx` already renders as "Inquiring". ⚠ **NOT** the `vendor_calendar_day_states.day_state='whitelist'` approve-first DAY STATE, which shares the word, is a different feature, and is deliberately **not** capped here. **Waitlist** = couples queued on a date that is already taken (`vendor_date_waitlist`), of whom the vendor may pick N — the existing flat 1–3 setting, now tier-derived.

**🔑 ONE GRID, NOT TWO HAND-TYPED COPIES.** The numbers must exist in TypeScript (the UI shows them) and in SQL (the enforcement has to be in the database — the accept path is reachable from the vendor inbox, the admin demo console and any future surface, and a per-date count is racy client-side). Two hand-maintained lists that agree today drift silently tomorrow, so `tests/db/vendor-tier-pipeline-caps.db.test.ts` **imports `TIER_CAPS` from the TypeScript SSOT and interrogates `vendor_tier_limit()` for every tier × key**. Editing one side alone turns CI red; there is no third place to update. (Mutation-proved: drifting Pro 5→6 in SQL alone fails 4 tests.)

**Shipped:**

- `apps/web/lib/vendor-tier-caps.ts` — `whitelistPerDate` + `waitlistAcceptances` on `TierCaps` and all six tiers, with `vendorWhitelistPerDate()` · `vendorWaitlistAcceptances()` · `canUseWaitlist()`. `verified` (the legacy free tier) takes the FREE numbers so the ladder stays monotonic; `custom` clones Enterprise per the standing owner rule.
- Migration `20271121655918` — `vendor_tier_limit(tier, key)`, a BEFORE trigger on `chat_threads` enforcing the whitelist cap per date, and a BEFORE trigger on `vendor_profiles` **clamping** waitlist settings to the plan (clamp, not raise: a downgraded vendor must still be able to save their own settings page). An unknown *key* returns `NULL`, never a silent `0` — a typo cannot read as "block everything".
- The waitlist settings picker is now built from the vendor's plan instead of a hardcoded `1/2/3`, so nobody is offered a number the database would clamp away behind their back. A plan with **no** waitlist gets a written sentence, not a disabled switch that reads as a bug (the no-fake-door pattern).
- `acceptInquiry` translates `WHITELIST_DATE_LIMIT` into a sentence. It arrives as a Postgres exception, and every other tier wall in this app reads as a sentence rather than a crash. It does not leak who the other couples are.

**🛑 SHIP-DARK, and this one matters more than usual.** Gated on `platform_settings.vendor_tier_pipeline_caps_enabled`, **default FALSE**, mirroring the two existing tier gates (`free_tier_booking_cap_enabled` · `VENDOR_TIER_FEATURE_GATE`). **Every vendor in prod today is `tier_state='free'`** (2 shops, both hidden), so switching it on now would cap the owner's own test vendors at ONE live candidate per date. It also brushes against the **2026-07-24 lock** — *"your inbox is never locked — every vendor can receive AND answer inquiries with no tier wall"*. These are different things (this caps per-DATE pipeline depth, not inbox access; a capped vendor still answers every other date and frees a slot by declining someone, the § T1.4 decline-the-others-first rule) — but at FREE=1 the second couple asking about the *same* date cannot be accepted until one is dropped. **Surfaced for the owner rather than silently shipped hot.** Flip: `UPDATE public.platform_settings SET vendor_tier_pipeline_caps_enabled = TRUE WHERE id = 1;`
⏭ **Named debt, not done:** that switch has no admin button yet, exactly like its `free_tier_booking_cap_enabled` precedent. A gate with no handle has bitten this project twice; naming it here so it is a decision, not an oversight.

**🚨 AND A PRE-EXISTING BUG FOUND BY THE TESTS: THE SQL TIER LADDER COULD NOT REACH SOLO.** `vendor_tier_rank()` enumerated only free · verified · pro · enterprise and sent everything else to `ELSE 0`. The enum has **six** values. So `solo` ranked **0, below free's 1** — and `guard_vendor_tier_no_silent_downgrade` read **free → solo as a DOWNGRADE and raised**. *A free vendor could not be put on Solo at all* — the first paid step on the ladder and the one every new subscriber takes. `custom` ranked 0 too, so enterprise → custom was blocked as a "downgrade" while custom → free never was. Latent, not live (the guard fires only on a tier CHANGE and prod has sold no subscriptions), but it would have bitten on the first Solo purchase, silently, with green CI. Fixed to mirror `TIER_RANK` one-for-one, with a test asserting the two ladders sort identically — plus one proving a *genuine* downgrade is still refused, so the fix cannot be mistaken for weakening the guard.
🔑 **The `ELSE 0` was written to be safe** — its own comment says a new tier "can never be silently treated as outranked by pro" — **and it did the opposite for two tiers that already existed.** A default that swallows *known* values is not a safety net, it is a hiding place.

**Tests — 25 db cases, all driven through real INSERT/UPDATE so the trigger wiring is exercised, never by reading a function body.** Parity (both keys × six tiers, derived from TS) · the owner grid verbatim · unknown key → NULL · unknown tier → free · both ladders sorting alike · free→solo allowed · genuine downgrade still refused · monotonicity · **the switch defaulting OFF and changing nothing while off** · Free 1 / Pro 5 / Enterprise 10 with the next one refused · per-date isolation · locking-in and declining each freeing a slot · re-accept never refused · no-date events never capped · one vendor's full date not touching another's · the waitlist clamp at 0/3/5 · the widened 0..10 CHECK · both triggers attached.

### Follow-up in the same PR — two guards pre-empted rather than discovered by CI

- **`anon-rpc-surface.baseline.txt`** now declares `enforce_vendor_whitelist_per_date` and `clamp_vendor_waitlist_to_tier`. Both are `RETURNS trigger`, so PostgreSQL refuses any call outside a trigger context and the anon EXECUTE grant is inert (same shape as `enforce_free_tier_booking_cap`). Neither takes a caller-supplied argument; the enforcer only ever RAISEs (it writes nothing) and the clamp only ever NARROWS the row in flight, so neither could widen anything even if it were reachable. Both are additionally inert until the platform switch is on. `vendor_tier_limit` does not appear because it is REVOKEd from anon and authenticated.
- **The suite runs `SET TIME ZONE 'UTC'`** — the clock prod and CI actually use. Nothing here casts a timestamptz to a date (the whitelist cap compares `events.event_date`, a DATE, to a DATE), so this changes no result; it is pinned because the sibling PR the same day shipped a fix that was **inert in prod** for exactly that reason while passing on a +08 laptop. Cheap insurance, and it documents the hazard for the next person editing this file.
