## 2026-09-09 · fix(ci): the events-grant guard sees every column, not just the first

`lint-events-column-grants.mjs` required `ADD COLUMN` to follow `ALTER TABLE events`
**immediately**, so in a comma-separated statement it captured **only the first column**:

```sql
ALTER TABLE public.events
  ADD COLUMN IF NOT EXISTS a TEXT,   -- seen
  ADD COLUMN IF NOT EXISTS b TEXT;   -- INVISIBLE
```

This is the only thing standing between an ungranted `events` column and every signed-in
read of that table going silently empty — `public.events` revokes table-level SELECT and
re-grants a per-column allowlist, and PostgREST refuses the **whole query** for one
unreadable column. The db coverage tests structurally cannot catch it: their `before()`
re-applies the lockdown, recomputing the allowlist over the brand-new column, so the bug
disappears exactly where it would be tested.

### Measured, not reasoned

| | before | after |
|---|---|---|
| events columns the scanner sees | **129** | **209** |
| grandfathered | 120 | 182 |
| newly surfaced, ungranted | — | 67 |

Found by sabotage during PR #5330: two columns were added in one statement and the
**second** one's `GRANT SELECT` line was deleted — the guard still **exited 0**. That PR
worked around it by splitting into one `ALTER TABLE` per column, which protects that one
migration and nothing else.

### The 67 were adjudicated one at a time against production

**None of them was a live outage**, which is why they could be grandfathered rather than
re-litigated:

- **62 still exist and every one is READABLE by `authenticated` in prod.** They predate the
  lockdown, whose blanket re-grant covered them. **None went into `NO_GRANT_NEEDED`** —
  that set means *deliberately unreadable*, and it would have been a lie for all 62.
- **5 were dropped from the table** (`editorial_tone`, `editorial_language`,
  `sde_published_at`, `sde_poster_r2_key`, `papic_pool_token_rotated_at`) and go into a new,
  separately named `DROPPED_SINCE_ADDED` set — migrations are never edited, so their
  `ADD COLUMN` text is still there to be found, but there is no column left to grant.

🔑 **`GRANDFATHERED` was itself generated by the narrow regex, so it was short by exactly
these names.** Growing it 120 → 182 completes a set that was always meant to contain them;
its docblock now says so, and keeps the "do not add to this set" rule for genuinely new
columns while recording that this was a one-time completion, verified in prod first.

⚠ **Residual risk, named rather than hidden:** if a future migration RE-ADDS one of the 5
dropped names, `DROPPED_SINCE_ADDED` silently excuses it and the column ships ungranted.
That is the one way a new column can still hide. It is written into the set's own docblock.

### Sabotage matrix — the guard can fail, and the old one could not

Occurrence counts printed before and after each mutation, against a 3-column fixture:

| mutation | grants | new guard | old guard, same tree |
|---|---|---|---|
| honest fixture | 3 | **0** ✅ | 0 |
| delete grants for the **2nd and 3rd** columns | 3→1 | **1** ✅ names *both* | **0** ✗ the hole |
| delete the **1st** column's grant | 3→2 | **1** ✅ | 1 (no regression) |
| remove the `events_host` rebuild | — | **1** ✅ names all 3 | would name only the 1st |

The fixture was removed before committing; the working tree contains only the guard.

### The widening opened a second hole, so it is closed in the same change

Scanning a whole statement means the span has to END somewhere, and it ends at the first
`;`. The guard only stripped **whole-line** comments, so a trailing one carrying a semicolon
would have ended the statement early and hidden every `ADD COLUMN` after it — a silent miss,
the very failure being fixed. Trailing comments are now stripped too.

Measured before changing it: **243 statement spans in the tree, 0 currently truncated** that
way — so this closes the hole before it opens rather than fixing a live miss. Proven with a
fixture whose trailing comment contains a semicolon: the hardened guard flags the ungranted
column after it (exit 1); a variant with only whole-line stripping **exits 0 and never
mentions it**.

`[^\n]*` cannot run past its own line, so the worst case is losing the rest of one line that
had `--` inside a string literal, never a following statement. The column count over the real
tree is **identical** either way (209), and `lint-one-comment-stripper` still passes
unchanged at 291 known — this file is not on that baseline and does not join it.

⚠ SQL **block** comments (`/* … */`) are still unhandled. That is pre-existing, no migration
in the tree uses one inside an `ALTER TABLE events` statement, and it is named here rather
than quietly left out.

A side effect worth noting: the `events_host` half of the guard now reports **every** column
of a multi-clause statement instead of just the first, so its error message stops
under-reporting the work needed to fix it.

SPEC IMPACT: None. This is a CI guard, not product behaviour.
